# 2026-09-14 학습 정리 — VR Pawn 벽 통과(Wall Clipping) 방지 시스템 구축

- 작성자: 김신정
- 주제: 물리 콜리전 없이 쿼리(트레이스) 기반으로 VR 이동 중 벽 통과를 막고, 텔레포트·튜토리얼 요소는 그대로 통과시키는 구조 설계
- 대상: `BP_XRPawn`(`ContinuousMove`, `ClampMoveByWallTrace`), `BP_Portal`, `BP_HoloGuide`, `Hall_Guide_1~5`, `Hall_Icon_2~5`, `BP_StageToggle`
- 테스트 경로: Unreal VR Preview (에디터 PIE, 자동 스폰/컴파일 검증 + 실기기 수동 확인 병행)

## 이번 학습의 결과 요약

| 구분 | 내용 |
| --- | --- |
| 한 일 | 스틱 연속 이동 시 벽을 그냥 통과하던 문제를, 몸에 물리 콜리전을 붙이지 않고 "이동 직전 캡슐 트레이스로 미리 물어보는" 방식으로 해결했다. |
| 문제 | 처음엔 캡슐을 액터 루트에 직접 붙였다가 스폰 실패·바닥 끼임·이동 완전 정지 등 연쇄 버그를 겪었다. |
| 해결 | 콜리전을 몸에 붙이는 대신, 이동량만큼 캡슐을 한 번 스윕 트레이스해서 막히면 벽을 따라 미끄러지도록(`ProjectVectorOnToPlane`) 이동 벡터를 보정하는 순수 쿼리 방식으로 전환했다. |
| 완료 | 벽은 막히고, 포털·튜토리얼 안내판·아이콘은 통과하며, 통과 대상 조회를 캐싱해 성능도 최적화했다. 다만 텔레포트/룸스케일 물리 이동 경로는 이 로직을 타지 않는다는 한계는 남아있다. |

## 1. 목표

기존에는 `BP_XRPawn`의 루트 컴포넌트(`VROrigin`)에 콜리전이 전혀 없어서, `ContinuousMove`가 `AddActorWorldOffset(bSweep=true)`로 스윕 체크를 하는 것처럼 보여도 실제로는 아무것도 막지 못했다. 왼쪽 스틱으로 밀면 벽을 그냥 통과했다.

목표는 다음 두 가지를 동시에 만족하는 것이었다.

1. 실제 벽/가구는 막는다.
2. 텔레포트 포털, 튜토리얼 안내판·아이콘처럼 **막히면 안 되는 오브젝트**는 그대로 통과시킨다.

## 2. 첫 번째 시도와 실패: 캡슐을 루트에 직접 붙이기

가장 직관적인 방법은 `CapsuleComponent`를 만들어 액터 루트로 승격시키는 것이었다. 그런데 이 접근에서 연쇄적으로 문제가 발생했다.

1. **스폰 실패**: 캡슐이 스폰 지점 바닥과 살짝 겹치자, `SpawnCollisionHandlingMethod`가 `AdjustIfPossibleButDontSpawnIfColliding`로 되어 있어 폰 자체가 스폰되지 않았다. 콜리전이 없던 원래 루트에서는 한 번도 발동한 적 없던 설정이 캡슐을 붙이자마자 문제를 일으킨 것이다.
2. **이동 완전 정지**: 캡슐을 `GetActorLocation()`(바닥 높이) 기준으로 배치하니, 반지름만큼 바닥 밑으로 파고든 상태로 스윕이 시작돼 방향과 상관없이 항상 "막힘" 판정이 나서 이동 자체가 안 됐다. 회전(오른쪽 스틱, `SnapTurn`)은 이 로직을 안 타서 정상 동작했기 때문에 "왼쪽만 안 된다"는 증상으로 보였다.
3. 캡슐을 다시 제거하고 원상 복구한 뒤에도 같은 스폰 실패 로그가 재현되는 것을 서버 로그로 직접 대조해, **이 실패가 벽 뚫기 작업과 무관한 별개 이슈가 아니라 캡슐 자체의 구조적 한계**라는 결론을 내렸다.

## 3. 최종 접근: 몸에 콜리전을 붙이지 않고 쿼리로만 판단

액터 콜리전을 완전히 제거하고, `ContinuousMove`가 이동량(`DesiredDelta`)을 실제로 적용하기 **직전에** 별도 함수 `ClampMoveByWallTrace`를 통과시키는 구조로 바꿨다.

```text
ContinuousMove
  → DesiredDelta 계산 (스틱 입력 × 카메라 요(Yaw) × 속도 × 델타타임)
  → ClampMoveByWallTrace(DesiredDelta) 호출
      1) 통과 대상 액터 목록 확보 (최초 1회만 조회, 이후 캐시)
      2) 바닥 기준 15~130cm(중심 72.5cm, 반지름 20cm) 캡슐로
         현재 위치 → 이동하려는 위치까지 1회 스윕 트레이스
      3) 막히면: 충돌면 노멀로 이동 벡터를 투영(ProjectVectorOnToPlane)
                해서 벽을 따라 미끄러지는 벡터로 변환
      4) 안 막히면: 원래 이동 벡터 그대로 반환
  → 보정된 벡터로 AddActorWorldOffset 적용
```

이 방식의 핵심은 **액터 자체에는 물리적 콜리전이 없다**는 점이다. 그래서 스폰 시점 콜리전 검사, 바닥 임베드, 캡슐이 가구에 끼는 문제가 구조적으로 발생하지 않는다. 대신 매 이동마다 "물어보고" 판단하기 때문에, 이 함수를 거치지 않는 이동(텔레포트, 실제 몸을 움직이는 룸스케일 이동)에는 적용되지 않는다는 트레이드오프가 있다.

트레이스 높이를 처음엔 가슴 높이(90cm) 한 곳만 뒀다가, 높이 74cm짜리 로비 소파를 못 잡는 사각지대가 발견되어 정강이 높이(35cm) 트레이스를 추가했다. 이후 최적화 단계에서 구체 2개를 캡슐 트레이스 1개(15~130cm 연속 구간)로 통합해, 사각지대 제거와 쿼리 횟수 절반 감소를 동시에 달성했다.

## 4. 통과 대상 처리: 태그만으로는 부족했던 이유

포털·튜토리얼 요소를 통과시키기 위해 `VRPassthrough` 커스텀 액터 태그를 만들고, `GetAllActorsWithTag` + 트레이스의 `ActorsToIgnore` 파라미터로 제외하는 방식을 썼다.

그런데 태그를 달아도 일부 오브젝트가 계속 막혔다. 원인은 태그 시스템과는 별개로, **오브젝트 자신의 콜리전 프로파일이 트레이스에 쓰는 Visibility 채널을 이미 Block으로 막고 있었기** 때문이다.

- 튜토리얼 안내판의 `WidgetComponent`는 기본 `UI` 콜리전 프로파일을 쓰는데, 이 프로파일이 Visibility 채널을 Block한다.
- 안내판 앞에 떠 있는 3D 아이콘(`Hall_Icon_2_Move` 등, 별도 `StaticMeshActor`)은 `BlockAllDynamic` 프로파일이라 모든 채널을 막는다.
- 두 경우 다 `ActorsToIgnore`가 있어도, 오브젝트 자체 콜리전 응답을 직접 Visibility=Ignore로 바꾸는 것이 훨씬 확실했다. 이후 태그(`VRPassthrough`)는 향후 다른 오브젝트를 추가할 때 쓸 수 있도록 이중 안전장치로 남겨뒀다.
- 안내판 앞 아이콘처럼 텍스트 패널과 별개 액터로 떠 있는 오브젝트가 있다는 것은 에디터 뷰포트를 직접 캡처해서 육안으로 확인하고서야 알아챘다. 이름만으로 추정하는 것보다 실제 화면을 보는 편이 확실했다.

## 5. 부수적으로 발견하고 고친 버그: `BP_StageToggle`의 None 접근 에러

작업 중 PIE 로그에 `BP_StageToggle`의 `UpdateButton` 함수에서 "GetPlayerPawn 결과가 None"이라는 런타임 에러가 반복적으로 찍히는 것을 발견했다.

- 이 에러는 `BP_XRPawn`을 완전히 원상 복구한 상태에서도 동일하게 재현되어, **벽 뚫기 작업과 무관한 기존 버그**임을 서버 로그로 확인했다.
- 원인은 `UpdateButton`이 매 틱 `GetPlayerPawn(0)`을 호출하는데, 레벨 시작 직후 플레이어 컨트롤러가 폰을 빙의하기 전 몇 프레임 동안 None이 반환되는 흔한 타이밍 이슈였다.
- 함수 맨 앞에 `IsValid` 분기를 추가해, 폰이 아직 유효하지 않은 프레임에는 조용히 건너뛰도록 수정했다. 기존 로직은 폰이 유효해지는 즉시(보통 1초 이내) 그대로 실행된다.

## 6. 성능 최적화

`ClampMoveByWallTrace`가 스틱을 미는 동안 매 프레임 호출되는데, 초기 구현은 매번 `GetAllActorsWithTag`로 레벨 전체 액터를 훑고 있었다. 통과 대상 목록은 런타임에 바뀌지 않으므로, `bPassthroughCached` bool과 `CachedPassthroughActors` 배열 변수를 추가해 **최초 1회만 조회하고 이후엔 캐시를 재사용**하도록 바꿨다.

## 7. 알려진 한계 (의도적으로 미해결)

- **룸스케일 물리 이동으로 인한 벽 끼임**: 헤드셋을 쓰고 실제로 몸을 기울이거나 걸어서 벽에 다가가는 경우는 스틱 입력이 아니므로 `ContinuousMove` 경로를 타지 않는다. 헤드셋 위치는 하드웨어 트래킹 값이라 애초에 콜리전 체크 대상이 아니다. 물리적으로 막는 것은 불가능하고, 해결하려면 몸(콜리전)이 머리 위치를 따라가다 막히면 화면을 페이드시키는 별도 시스템이 필요하다. 이번 세션에서는 팀 논의 후 우선순위를 낮춰 보류했다.
- 텔레포트는 내비메시 에이전트 반경(35cm)이 이동 트레이스 반경(20cm)보다 넉넉해 벽에 붙어버릴 위험은 낮다고 판단했지만, 별도 검증 로직은 없다.

## 8. 협업 시 주의할 점

- 앞으로 통과시켜야 할 새 오브젝트가 생기면, **먼저 그 오브젝트 자신의 콜리전 프로파일(특히 Visibility 채널 응답)을 확인**한 뒤 `VRPassthrough` 태그를 달 것. 태그만 달고 콜리전 프로파일을 안 보면 이번처럼 계속 막힐 수 있다.
- `ClampMoveByWallTrace`의 캡슐 범위(바닥 위 15~130cm)보다 낮거나 높은 가구/구조물은 여전히 사각지대일 수 있으므로, 새 전시물을 배치할 때 실제로 걸어서 확인하는 편이 안전하다.
- `BP_XRPawn`은 바이너리 에셋이라 동시 수정 시 충돌 위험이 크다. 이동/콜리전 관련 함수(`ContinuousMove`, `ClampMoveByWallTrace`)를 건드릴 계획이 있으면 미리 공유할 것.

## 9. 다음 확인 항목

1. 룸스케일 벽 끼임 대응(화면 페이드) 진행 여부를 팀과 논의해 결정한다.
2. 새로 추가되는 전시실 오브젝트(특히 낮은 가구, UI 패널)에 대해 콜리전 프로파일을 표준화하는 방안을 검토한다.
3. 캡슐 트레이스 슬라이드 로직의 구석(코너) 케이스는 현재 방 크기가 넉넉해 보류했지만, 좁은 구간이 추가되면 재검증이 필요하다.

## 10. 한 줄 회고

VR 이동에서 벽을 막는 문제는 "몸에 콜리전을 얼마나 정교하게 붙이느냐"가 아니라 **"어떤 순간에 어떤 방식으로 물어보고, 무엇을 예외로 둘지를 얼마나 명확히 설계하느냐"**의 문제였다 — 물리 콜리전을 포기하고 쿼리 기반으로 전환한 뒤에야 스폰·바닥 끼임 같은 부작용 없이 안정적으로 동작했다.
