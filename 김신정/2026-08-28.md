# 2026-08-28 학습 정리 — VR 유물 복원 체험 프로젝트 핸드트래킹 시 기술 스택 선정

- 작성자: 김신정
- 관련 Jira 작업: 없음
- 학습 주제: VR 유물 복원 체험 프로젝트의 기술 스택을 대안 대비 선정 이유 중심으로 정리
- 대상: Unreal Engine 5 / Meta Quest 2 · PICO 4 / OpenXR 핸드트래킹 / CNN 스케치 인식 / Blender + Claude Code 복원
- 목적: 팀 스터디·기록용 요약. 왜 이 기술을 골랐는지(대안 대비 이유) 중심.

## 1. 프로젝트 개요

**전제**

| 항목 | 내용 |
|---|---|
| 엔진 | Unreal Engine 5 |
| 타깃 기기 | Meta Quest 2, PICO 4 |
| 데이터 소스 | 국립중앙박물관 "소장품 3D 데이터", 국가유산청 "국가유산 디지털 서비스(3D 에셋)" |

**핵심 사용자 흐름**

1. 사용자가 VR 안에서 손으로 허공에 그림을 그린다 (예: 토기 형태)
2. 그린 그림을 AI가 인식해서, 해당하는 실제 유물(예: 빗살무늬토기)을 찾아낸다
3. 먼저 **기존 상태**(깨지거나 무늬가 소실된 실제 발굴 상태)의 3D 모델을 보여준다
4. 이어서 **복원된 상태**(원형, 무늬가 이어진 완성도 높은 모습)로 전환/연출한다
5. *(부가, 우선순위 낮음)* 사용자가 손으로 유물을 직접 만져볼 수 있게 한다

```
[손으로 허공에 그리기] → [AI 스케치 인식] → [기존 상태 유물 등장] → [복원 연출] → (만지기)
```

## 3. 기술 선정 이유 상세

### 3-1. 엔진: Unreal Engine 5 (vs Unity)

- 유물 표면 디테일(질감, 풍화 흔적)을 실감나게 보여주는 게 중요한 프로젝트라, **Nanite/Lumen 기반 고품질 렌더링**이 강점인 UE5가 유리함
- 복원 연출(조각이 모이고 무늬가 채워지는 과정)을 만들 때 **Sequencer**(시네마틱 타임라인 툴)가 강력함
- AI 모델을 엔진 내부에서 직접 돌릴 수 있는 **NNE(Neural Network Engine)** 가 공식 지원됨
- *(참고)* Unity가 XR 핸드트래킹 생태계 진입장벽은 더 낮은 편이지만, 이번 프로젝트는 비주얼 퀄리티와 연출이 핵심이라 UE5 선택이 합리적

### 3-2. 표준 API: OpenXR (vs 기기별 전용 SDK만 사용)

- Quest 2(Meta)와 PICO 4(바이트댄스)는 제조사가 다른 헤드셋 → 각자 전용 SDK로만 개발하면 로직을 두 번 짜야 함
- **OpenXR**은 여러 헤드셋 제조사가 합의한 공통 표준이라, 핵심 로직(손 추적, 인터랙션)을 한 번만 짜고 기기별로는 최소한의 설정만 얹으면 됨
- 향후 다른 헤드셋(Quest 3, Vision Pro 등) 확장 시에도 유리

**기기별 추가 플러그인**

| 기기 | 필요 플러그인 |
|---|---|
| Quest 2 | Meta XR (OculusXR) Plugin |
| PICO 4 | PICO Unreal OpenXR SDK |

### 3-3. 핸드트래킹 구현 방식

| 항목 | 선택 | 이유 |
|---|---|---|
| 손끝 위치 추적 | `UOculusXRHandComponent` 등 관절 트랜스폼 API | 플러그인이 관절 위치를 자동 갱신, 별도 하드웨어 없이 헤드셋 카메라만으로 인식 |
| 그리기 On/Off 판정 | 엄지-검지 손끝 **거리 계산**으로 직접 핀치 판정 | OS별 pinch-strength 바인딩(예: Meta 전용 값)에 의존하면 크로스플랫폼이 깨짐. 거리 계산은 플랫폼 무관하게 동일 로직 사용 가능 |
| 궤적 시각화 | **Niagara Ribbon** | UE5 내장 VFX 시스템이라 별도 플러그인 불필요, 실시간 리본 렌더링에 최적화. 오픈소스 Open Brush가 같은 방식으로 구현되어 있어 참고 가능 |

#### 난이도 체감

- 손 인식 자체(기본 세팅) → **쉬움**, 공식 샘플로 하루~이틀
- 핀치 + 궤적 기록 로직 → **중간**, 며칠
- 트래킹 노이즈(손가락 겹침, 빠른 움직임 시 튐) 스무딩 → **실제로 가장 시간 잡아먹는 폴리싱 구간**
- Quest2/Pico4 동시 대응 → OpenXR 덕에 큰 부담 없음, 기기별 실기기 테스트 시간만 별도 확보

#### 현실적으로 부딪히는 마찰 (과소평가하면 안 되는 부분)

- Meta XR SDK와 PICO OpenXR SDK가 UE 버전에 따라 궁합이 안 맞아 플러그인 충돌이 흔함
- "표준"인 OpenXR이라도 기기마다 관절 인덱스 순서, 트래킹 신뢰도 값 등 미묘하게 달라서 완전한 공용 코드로는 안 끝나고 기기별 분기 처리가 어느 정도 필요함
- PC 한 대에서 **Quest 런타임과 PICO 런타임을 동시에 "활성 OpenXR 런타임"으로 못 둠** → 테스트 기기 바꿀 때마다 PC에서 런타임 전환 필요
- 결론: "어렵다"기보다 **"삽질이 반드시 낀다"**에 가까움. 다만 이미 남들이 겪은 유형의 문제라 감당 가능한 수준

#### 언리얼 에디터에서 바로 확인 가능

- 매번 APK 빌드 없이, PC에 헤드셋을 연결해두고 에디터의 **VR Preview**로 실행하면 손 트래킹까지 에디터 안에서 실시간 확인 가능
  - Quest 2: Quest Link(유선) 또는 Air Link(무선)
  - PICO 4: PICO Streaming Assistant
- 단, 위 런타임 전환 이슈 때문에 "개발 중 빠른 확인"은 에디터에서 하되, "이 기기에서 진짜 잘 도는지" 최종 확인은 APK 빌드 후 스탠드얼론 실행으로 별도 검증 필요 (PC 연결 상태와 완전 독립 실행은 성능/트래킹 특성이 다를 수 있음)

### 3-4. 그림 인식 (AI)

- **CNN 이미지 분류기**를 선택 *(vs 컨투어/DTW 같은 규칙 기반 템플릿 매칭)*
  - 손으로 그린 궤적은 사람마다 삐뚤빼뚤함 → 규칙 기반 매칭은 오탐이 잦음
  - 학습 기반 분류기가 다양한 손그림 편차에 더 강건하고, 캡스톤 프로젝트로서 "AI 활용" 임팩트도 큼
- 데이터: 공개된 Quick, Draw! 데이터셋은 일반 사물 위주라 그대로 못 씀 → **팀에서 직접 빗살무늬토기 실루엣 스케치를 수집**해 자체 데이터셋 구축 필요
- 그린 궤적 → 2D 실루엣 이미지로 변환 → 분류기에 입력

**연동 방식: 외부 Python 서버** *(vs UE5 내장 NNE)*

- NNE(ONNX 인게임 추론)는 네트워크 지연이 없다는 장점이 있지만, 모델을 바꿀 때마다 엔진 재빌드/재설정이 필요해 개발 속도가 느림
- 프로젝트 기간이 정해진 스터디/캡스톤 특성상, **FastAPI 등으로 별도 서버를 띄우고 HTTP/WebSocket으로 통신**하는 쪽이 반복 실험과 모델 교체에 훨씬 유리
- Quest2/Pico4는 PC에 유선/무선 연결(Quest Link, PICO Streaming Assistant)해서 PC VR로 구동 — 렌더링과 AI 추론 모두 PC가 담당하고 헤드셋은 트래킹/디스플레이만 담당 (스탠드얼론으로는 실시간 AI 추론 감당 어려움)

### 3-5. 유물 복원 파이프라인: Blender + Claude Code (MCP)

- `blender-mcp`를 통해 Claude Code가 Blender의 Python API(`bpy`)를 직접 호출 → 자연어 지시로 **지오메트리(형태) 복원**(대칭 보완, 깨진 메시 복구 등) 가능
- 실제로 사용해본 결과 형태 복원은 결과물이 꽤 좋았음
- **한계**: `bpy`는 지오메트리/머티리얼 노드 세팅은 다룰 수 있지만, "이 부분이 원래 어떤 색이었을지"를 새로 그려내는 **이미지 생성** 작업은 못 함 → 풍화/탈색 등 색상 복원에는 적용 안 됨

**색상/풍화 복원을 위한 대안** *(추후 확장)*

- 유물 텍스처를 UV 이미지로 추출 → 이미지 **인페인팅 모델**(Stable Diffusion 계열 등)로 손상 부분만 채워 넣고 재임포트
- 또는 유사 유물 레퍼런스를 참고해 프로시저럴 머티리얼(색 그라디언트/패턴 셰이더)로 "추정 복원" 연출만 하는 절충안

> **정리**: 지오메트리 복원(Blender+Claude MCP)과 색상 복원(이미지 생성 AI)은 서로 다른 종류의 AI가 필요한 별개 작업으로 스코프를 나눠서 진행하는 게 합리적.

## 4. 단계별 실행 가이드 (Step-by-step)

전체를 한 번에 만들려 하지 말고, **각 단계 끝에서 항상 "돌아가는 데모"가 있는 상태**를 유지하는 순서로 진행합니다.

### Phase 0 · 환경 세팅 (1~2일)

1. Unreal Engine 5 설치, 빈 VR 템플릿 프로젝트 생성
2. Edit > Plugins에서 **OpenXR**, **OpenXR Hand Tracking** 활성화
3. Quest 2용 **Meta XR (OculusXR) Plugin** 설치
4. PICO 4용 **PICO Unreal OpenXR SDK** 설치
5. 프로젝트 세팅에서 Hand Tracking Support 옵션 켜기
6. PC-헤드셋 연결 준비: Quest 2는 Quest Link/Air Link, PICO 4는 PICO Streaming Assistant 설치

확인 목표: 에디터 VR Preview로 헤드셋 화면이 뜨고, 손 스켈레톤(뼈대)이 보이는 것까지

### Phase 1 · 손 트래킹 & 그리기 (며칠~1주)

1. 손 액터에 손 컴포넌트(`UOculusXRHandComponent` 등) 붙여서 관절 트랜스폼 받아오기 확인
2. 검지 손끝(Index Tip) 본의 월드 위치를 매 프레임 로그로 찍어서 값이 잘 나오는지 검증
3. 엄지-검지 손끝 거리 계산 함수 작성 → 임계값 이하면 "핀치 중"으로 판정
4. 핀치 중일 때 손끝 위치를 배열에 누적 기록
5. 기록된 위치들을 따라 Niagara Ribbon 스폰/업데이트 → 허공에 궤적이 그려지는지 확인
6. 트래킹 튐 방지용 위치 스무딩(이동 평균/보간) 적용

확인 목표: 핀치해서 허공에 선을 그리면 리본이 실시간으로 따라오는 데모

### Phase 2 · "쉬운 버전" 파이프라인 완성 (며칠)

1. 그리기 완료 트리거(핀치 해제 후 일정 시간, 또는 별도 버튼) 구현
2. 완료되면 무조건 미리 정해둔 유물(예: 빗살무늬토기) **기존 상태 메시**를 스폰
3. 몇 초 뒤 **복원 상태 메시**로 전환 (Level Sequence 크로스페이드 또는 머티리얼 Dissolve 파라미터)

확인 목표: "그리기 → 유물 등장 → 복원 연출"까지 처음부터 끝까지 손으로 돌려볼 수 있는 상태 *(이 시점에 이미 데모 가능)*

### Phase 3 · AI 스케치 인식 연동 (1~2주)

1. 팀원들이 빗살무늬토기(및 필요하면 다른 유물) 실루엣을 여러 번 그려서 데이터 수집 (그린 궤적을 2D 이미지로 저장하는 툴 먼저 필요)
2. 간단한 CNN 분류기 학습 (PyTorch)
3. FastAPI 등으로 추론 서버 구축, `/predict` 같은 엔드포인트로 이미지 보내면 분류 결과 반환
4. UE5에서 그리기 완료 시 궤적을 2D 이미지로 렌더링 → HTTP로 서버에 전송 → 결과 받아서 해당 유물 스폰 (Phase 2의 "무조건 고정 유물" 로직을 이걸로 교체)

확인 목표: 실제로 그린 모양에 따라 다른 유물이 나오는 데모

### Phase 4 · 실기기 검증 & 폴리싱 (지속)

1. Quest 2, PICO 4 각각 APK로 패키징해서 스탠드얼론(또는 PC 연결) 실행 테스트
2. 트래킹 품질, 프레임 드랍, 인식 정확도 등을 실기기에서 재확인 및 튜닝
3. 손 인터랙션 "손맛" 다듬기 (반응 속도, 리본 두께/색 등 UX 디테일)

### Phase 5 · 확장 (여유 있을 때)

1. 색상/풍화 복원 — 텍스처 인페인팅 모델 적용
2. 유물 그랩(만지기) 인터랙션 추가
3. 여러 유물 종류로 확장 (데이터셋/모델 일반화)
