# 2026-08-31 학습 정리 — 명세 재작성과 VR 환경 이해

- 학습 주제: AI가 만든 기존 명세를 뜯어보며 무엇이 잘못됐는지 파악하고, 팀 기준으로 다시 세우기
- 병행 학습: VR 앱이 일반 앱과 무엇이 다른지 — 기기 성능, 이동·회전 방식, 멀미
- 확인 기준: 근거가 없는 값은 채우지 않고 "미확정"으로 남긴다

---

## 1. 핵심 결론

**1) AI가 쓴 명세는 그럴듯하지만 팀이 합의하지 않은 내용이 섞인다.**

기존 `PROJECT_MASTER_SPEC.md` v1.0은 형식이 완벽했다. 요구사항 ID, 수용시험, 추적표까지
다 있었다. 그런데 뜯어보니 **팀이 한 번도 논의하지 않은 내용**이 절반이었다.

가장 놀란 것은 **엔진이 Unity로 쓰여 있었다**는 것이다.
`Unity` → `언리얼5` 전역 치환만 한 흔적이 87곳 있었다.

```text
docs.언리얼53d.com          ← docs.unity3d.com
com.언리얼5.xr.hands        ← com.unity.xr.hands
6000.0.66f2                 ← Unity 6 버전 번호
ScriptableObject / SceneManager / persistentDataPath / IL2CPP
```

3부·4부 전체가 Unity 기준인데 이름만 언리얼이었다. 그대로 따라 만들었으면 전부 헛일이 됐다.

**2) "빈칸"보다 "근거 없이 채워진 값"이 더 위험하다.**

v1.0에는 핵심 성공 지표 3행과 7인 역할표가 **통째로 비어** 있었다. 이건 눈에 보인다.
반면 복원 대상이 `ssu022891-001-30000_Step3.stl`로 **못박혀** 있었는데,
이건 팀이 정한 게 아니라 누군가의 실험 파일이었다. 이건 눈에 안 보인다.

빈칸은 채우면 되지만, 잘못 채워진 값은 **틀렸다는 걸 아무도 모른 채** 진행된다.

**3) 문서가 버전 변천사를 겸하면 읽기 어려워진다.**

처음엔 "v1.0에서 무엇이 바뀌었나"를 문서 앞에 넣었다. 회의에서 빼자는 지적을 받았다.
맞는 지적이다. **명세는 지금 무엇을 만드는지만 말하고, 왜 바뀌었는지는 결정 기록이 담당한다.**

## 2. 명세를 다시 세운 방법

한 번에 다시 쓰지 않고 **질문 → 답변 → 확정 → 기록**을 8라운드 반복했다.

| 라운드 | 정한 것 |
| --- | --- |
| R1 | 엔진, 주력 기기, 범위, 핵심 컨셉 |
| R2 | 팀 역량, 엔진 확정 게이트, 입력 방식, VR 경험 |
| R3 | 전시 방식, 정보 UI, 유물 조작, 복원부 표시 |
| R4 | 복원 사례, 제작 방식, 검증 절차 |
| R5 | 2D→3D 모델, MCP 범위, provenance |
| R6 | 입력 경로, 전시 규모, 팀 역할, 시연 상황 |
| R7 | 직군 정의, 성능 예산 방침 |
| R8 | MUST 범위, 일정, 산출물 형태 |

**배운 것:** 문서를 먼저 쓰고 검토받는 것보다, **뼈대를 질문으로 확정한 뒤 쓰는 게 빨랐다.**
쓰고 고치면 이미 쓴 문장에 끌려간다.

각 라운드 결과는 `docs/DECISIONS.md`에 `D-01`~`D-43`으로 남겼다.
**나중에 "왜 이렇게 정했지?"를 되짚을 수 있게** 근거까지 같이 적었다.

## 3. 명세에 넣은 두 가지 장치

### 3-1. 미확정 항목 등록부

v1.0의 근본 문제가 "정하지 않은 것을 정한 것처럼 적은 것"이었으므로,
**비워둔 것을 비워뒀다고 기록하는 자리**를 만들었다.

| 항목 | 결정 시점 | 결정 못 하면 |
| --- | --- | --- |
| 엔진 최종 확정 | W1 게이트 | Unity로 전환 |
| 성능 예산 수치 | W1 실기 측정 | 임시 기준 유지 |
| 복원 대상 유물 | W1~W2 | 확보 가능한 것 중 선정 |

핵심은 **"결정 못 하면 무엇으로 가는지"까지 적는 것**이다.
이게 없으면 미확정 항목이 그냥 방치된다.

### 3-2. W1 결정 게이트

프로젝트 생사를 가르는 네 가지를 1주차에 몰아서 판정하도록 했다.

| 게이트 | 확인 | 실패 시 |
| --- | --- | --- |
| G1 엔진 | UE5로 실기 빌드가 되는가 | Unity로 전환 |
| G2 데이터 | 실측 3D 스캔을 확보할 수 있는가 | 사진 단일 경로 |
| G3 생성 | 3D 생성 모델이 도는가 | 실행되는 것 1개 |
| G4 MCP | Blender MCP로 메시 편집이 되는가 | 복원 단계 축소 |

**배운 것:** 위험은 뒤로 미루면 커진다. **되돌릴 수 있을 때 확인해야 한다.**
5주 중 4주차에 엔진이 안 된다는 걸 알면 손쓸 수 없다.

## 4. VR 환경 이해

명세를 쓰려면 VR이 일반 앱과 뭐가 다른지 알아야 했다. 이해한 것들이다.

### 4-1. 기기 성능 등급

| 기기 | 칩셋 | 세대 |
| --- | --- | --- |
| Quest 2 | Snapdragon XR2 | **Gen 1** |
| PICO 4 | Snapdragon XR2 | **Gen 1** |
| Quest 3 | Snapdragon XR2 | Gen 2 |

우리 보유 기기는 둘 다 **Gen 1**이다. Quest 3 기준으로 잡힌 v1.0의 성능 예산
(72Hz / 350k tris / draw call 120 / 256MiB)은 **그대로 쓸 수 없다.**

**배운 것:** "VR 기기"라고 뭉뚱그리면 안 된다. 세대가 다르면 예산이 다르다.
그래서 성능 수치를 명세에 적지 않고 **W1 실기 측정 항목으로 남겼다.**

### 4-2. VR 멀미 — 이동과 회전이 왜 중요한가

VR 멀미의 1순위 원인은 **몸은 가만히 있는데 시야만 움직이는 것**이다.
눈은 "움직인다"고 보고하는데 전정기관은 "안 움직인다"고 보고한다. 이 불일치가 멀미를 만든다.

| 방식 | 멀미 | 자연스러움 |
| --- | --- | --- |
| 텔레포트 | 적음 — 이동이 순간이라 흐르는 시야가 없다 | 낮음 |
| 연속 이동 | **많음** | 높음 |
| 스냅 턴 (30도씩) | 적음 | 낮음 |
| 스무스 턴 | **많음** — 시야 전체가 계속 흐른다 | 높음 |

상용 VR 앱이 텔레포트를 기본으로 두는 이유가 여기 있다. 뚝뚝 끊기는 어색함이
멀미를 막는 **안전장치**다.

> **팀 결정:** 회의에서 **연속 이동 + 시선 회전**으로 정했다. 자연스러움을 택한 것이다.
> 멀미 위험은 인지하고 감수하되, 이동 가속을 최소화하고 리허설에서 시연자 여러 명이
> 사전 검증하기로 했다. 명세 위험 표에 등재했다.

### 4-3. 시연 방식이 요구사항을 바꾼다

시연을 **발표자가 착용하고 미러링**하기로 정하자 우선순위가 통째로 바뀌었다.

| 항목 | 착용자가 심사위원일 때 | 발표자일 때 |
| --- | --- | --- |
| 초심자 온보딩 | 최우선 | **핵심 아님** — 숙련자다 |
| 미러링 화면 가독성 | 부차적 | **최우선** — 심사위원은 화면으로만 본다 |

v1.0의 `NFR-UX-001`("VR 초심자 5명 중 4명이 5분 내 완주")을 MUST에서 내렸다.

**배운 것:** 같은 기능이라도 **누가 쓰느냐**에 따라 요구사항의 우선순위가 뒤집힌다.
기능 목록을 먼저 정하고 사용자를 나중에 정하면 이런 게 안 잡힌다.

### 4-4. UE5 + Quest 2 조합의 난이도

UE5의 모바일 VR 렌더링 경로는 Unity URP보다 최적화 여지가 좁다.
팀에 UE5 경험자가 없다는 점까지 겹쳐서, **엔진 확정을 W1 게이트로 미루고
Unity 기반 v1.0 문서를 폐기하지 않고 보관**하기로 했다.

`docs/archive/v1.0-unity-PROJECT_MASTER_SPEC.md`가 그 이유로 남아 있다.

## 5. 협업 규칙과 저장소 정리에서 배운 것

명세와 별개로 `CONTRIBUTING.md`와 저장소 구조도 손봤다.

### 5-1. 문서와 실물이 어긋나 있었다

| 문서 | 실제 |
| --- | --- |
| 브랜치 `develop` | **`dev`** |
| Jira 키 `S15P11C103` | **`S15P21C201`** |
| 데일리 리포트 `docs/week-NN-이름` 브랜치 | **`Study` 브랜치에 팀원 폴더** |

문서대로 `git switch develop` 하면 실패한다. 규칙 문서가 틀리면 **아무도 안 따르게 된다.**

### 5-2. `.gitignore`는 코드를 올리기 전에 있어야 한다

언리얼은 `Binaries/` `Intermediate/` `Saved/` `DerivedDataCache/`를 계속 만든다.
이걸 한 번 커밋하면 저장소가 금방 무거워진다.

Git LFS도 마찬가지다. **`.gitattributes`를 먼저 커밋·푸시한 뒤 바이너리를 추가해야 한다.**
순서가 바뀌면 이미 올라간 파일이 LFS로 전환되지 않는다.

**배운 것:** 저장소 설정은 **파일이 들어오기 전에** 끝내야 한다. 나중에 고치면 이력을 다시 써야 한다.
