## 1. 핵심 결론

**1) MCP는 손을 대신해 주지만 이해를 대신해 주지 않는다.**

전시대와 정보 패널을 MCP로 거의 전부 만들 수 있었다. 그런데 정작 막힌 지점들은
"어떻게 만드는가"가 아니라 **"왜 동작하지 않는가"** 였고, 그건 엔진의 동작 방식을
알아야 풀렸다. 명세 4부의 원칙(MCP만 쓰면 학습이 되지 않는다)이 실제로 맞았다.

**2) 화면으로 판단하면 틀린다.**

근접 감지는 코드상 문제가 없어 보였는데 실제로는 전혀 동작하지 않았다.
PIE를 실행해 런타임 상태를 직접 읽어보고서야 원인을 찾았다.

```text
만들었다 → 컴파일됐다 → 동작한다  (X)
만들었다 → 컴파일됐다 → 실행해서 상태를 확인했다 → 동작한다  (O)
```

**3) VR은 "평면 화면 UI + 3D"가 아니라 다른 규칙의 세계다.**

스크린 스페이스 UI를 못 쓰고, 자동 노출을 못 쓰고, 조명 Mobility가 기능 설계를 제약한다.
Unity 경험에서 옮겨올 수 있는 개념도 있었지만 VR 특유의 제약은 따로 배워야 했다.

| 전시 공간 | VR 템플릿 레벨 복제 후 데모 소품 정리, 흰 벽·천장 구성 |

```text

단계 전환 (버튼)          → (단계 + 1) % 3 → 메시 교체 + 패널 텍스트 갱신
```

## 3. 개념 정리

### 3.1 VR의 UI는 월드 공간에 놓는다

평면 게임의 UI는 화면에 붙는다(스크린 스페이스). VR은 화면이 두 개이고 머리가 움직이므로
화면에 붙은 UI는 쓸 수 없다. `WidgetComponent`를 `World` 스페이스로 놓아
**3D 공간의 판**으로 만든다.

여기서 처음 헷갈린 것: 디자이너에서 만든 UI가 실제와 크기가 달라 보였다.
위젯 루트에 크기가 없으면 디자이너 캔버스(기본 Fill Screen) 전체로 퍼지기 때문이다.

→ 루트를 `SizeBox`로 감싸고 `WidgetComponent.DrawSize`와 같은 값으로 고정하면
  디자이너에서 보는 것과 헤드셋에서 보는 것이 일치한다.

### 3.2 조명 Mobility가 기능 설계를 제약한다

| Mobility | 라이트맵 | 움직이는 물체를 직접 비추나 | 런타임 비용 |
| --- | --- | --- | --- |
| Static | 굽는다 | **아니오** | 0 |
| Stationary | 굽는다 | 예 | 있음 |
| Movable | 안 굽는다 | 예 | 큼 |

**Static 라이트는 움직이는 물체를 직접 비추지 않는다.** 이걸 몰라서
"조명을 넣었는데 유물이 어둡다"에서 한참 막혔다.

그리고 이게 우리 프로젝트의 핵심 기능과 직접 부딪힌다.

```text
복원 3단계 토글 = 런타임에 메시를 교체한다
        ↓
유물은 Static일 수 없다 (Movable이어야 한다)
        ↓
유물을 비추는 조명은 Stationary여야 한다
        ↓
Quest 2에서 동적 조명 개수 예산을 신경 써야 한다
```

기능 요구사항 하나가 조명 설계 전체를 결정한다는 것이 인상적이었다.

**정리한 구성**

- 공간 전반 조명 → Static (구우면 런타임 비용 0, 공짜로 방을 밝힌다)
- 전시물 조명 → Stationary (유물을 직접 비출 수 있는 유일한 선택)

### 3.3 라이팅 빌드가 왜 필요한가

`LIGHTING NEEDS TO BE REBUILT` 경고를 보고 알아본 내용.

움직이지 않는 물체의 조명은 미리 계산해 텍스처(라이트맵)로 구워 파일에 저장한다
(`<레벨명>_BuiltData.uasset`). 실시간으로 계산하지 않으므로 모바일에서 필수다.

- 정적 물체를 옮기거나 추가·삭제하면 → 다시 굽는다
- Static/Stationary 조명을 바꾸면 → 다시 굽는다
- 머티리얼 알베도를 바꾸면 → 다시 굽는다 (반사광이 달라지므로)

레벨을 복제할 때 `_BuiltData`가 따라오지 않아 경고가 떴다.

### 3.4 노출(Exposure)

가장 예상 못 했던 개념. 카메라가 밝기를 자동으로 맞추는 기능이다.

**자동 노출을 켜둔 채로는 조명을 조정할 수 없다.** 조명을 낮추면 노출이 올라가서
화면은 그대로다. 실제로 "너무 밝다"의 원인이 조명 세기가 아니라 노출이었다.

VR에서는 고정해야 한다.

- 고개를 돌릴 때 밝기가 출렁이면 멀미가 난다
- 미러링 화면(FR-UI-006)이 매번 다르게 찍힌다

`PostProcessVolume`의 Min/Max Brightness를 같은 값으로 두면 고정된다.

**부작용도 배웠다.** 노출을 고정하니 정보 패널이 어두워졌다.
월드 공간 UI도 씬과 똑같이 노출·톤매핑을 타기 때문이다.

```text
흰 글자 0.95  ×  노출배율  =  거의 검정
```

위젯의 Tint RGB를 올려 보정했다. 틴트는 곱셈이므로 색끼리의 대비는 유지되고
절대 밝기만 올라간다.

### 3.5 흰 방은 생각보다 밝다

벽 알베도(반사율)가 높으면 빛이 여러 번 반사되어 **직접광보다 반사광이 더 밝아진다.**
알베도 0.86을 0.75로 낮추자 체감 밝기가 꽤 줄었다. 여전히 흰색으로 읽힌다.

## 4. 막혔던 지점과 원인

배운 것 중 가장 값이 컸던 부분이다. 전부 "만들었는데 안 되는" 상황이었다.

### 4.1 에디터 언어가 한국어라서 막혔다

블루프린트 노드의 타입 ID가 UI 언어를 따라간다.

| | 한국어 | English |
| --- | --- | --- |
| BeginPlay | `이벤트추가\|이벤트BeginPlay` | `AddEvent\|EventBeginPlay` |
| 메시 교체 | `컴포넌트\|스태틱메시\|SetStaticMesh` | `Components\|StaticMesh\|SetStaticMesh` |

MCP의 블루프린트 DSL은 `AddEvent|` 접두사를 하드코딩하고 있어서
**한국어 에디터에서는 이벤트 노드와 Cast 노드를 아예 만들 수 없었다.**
영어로 바꾸자 둘 다 해결됐다.

교훈: 튜토리얼·문서·도구가 모두 영어 기준이다. **에디터는 영어로 쓴다.**

### 4.2 폰에 충돌체가 없어서 근접 감지가 안 됐다

트리거 구체를 달고 `EventActorBeginOverlap`을 연결했는데 아무 일도 없었다.
PIE로 폰을 트리거 안으로 옮겨봐도 반응이 없었다.

원인: **`BP_XRPawn`에 충돌 컴포넌트가 하나도 없다.** 캡슐도 바디도 없다.
컴포넌트는 VROrigin / Camera / 손 메시 / 모션컨트롤러뿐이다.
겹침 이벤트는 충돌체가 있어야 발생하므로 영원히 발생하지 않는다.

**해결: 거리 측정으로 바꿨다.**

```text
플레이어 카메라 위치 ─┐
                     ├→ 거리 < 임계값 → 표시
전시대 위치 ─────────┘
```

- 매 프레임(Tick)이 아니라 0.2초 타이머 — 모바일 프레임 비용 절약
- 카메라(머리) 기준이 VR에서 더 자연스럽다

여기서 두 번째 함정: 변수를 나중에 추가했더니 **이미 배치된 액터 3개는 값이 0이었다.**
클래스 기본값을 바꿔도 기존 인스턴스에 전파되지 않는다. `거리 < 0`이라 영원히 거짓이었다.

### 4.3 컨트롤러 레이저가 패널을 통과했다

`WidgetInteractionComponent`가 없어서 안 되는 줄 알았는데, **폰에 이미 양손에 붙어 있었다**
(사거리 500cm). 문제는 위젯 쪽이었다.

레이저는 커스텀 충돌 채널 `3DWidget`으로 추적하는데,
`WidgetComponent`의 기본 프로파일 `UI`는 그 채널을 명시하지 않아 기본값 `Ignore`가 적용된다.
**레이저가 그냥 통과한다.**

템플릿의 `BP_Menu`를 열어보니 답이 있었다.

```text
collisionProfileName : Custom
모든 기본 채널        : Ignore
3DWidget             : Block      ← 이것
```

교훈: **템플릿에 이미 동작하는 예시가 있으면 그것을 열어본다.** 추측보다 빠르다.

### 4.4 Lumen이 켜져 있었다

`DefaultEngine.ini`에 모바일 VR 설정과 PC 전용 설정이 섞여 있었다.

- `r.ForwardShading=True`, `r.MobileHDR=False` → 모바일 VR
- `r.DynamicGlobalIlluminationMethod=1` (Lumen), `r.RayTracing=True` → **PC 전용**

Lumen은 Quest 2에서 동작하지 않는다. 켜둔 채로 조명을 맞추면
**에디터에서 보는 것과 헤드셋에서 보는 것이 달라서** 그 작업이 전부 헛일이 된다.

교훈: 조명·렌더링 작업 전에 **렌더링 경로를 먼저 확정한다.**

### 4.5 에셋을 지울 때 참조를 먼저 본다

프로젝트 용량을 줄이려고 무기 에셋을 지우려 했는데 의존 관계가 얽혀 있었다.

```text
템플릿 레벨 ──▶ BP_Pistol ──▶ SM_Pistol ──▶ 머티리얼 ──▶ 텍스처 4개
```

통째로 지우면 템플릿 레벨이 깨진다. 참조를 역추적해서 안전한 20개만 지웠다.
`M_Weapon`이 Rifle 폴더에 있는데 Pistol 머티리얼이 참조하는 식이라 눈으로는 놓치기 쉬웠다.

## 5. Unreal MCP 사용 경험

UE 5.8에 내장돼 있다(Experimental). 서드파티 플러그인이 필요 없다.

### 되는 것

- 위젯 트리 생성과 프로퍼티 설정
- 블루프린트 에셋·컴포넌트·변수 생성
- **함수·이벤트 그래프를 S-expression DSL로 작성** (영어 에디터 전제)
- 머티리얼 인스턴스 생성과 파라미터 설정
- 레벨 액터 배치, 레벨 복제·전환
- **PIE 실행과 런타임 상태 검사** — 검증에 결정적이었다
- 출력 로그 읽기
- **에디터 메뉴 클릭** — 전용 툴이 없는 기능(라이팅 빌드)을 UI 자동화로 실행

### 안 되는 것

- 커스텀 이벤트 생성 → 함수 그래프로 대체
- 블루프린트 인터페이스 에셋 생성
- 디자이너 캔버스 크기 변경 → SizeBox로 우회
- 에디터 언어 설정 변경
- **패키징·실기 배포·C++ 빌드** → G1 게이트에는 도움이 안 된다

### 실습에서 얻은 사용법

- 프로퍼티 이름을 추측하지 않는다. `list_properties`로 먼저 확인한다.
  틀리면 에러가 정확한 이름을 알려주므로 그걸 읽는 게 빠르다
- 여러 호출은 파이썬 스크립트 하나로 묶는다. 왕복이 크게 줄어든다
- 화면 확인은 사람이 한다. 스크린샷은 실용적이지 않다

## 7. 실기에서 확인해야 하는 것

PC 화면으로는 판정할 수 없는 항목이다. 추정으로 진행하지 않는다.

1. **한글 폰트가 Android 패키징에 포함되는가** — 기본 폰트에 한글이 없고 fallback이 대신 그린다.
   누락되면 헤드셋에서 한글이 전부 네모로 나온다
2. 한글은 굵기(Bold)가 적용되지 않는다 — fallback에 Regular 하나뿐. 크기·색으로만 위계를 준다
3. 컨트롤러로 버튼이 실제로 눌리는가
4. 조명 세기·폰트 크기 — 전부 PC 모니터 기준 추정값
5. 미러링 화면 가독성 (FR-UI-006)
6. Stationary 조명 몇 개까지 감당되는가 (NFR-PERF)
7. **Quest 2 빌드 자체** — G1 게이트. 실패하면 Unity 전환
