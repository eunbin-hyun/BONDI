## 0. 오늘의 요약

어제 세운 전시실에 **실제 복원 유물을 올리고, 복원 전/후를 버튼으로 전환**하는 것까지 동작시켰다.

핵심 수확 네 가지.

1. **Meta Link는 이 노트북에서 원천적으로 불가능하다.** GPU 설정 문제가 아니라 디스플레이 소유 구조 문제였다.

3. **템플릿의 잡기는 겹침이 아니라 스피어 트레이스다.** 이걸 모르고 손대서 두 번 망가뜨렸다.
4. **좌표계·단위·핀 순서에서 세 번 다른 방식으로 틀렸다.** 명세 19.3이 왜 있는지 몸으로 알았다.

## 1. Meta Link 하드웨어 비호환 — 진단 과정

### 1.1 증상

Meta Horizon Link PC 앱에 빨간 배너.

```text
시스템의 하드웨어가 호환되지 않아 Link 기능을 사용할 수 없습니다.
```

### 1.2 이 PC의 구성

| 항목 | 값 |
| --- | --- |
| 기기 | SAMSUNG 960XGL (갤럭시북 계열) |
| CPU | Intel Core Ultra 9 185H (16코어 / 22스레드) |
| dGPU | NVIDIA GeForce RTX 4070 Laptop (8GB) |
| iGPU | **Intel Arc Graphics** |
| RAM | 63.5 GB |

명세 22.1의 기준 PC(RTX 4070 Laptop)와 일치한다. 성능은 문제가 아니었다.

### 1.3 Meta 공식 지원 표를 잘못 읽었다

[요구사항 문서](https://www.meta.com/ko-kr/help/quest/140991407990979/)의 GPU 표는
`GPU 이름 | 지원됨 | 현재 지원되지 않음` 3열 구조인데, **두 열 모두 `X`로 표시**한다.

처음에 RTX 40-series 옆의 `X`를 보고 "미지원"으로 읽었다. DOM을 직접 뜯어 확인한 결과:

```json
["NVIDIA GeForce RTX 40-series", "X", ""]   ← 2번째 칸 = 지원됨
["NVIDIA Titan Z",              "",  "X"]   ← 3번째 칸 = 미지원
```

**RTX 40-series는 지원 대상이다.** 미지원으로 명시된 것은 따로 있었다.

> 현재 **Intel Arc GPU**는 Meta Horizon Link에서 지원되지 않습니다.

즉 배너의 원인은 RTX가 아니라 **내장 Intel Arc**였다.

### 1.4 시도한 것 — 앱별 GPU 지정

Windows `설정 → 시스템 → 디스플레이 → 그래픽`에서 앱을 고성능(NVIDIA)으로 지정.

레지스트리 `HKCU\Software\Microsoft\DirectX\UserGpuPreferences` 에 기록되는 값의 의미를 알게 됐다.

| 값 | 의미 |
| --- | --- |
| `GpuPreference=0` | Windows가 결정 (= 절전 우선 → **iGPU를 잡는다**) |
| `GpuPreference=1` | 절전 (iGPU) |
| `GpuPreference=2` | 고성능 (dGPU) |

처음에 앱을 목록에 **추가만 하고 옵션을 안 바꿔서** `0`으로 남아 있었다.
목록에 넣는 것과 고성능으로 지정하는 것은 별개의 동작이다.

`OculusClient.exe` 와 `OVRServer_x64.exe` 를 `2`로 바꾸고 재부팅했지만 **배너 그대로**.

### 1.5 실패 원인 — 렌더링 GPU와 디스플레이 소유 GPU는 다르다

이게 오늘 가장 중요한 개념 정리다.

| | 앱별 GPU 설정이 바꾸는 것 | Meta가 검사하는 것 |
| --- | --- | --- |
| 대상 | **누가 계산(렌더링)할지** | **누가 화면 출력을 소유했는지** |

`nvidia-smi` 로 확인한 실제 상태:

```text
NVIDIA GeForce RTX 4070 Laptop GPU   display_active: Disabled
Intel Arc Graphics                   2880 x 1800 @ 120Hz
모니터 연결 방식                       Internal (내부 패널 직결)
```

**RTX 4070에는 붙은 화면이 하나도 없다.** 노트북 패널이 Intel Arc에 하드웨어로 직결돼 있고,
MUX 스위치가 없는 기종이라 이 배선을 소프트웨어로 바꿀 수 없다.

Optimus 구조에서는 이렇게 동작한다.

```text
RTX 4070 이 렌더링  →  결과를 Intel Arc 프레임버퍼로 복사  →  Arc 가 패널에 출력
```

Arc는 방해물이 아니라 **출력 담당**이다. 장치 관리자에서 끄면 화면이 꺼질 뿐,
RTX가 그 자리를 대신하지 못한다.

> **결론:** 이 노트북에서 Meta Link(PC VR)는 하드웨어적으로 불가능하다.
> 외부 모니터를 HDMI로 연결하면 RTX가 디스플레이를 갖게 되어 통과할 가능성이 있지만,
> 그 포트도 iGPU 경유일 수 있어 확실하지 않다.

### 1.6 우회 — ALVR + SteamVR

처음에는 Steam Link로 가려 했으나, 공세민이 이미 **Quest 스토어에서 Steam Link가 검색되지 않는다**는
것을 확인해뒀다(`공세민/quest2-alvr-steamvr-setup.md`). 그래서 ALVR로 갔다.

실제로 연결된 경로는 이것이다.

```text
Unreal VR Preview
   ↓ OpenXR
SteamVR (활성 런타임)
   ↓ ALVR 드라이버
ALVR Streamer (PC)  ──Wi-Fi──▶  ALVR 앱 (Quest 2)
```

ALVR은 SteamVR의 **외부 드라이버**로 등록된다. `%LOCALAPPDATA%\openvr\openvrpaths.vrpath` 에서 확인된다.

```json
"external_drivers": [ "C:\\Users\\SSAFY\\Downloads\\alvr_streamer_windows" ]
```

**Meta Horizon Link를 아예 거치지 않으므로 하드웨어 검사도 받지 않는다.**

여기서 어제 잘못 이해한 것을 정정하게 됐다. 어제는 "활성 OpenXR 런타임을 Meta로 바꿔야 한다"고
생각했는데, ALVR·Steam Link 경로에서는 **SteamVR이 활성 런타임이어야 맞다.**
경로에 따라 필요한 런타임이 다르다.

| 경로 | 활성 OpenXR 런타임 |
| --- | --- |
| Meta Link (PC VR) | Meta |
| **ALVR / Steam Link** | **SteamVR** |
| PICO Connect | SteamVR |

ALVR이 이 상황에 맞는 이유가 두 가지 더 있다.

- 공식 요구사항에 **Intel Arc(VPL)를 지원 대상으로 명시**한다 — Meta가 미지원이라 한 그 GPU다
- v20.12부터 대시보드의 **Wired Connection 토글**로 USB 유선 연결을 지원한다 (ADB를 자체 포함)

### 1.7 확인한 대안들

| 방식 | 렌더링 주체 | 이 노트북에서 | 연결 |
| --- | --- | --- | --- |
| Meta Link | PC | ❌ 하드웨어 검사 실패 | 유선/무선 |
| Steam Link | PC | ❌ **Quest 스토어에 없음** (공세민 확인) | 무선만 |
| **ALVR** | PC | ✅ **동작 확인** | 무선 / **유선 지원** |
| APK 내부 빌드 | **헤드셋 자체** | ✅ GPU 무관 | 설치 |

### 1.8 중요 — 이 문제는 PC마다 다르다

내 결론을 팀 전체로 일반화하면 안 된다. 오늘 올라온 팀원 문서가 이를 보여준다.

## 2. VR에서 화면이 사라진 이유 — 가디언 경계

### 2.1 증상 두 가지를 구분해야 했다

처음에는 원인을 잘못 짚었다. 실제로는 **서로 다른 두 문제**였다.

| 증상 | 원인 |
| --- | --- |
| 벽·바닥·천장만 사라지고 전시대는 남음 | `BP_Passthrough` 액터 |
| **전부 사라지고 실제 방이 보임** | **Quest 가디언 경계** |

### 2.2 BP_Passthrough — 태그로 씬을 숨기는 액터

XR 템플릿에 들어 있는, 보이는 몸체가 없는 액터다. 로직만 실행한다.

```text
HidePassthroughActors(Hide):
  "Passthrough" 태그가 붙은 액터를 전부 →  숨기고 + 충돌까지 끔
  (단 "Floor" 태그가 있으면 충돌은 유지)
```

확인해보니 그 태그가 **벽 7개 + 바닥 + 천장 + 하늘** 10개에 붙어 있었다.
템플릿 VR 메뉴(`WBP_Menu`)에서 호출되므로, 이동 중 메뉴 버튼이 눌리면 전시실이 통째로 사라진다.

박물관에 패스스루는 필요 없으므로 레벨에서 액터만 제거했다.
블루프린트 원본은 남겨서 필요하면 다시 놓을 수 있게 했다.

### 2.3 가디언 경계 — 실제 원인

SteamVR이 헤드셋 경계 정보를 PC에 복사해둔다.
`C:\Program Files (x86)\Steam\config\chaperone_info.vrchap`

```json
"play_area": [1.08894444, 1.08894444]
경계 사각형 : 2.18 m x 2.18 m  (중심에서 사방 1.09 m)
꼭짓점 4개, 중심 대칭  →  스테이셔너리 모드
```

전시실 내부는 **10m × 10m**. 면적으로 **21분의 1**이다.
전시대 간격이 2.5m인데 경계가 2.18m니, 옆 전시대로 걸어가려는 순간 이미 경계를 넘는다.

경계를 룸스케일로 다시 그려서 해결했다.

### 2.4 근본 해결은 연속 이동

경계를 넓혀도 **10m 전시실을 실제로 걸어다닐 수는 없다.** 시연장에서도 마찬가지다.

명세가 `FR-VR-004`(컨트롤러 입력으로 연속 이동)를 MUST로 잡은 이유를 실감했다.
제자리에 서서 썸스틱으로 이동하면 경계와 무관해진다.

현재 템플릿 기본은 **텔레포트**이므로 명세와 다르다. 아직 미구현.

## 3. 실제 복원 유물 반입

### 3.1 자료 선별

`Downloads`의 복원 자료에서 전시 가능한 것을 골랐다.
선별 결과는 `Downloads/전시후보_선별/00_선별_결과.md` 에 정리해뒀다.

| 순금 관모 장식 `bon004740` | 금 | 형상+색 | OBJ+텍스처 | 후보 — 전후 대비가 극적 |

### 3.2 GLB가 1000배 크게 들어왔다

```text
임포트된 크기 : 26,809 x 26,810 x 36,911 유닛   (= 268 m 짜리 토기)
실제 크기     :      262 x      383 x      268 mm
```

원인: **GLB가 밀리미터 단위로 저장돼 있는데 glTF 규격은 미터 기준**이라,
임포터가 m→cm 환산으로 ×100을 했다. 결과가 1000배.

스케일 `0.001`로 맞췄다. 다행히 pivot은 바닥(min z = 0)에 있어 명세 19.3을 만족했다.

### 3.3 OBJ는 눕는다 — Y-up vs Z-up

같은 유물의 다른 단계를 OBJ로 넣었더니 옆으로 누웠다.

| | 복원후 (GLB) | 복원전 (OBJ) |
| --- | --- | --- |
| 상하 축 | Z-up ✅ | **Y-up** ❌ |
| pivot | 바닥 (0 ~ 369) | **중앙** (-135 ~ 133) |
| 단위 | mm ×100 | mm 그대로 |
| 필요한 보정 | 스케일 0.001 | **Roll 90 + 스케일 0.1** |

glTF 임포터는 Y-up → Z-up 변환을 해주지만 **OBJ 임포터는 안 해준다.**

> 같은 유물, 같은 사람이 만든 출력물인데 포맷에 따라 보정이 전부 다르다.
> 명세 19.3이 **"①②③이 같은 좌표·같은 pivot·같은 크기여야 한다"** 고 요구하는 이유를 이제 안다.
> AI 직군이 내보낼 때 규약을 통일하지 않으면 VR 쪽에서 유물마다 수동으로 맞춰야 한다.
> 팀에 공유할 안건.

### 3.4 자산 예산 초과

| 항목 | 명세 20장 임시 기준 | 실제 |
| --- | --- | --- |
| 유물 1점 면 수 | ≤ 30,000 | 빗살무늬토기 **391,456** |
| 텍스처 | ≤ 2장, 각 변 ≤ 1024 | `bon004740` 텍스처 82 MB |

## 4. 잡기 시스템 — 템플릿 구조를 먼저 읽어야 했다

이 부분에서 두 번 망가뜨렸다. 둘 다 **구조를 모르고 손댄 결과**였다.

### 4.1 잡기 탐색 방식

`BP_XRPawn::GetGrabComponentNearMotionController` 를 읽고 알게 된 것.

```text
컨트롤러 위치에서 SphereTraceForObjects
  대상 오브젝트 타입 = ObjectTypeQuery4
     ↓
맞은 액터에서 GetComponentsByClass(BP_GrabComponent) 검색
     ↓
가장 가까운 것을 반환
```

**겹침(overlap) 이벤트를 전혀 쓰지 않는다.** 손에는 충돌체가 아예 없다.
그래서 내가 만든 감지 구체(`SphereComponent` + `OverlapAllDynamic`)는 손이 통과해도 무반응이었다.

### 4.2 필요한 충돌 설정

`ObjectTypeQuery4` = `ECC_PhysicsBody`. 작동하는 예제(`BP_Grabbable_SmallCube`)를 확인했다.

| | 작동하는 예제 | 내가 처음 설정한 값 |
| --- | --- | --- |
| 프로필 | `PhysicsActor` | `BlockAllDynamic` ❌ |
| 오브젝트 타입 | `ECC_PhysicsBody` | `ECC_WorldDynamic` ❌ |
| Collision Enabled | `QueryAndPhysics` | 동일 |

### 4.3 실패 1 — Mobility가 Static

첫 시도에서 출력 로그에 이런 메시지가 떴다.

```text
Attaching Artifact_BitsalPot.StaticMeshComponent0 to BP_XRPawn0.MotionControllerLeftGrip
FAILED - object not grabbed
```

탐색은 성공했는데 **부착이 실패**했다. 컴포넌트 `Mobility`가 `Static`이면
런타임에 움직일 수 없어서 컨트롤러에 붙지 못한다. `Movable`로 바꿔 해결.

### 4.4 실패 2 — 충돌을 없애버렸다

회전 보존을 위해 루트에서 메시를 빼면서(3항 참조) **충돌이 함께 사라졌다.**
스피어 트레이스가 맞힐 대상이 없으니 손이 통과했다.

루트에 전용 충돌 구체(`SphereComponent`, 반경 20cm, `PhysicsActor`, 비표시)를 달아 해결.
트레이스는 액터를 맞히기만 하면 되므로, 어느 컴포넌트가 충돌을 갖든 상관없다.

## 5. 복원 전/후 토글 구현

### 5.1 설계 — 액터 숨김에서 메시 교체로

처음에는 두 액터를 만들어 하나를 숨기는 방식으로 했다.
그런데 사용자가 토기를 잡고 돌려놓아도 전환하면 **방향이 초기화**됐다.
두 액터가 별개라 회전이 이어지지 않았다.

**해결: 컴포넌트 역할을 분리했다.**

```text
Artifact_BitsalPot
├── StaticMeshComponent0   (루트, 메시 없음)     ← 사용자가 잡고 돌린 회전이 쌓이는 곳
│   ├── GrabComponent                            ← 루트를 컨트롤러에 부착
│   ├── ArtifactMesh   (태그 "ArtifactMesh")      ← 메시 + 좌표계 보정만 담당
│   └── GrabCollision  (구체 20cm, 비표시)        ← 트레이스가 맞히는 대상
└──
```

전환 로직은 **자식(`ArtifactMesh`)만 건드린다.** 루트는 손대지 않으므로
사용자가 돌려놓은 방향이 그대로 유지된다.

`BP_GrabComponent::TryGrab` 이 **AttachParent를 컨트롤러에 붙인다**는 점이 핵심이다.
GrabComponent를 루트의 자식으로 두면 루트가 붙고, 메시의 상대 보정은 보존된다.

| | `ArtifactMesh` 에 적용 | 루트 |
| --- | --- | --- |
| 손상 | `Pot_Damaged`, 0.1배, Roll 90 | **변경 없음** |
| 복원 | `Pot_3_Pristine`, 0.001배, Roll 0 | **변경 없음** |

### 5.2 MakeRotator 핀 순서 — (Roll, Pitch, Yaw)

전환하면 토기가 누워서 나왔다. 원인은 인자 순서였다.

```text
MakeRotator 핀 순서 : (Roll, Pitch, Yaw)
내가 넣은 값        : (0, 0, 90)   →  Yaw 90    ❌ 누운 채 방향만 틀어짐
필요했던 값         : (90, 0, 0)   →  Roll 90   ✅
```

Rotator를 `(Pitch, Yaw, Roll)` 순으로 착각했다. 실제 노드 핀을 조회해서 확인하는 습관이 필요하다.

### 5.3 SetStaticMesh는 머티리얼 오버라이드를 초기화한다

전환하면 재질이 날아가 흰색으로 돌아왔다.

**`SetStaticMesh`를 호출하면 컴포넌트의 `overrideMaterials`가 초기화된다.**
메시가 바뀌면 이전 메시 기준의 오버라이드가 무효가 되니 당연한 동작이다.

처음에는 전환 직후 `SetMaterial`을 호출하려 했지만 타입 연결이 계속 막혔다
(`ActorComponent` → `PrimitiveComponent`, 캐스트를 넣어도 동일).

**해결: 메시 에셋 자체에 재질을 지정했다.**

```text
Pot_Damaged      슬롯 "defaultMat"  →  MI_Artifact_Clay_Damaged  (풍화 회갈색)
Pot_3_Pristine   슬롯 "토기_신제"    →  MI_Artifact_Clay          (태토색)
```

메시를 바꾸면 그 메시에 딸린 재질이 자동으로 따라온다.
오버라이드가 없으니 초기화될 것도 없다. 결과적으로 로직도 단순해졌다.

### 5.4 푸시 버튼 — 그립 없이 손만 대면

처음에는 "유물을 잡고 한 바퀴 돌리면 전환"으로 만들었는데, 누적 회전 방식은
손이 떨리기만 해도 값이 쌓이고 언제 넘는지 예측이 안 돼서 버렸다.
명세 `FR-UI-003`도 버튼을 MUST로 잡고 있다.

겹침 이벤트가 안 되므로(4.1 참조) **거리 계산 방식**으로 만들었다.

```text
EventTick:
  쿨다운 > 0 이면 감소만 하고 종료
  아니면:
    폰의 MotionControllerComponent 전부 순회
    버튼과의 거리 < 16cm  →  ToggleStage 실행 + 쿨다운 0.8초
```

### 5.5 왼손만 안 됐던 이유 — 컴포넌트가 4개다

오른손은 되는데 왼손은 안 됐다. 폰의 모션컨트롤러 컴포넌트를 세어보니 **4개**였다.

```text
MotionControllerRightGrip   ┐ 오른손
MotionControllerRightAim    ┘
MotionControllerLeftGrip    ┐ 왼손
MotionControllerLeftAim     ┘
```

`Grip`과 `Aim`은 거의 같은 위치에 있다. 그런데 쿨다운 검사를 **루프 밖**에 둬서,
한 손이 다가가면 그 손의 두 컴포넌트가 연달아 조건을 만족해 **한 프레임에 두 번 전환**됐다.

```text
루프 진입 (쿨다운 0 확인 — 한 번만)
  LeftGrip  → 16cm 안 → 전환 (손상 → 복원)
  LeftAim   → 16cm 안 → 전환 (복원 → 손상)   ← 원위치
```

쿨다운 검사를 **루프 안**으로 옮겨서 해결했다.
첫 전환에서 쿨다운이 걸리면 나머지 컴포넌트는 건너뛴다.

> 배열을 순회할 때 상태를 바꾸는 코드는 **매 반복마다 조건을 다시 확인**해야 한다.

## 6. 정보 패널 — 관측과 추정의 구분

### 6.1 상태별로 패널을 따로 뒀다

패널 하나에서 글자를 바꾸는 대신 상태별 위젯을 만들고 태그로 함께 전환시켰다.
로직이 단순해지고, 상태별로 다른 문구를 넣기 쉽다.

### 6.2 손상 상태에는 AI 가설 문구를 넣지 않는다

처음에 두 상태 모두 "AI 기반 복원 가설입니다"를 넣었는데, 이건 틀린 표시다.

명세 3.1의 분류를 다시 읽고 정리했다.

| 분류 | 이 프로젝트에서 | 우리 토기의 경우 |
| --- | --- | --- |
| `observed` | 입력 사진, 실측 3D 스캔 | **손상 상태 = 실측 스캔** |
| `ai_inferred` | 생성된 3D, 채운 결손부 | 복원 상태 = AI 복원 결과 |

**손상 상태는 실제 관측물이므로 AI 추정이 아니다.** 문구를 빼는 것이 맞다.

| | 복원 전 패널 | 복원 후 패널 |
| --- | --- | --- |
| 근거 | **실측 3D 스캔 (관측)** | AI 복원 결과 (추정) |
| 면책 문구 | **없음** | "AI 기반 복원 가설입니다" |

> 명세 3장은 ①손상 상태를 "생성 모델이 만든 형상"으로 전제하는데,
> 우리는 **실측 스캔**을 갖고 있어서 ①이 진짜 `observed`다.
> 사진 기반 생성보다 근거가 강한 구성이므로 발표에서 내세울 수 있다.

### 6.3 위젯 컴포넌트는 에디터 뷰포트에서 렌더가 불안정하다

패널이 에디터에서 빈 사각형으로만 보여서 한참 헤맸다.
설정값을 전부 읽어봐도 정상이었고, **VR에서는 완벽하게 렌더됐다.**

에디터 뷰포트 렌더링은 신뢰하지 말고 실기에서 확인해야 한다.

### 6.4 `bHidden`은 에디터를 숨기지 않는다

스크린샷을 찍으려는데 두 상태의 패널이 겹쳐 나왔다.
`bHidden`(= Actor Hidden In Game)은 **게임 실행 중에만** 적용된다.

에디터 스크린샷용으로는 액터를 잠시 다른 위치로 옮겼다가 되돌리는 방식을 썼다.

### 메모리 사고

작업 중 언리얼이 `Memory Pressure: Critical` 경고를 띄웠다. 가용 메모리 **0.35GB**.

원인은 응답 없이 중단시킨 자동화 스크립트가 **좀비 프로세스로 남아 43.6GB를 점유**한 것.
작업만 중단해도 프로세스는 살아남을 수 있다. 종료 후 44GB를 회수했다.

> 장시간 작업 중에는 메모리 상태를 주기적으로 확인해야 한다.
> 언리얼이 죽으면 저장하지 않은 작업이 날아간다.

## 9. 팀에 공유할 안건

1. **PC VR 연결 방식 재결정** — **PC마다 장애가 다르다.**
   현은빈 PC는 Intel Arc 때문에 Link 앱 자체가 거부되고, 김소영 PC는 SSAFY Wi-Fi discovery에서 막혔다.
   현재 확인된 조합은 **ALVR + SteamVR**(현은빈)과 **Air Link + 핫스팟**(김소영)이다.
   명세 22.2와 `U-08`을 갱신하면서 **시연에 쓸 PC와 연결 방식을 함께 확정**해야 한다.
   무선은 교육기관 망에서 불안정하므로 ALVR 유선을 검토할 가치가 있다.

2. **좌표계·단위 규약 통일** — 같은 유물의 GLB와 OBJ가 상하 축·pivot·단위가 전부 달랐다.
   AI 직군이 내보낼 때 규약을 정하지 않으면 VR 쪽에서 유물마다 수동 보정이 필요하다.
   명세 19.3을 실제 값으로 채워야 한다.

3. **자산 예산** — 빗살무늬토기가 391,456면으로 임시 기준의 13배다.
   `U-07` 실기 측정 후 감면 목표를 정해야 한다.

4. **한글 폰트 라이선스** — 현재 맑은 고딕(Windows 번들)을 임시로 쓰고 있다.
   APK 임베드 시 재배포 제약이 있을 수 있어 OFL 계열로 교체해야 한다.
   12.8MB라 서브셋도 필요하다. FE 담당 영역.

5. **손상 상태의 provenance** — 우리 토기는 실측 스캔이 있어 ①단계가 진짜 `observed`다.
   명세 3장의 전제(①도 생성 모델 결과)와 다르므로, 더 강한 구성으로 문구를 다듬을 여지가 있다.
