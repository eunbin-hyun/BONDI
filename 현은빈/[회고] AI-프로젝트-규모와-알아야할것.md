## 1. 이 문서에서 "비용"은 무엇을 뜻하나

한 가지가 아니라 네 가지가 섞여 있어서 따로 적는다.

| 비용 | 우리 프로젝트에서 | 금액 |
| --- | --- | --- |
| **① 돈 (GPU 임대·API)** | Colab · RunPod · 유료 API 를 쓴 기록이 없다. 전부 노트북에서 돌렸다 | **0원** |
| **② 이미 가진 장비** | 노트북은 원래 있던 것이라 이번 프로젝트의 추가 지출이 아니다. 새로 샀다면 이게 제일 큰 항목이다 | 추가 0원 |
| **③ 시간 (GPU 점유)** | 학습·생성이 도는 동안 노트북을 다른 일에 못 쓴다. 아래 §2 가 이 항목이다 | 약 4시간 + 생성 |
| **④ 사람 시간** | 실험 설계, 로그 읽기, 설치 오류 해결. 가장 크지만 로그에는 안 남는다 | 기록 없음 |

그래서 "얼마 들었나"의 답은 **현금은 0원, 대신 GPU 시간과 사람 시간으로 갚았다**이다.
8GB 에 안 들어가는 모델(SAM 3D 등)은 이 구조를 깨고 ① 돈이 들어가야 해서 접었다.
클라우드로 갈 때의 시간당 단가는 조사하지 않았다. 필요해지면 그때 따로 조사한다.

### 2.4 VRAM 과 모델 크기 — 8GB 로 무엇을 돌릴 수 있나

**VRAM 은 GPU 전용 메모리다.** 모델 가중치와 계산 중간값(활성값)을 전부 여기에 올려야 하고, 모자라면 OOM 으로 멈춘다.
컴퓨터 RAM 과 별개이고, GPU 가 바로 접근하는 것은 VRAM 뿐이다.

> **가중치 용량 = 파라미터 수 × 정밀도(바이트)**, 여기에 활성값이 더 붙는다.
> 실제로는 가중치의 1.2~2배를 잡아야 안전하고, 입력이 크면 더 는다.

| 정밀도 | 파라미터 1개 | 1B(10억)당 가중치 |
| --- | --- | --- |
| fp32 | 4바이트 | 4GB |
| fp16 / bf16 | 2바이트 | 2GB |
| int8 | 1바이트 | 1GB |
| 4비트 | 0.5바이트 | 0.5GB |

**8GB (실제 가용 약 7GB) 에서 한 번에 올릴 수 있는 크기** — 위 공식에서 나온 대략의 상한이다.

| 정밀도 | 가중치만 | 현실적 상한 |
| --- | --- | --- |
| fp16 / bf16 | 약 3.5B | 약 2~3B |
| int8 | 약 7B | 약 4~5B |
| 4비트 | 약 14B | 약 7~8B |

노트북에서 "7~8B 언어모델을 돌린다"는 말은 대부분 4비트 양자화를 쓴 경우다.
한 번에 올리는 양이 8GB 를 넘지 않게 순서대로 올렸다 내리면 이보다 큰 모델도 돌 수 있다 — TRELLIS.2 가 이 경우다.

| 모델 | 크기 | 8GB 에서 |
| --- | --- | --- |
| U-Net · AdaPoinTr | 수백만~수천만 | 학습까지 여유롭게 가능 |
| TRELLIS.2 | 4B (DiT 1.3B × 3 + 인코더·디코더) | 통째로는 어렵고 `low_vram` 으로 가능. DiT 하나가 약 2.4GB 라 한 번에 하나만 올림 |
| SAM 3D Objects | 공식 32GB 요구 | 불가 |

#### 말할 때 — "4B 라서"가 아니라 "4B × 정밀도"

모델 크기는 **파라미터 수 × 숫자 하나의 크기**다. 4B 만 말해도, fp16 만 말해도 반쪽이다.
(같은 4B 라도 4비트면 약 2GB, 16비트면 약 8GB. 파라미터가 적으면 16비트여도 작다 — AdaPoinTr 130MB.)

> TRELLIS.2 는 파라미터가 4B 이고 bf16/fp16 원본이라 가중치가 약 8GB(파일은 해상도별 버전을 포함해 약 16GB)다.
> 노트북의 가용 VRAM 은 약 7GB 라서 한 번에 다 올릴 수 없었다.
> 그래서 `low_vram` 으로 모델을 하나씩 올렸다 내리는 방식으로 돌렸다. 양자화로 줄이지는 않았다.

주의: DiT 5개 합 약 12GB 는 512·1024 해상도별 버전이 섞인 숫자라, 한 번 생성에 전부 쓰는지는
파이프라인 코드로 확인하지 않았다. "12GB 를 한꺼번에 올려야 했다"고는 쓰지 않는다.

#### 같은 "4B" 인데 올라마 LLM 보다 무거운 이유

| | 올라마의 LLM 4B | TRELLIS.2 4B |
| --- | --- | --- |
| 정밀도 | 보통 **4비트 양자화** → 약 2.5GB | **bf16/fp16 원본** → 파일 약 16GB (512·1024 두 해상도와 인코더 포함) |
| 4B 의 뜻 | 모델 하나 | DiT 세 개 + 인코더·디코더를 **합친 숫자** |
| 계산 방식 | 토큰을 한 개씩 뽑는다. 활성값이 작다 | 확산 모델이라 **12스텝을 반복**하고 단계마다 여러 번 계산한다 (guidance 로 더 늘어남) |
| 입력 | 글자 수에 비례하나 작다 | 복셀 수에 비례한다. 수십~수백만 개가 되면 활성값이 가중치보다 커진다 |
| 걸리는 시간 | 답 한 번에 수 초 | 유물 한 점 약 9분 (샘플링만 약 3분) |

즉 **가볍다/무겁다는 파라미터 수가 아니라 정밀도, 계산량, 입력 크기가 함께 정한다.**
같은 4B 라도 올라마 쪽은 줄여 놓은 4비트라 2.5GB 에 들어가고, TRELLIS 는 원본 16비트에 반복 계산까지 있어서
`low_vram` 이라는 우회가 필요했다. 이 값들은 일반 공식과 로그에서 나온 대략값이라, 정확한 것은 `nvidia-smi` 로 재야 한다.

## 3. 알아야 할 것 — 실제로 겪은 것 위주

### 3.1 모델을 고르기 전에

1. **VRAM 부터 본다.** SAM 3D 는 8GB 성공 보고가 없고 12GB 에서도 1회 1시간이었다. 시간을 더 쓰지 않고 접었다.
2. **"요구 VRAM"은 한 숫자가 아니다.** 입력의 복셀 수 같은 활성값이 지배하는 모델은 공식 숫자 아래에서도 되고 위에서도 터진다. 같은 16GB 에서 성공과 OOM 이 갈린 사례가 있었다.
3. **fp16 은 8GB 를 만드는 수단이다.** "16GB 요구"는 fp32 기준이었다. 거꾸로 이해하고 포기할 뻔했다.
4. **README 와 이슈 스레드를 이름보다 믿는다.** "8GB 지원" 포크의 README 가 24GB 를 요구한 적이 있다. GPU 별 결과와 우회책은 이슈에 다 있었다.
5. **OOM 메시지로 원인을 단정하지 않는다.** 8GB 카드의 OOM 보고 일부는 VRAM 이 아니라 빌드 버그였다 (flex_gemm 저VRAM 경로도 같은 종류).

### 3.2 돌리는 동안

6. **같은 GPU 를 쓰는 것을 끈다.** Quest Link · Unreal · GPU 가속 브라우저가 VRAM 을 0.5~1GB 잡는다. 실제 가용은 약 7GB.
7. **조정 손잡이는 해상도다.** OOM 이 나면 512 로 내리는 것이 유일한 조정이었다. 처음엔 512 로 성공부터 확인하고 올린다.
8. **다중 이미지 입력은 8GB 에서 OOM.** 1장씩만.
9. **로그를 남긴다.** 이번에 가장 크게 막힌 곳. 학습 스크립트가 옮겨지자 배치·학습률을 알 수 없게 됐다. 실험마다 아래 한 줄은 남긴다.

   > `GPU · 배치 · lr · 에폭 · 에폭당 시간 · VRAM 피크 · 총 시간 · 비용`

### 3.3 결과를 해석할 때

10. **모델을 바꾸기 전에 내가 무엇을 보여줬는지 본다.** AdaPoinTr 는 학습 데이터의 결손 깊이 분포(평균 0.153 → 대상 0.4~0.5)를 맞췄더니 0.179 → 0.913 이 됐다. 구조 변경보다 컸다.
11. **체크포인트 고르는 지표도 실험 대상이다.** val CD 최저(ep8)와 순증 최고(ep7)는 다른 에폭이었다.
12. **내 설명이 틀릴 수 있다.** SLAT 조각남을 "정점이 안 만나서"로 설명했다가 측정으로 반증했다. 설명은 측정으로 검증한다.
13. **반증도 결과다.** SLAT 주입(v1~v11)과 학습 기반 완성 경로는 접었고, 접은 근거가 측정으로 남아 있어 보류 이유를 말할 수 있다.

### 3.4 설계

14. **AI 가 꼭 필요한지부터 따진다.** 형상 복원은 회전대칭 가정과 수학으로 풀고, AI 는 사진 → 손상 3D 와 재질에만 썼다. 그 덕에 관측값과 추정값을 노드로 나눠 `NFR-ETH-003` 을 지킨다.
15. **같은 목적을 더 싸게 하는 길이 있으면 그쪽이 먼저다.** 에이전트에게 시킨 Blender 복원은 37분에 끝났다.
