# 2026-09-04 학습 정리 — SAM 3D Objects는 8GB 노트북에서 왜 안 되는가

- 작성자: 현은빈
- 학습 주제: Meta SAM 3D Objects의 단일 이미지 → 3D 생성 요구사항 조사, 8GB VRAM에서의 실행 가능성 판단, 대안 경로 선정
- 기준 PC: SAMSUNG 960XGL · RTX 4070 Laptop (8GB) · RAM 64GB · Windows 11
- 결론: **로컬 실행 불가.** 같은 계열의 TRELLIS.2로 경로를 바꿨다 → [세팅](%5BAI%5D%20trellis2-%EC%84%A4%EC%B9%98%EC%99%80-%EC%84%B8%ED%8C%85.md) · [모델 구조](%5BAI%5D%20trellis2-%EB%AA%A8%EB%8D%B8-%EA%B5%AC%EC%A1%B0.md)

## 0. 오늘의 요약

전시실에 올릴 복원 유물 3D를 사진 한 장에서 뽑을 수 있는지, Meta가 2025년 11월에 낸 [SAM 3D Objects](https://ai.meta.com/research/sam3d/)부터 확인했다. 결과는 이 노트북에서는 안 된다는 것이었고, 조사 과정에서 얻은 것이 더 컸다.

핵심 수확 세 가지.

1. **공식 요구 VRAM 32GB는 과장이 아니었다.** 12GB에서 성공한 사용자도 데모 한 번에 1시간이 걸렸다. 8GB 성공 사례는 없다.
2. **메모리가 터지는 지점은 모델 크기가 아니라 1단계 복셀 수다.** 이 구조는 TRELLIS 계열 전체에 공통이라, 이후 TRELLIS.2를 다룰 때 그대로 적용됐다.
3. **"8GB 지원"이라는 이름을 단 포크가 있어도 README를 읽어야 한다.** 이름과 실제 요구사항이 정반대인 경우가 있었다.

---

## 1. SAM 3D Objects가 무엇인가

Segment Anything 계열의 3D 확장이다. 사진 한 장과 물체 마스크를 넣으면 그 물체의 3D를 만든다. 출력은 가우시안 스플랫(PLY)과 메시(GLB).

구조는 TRELLIS v1과 같은 뼈대다.

```text
희소 구조 생성 (어느 복셀이 채워졌나) → SLAT 생성 (복셀별 잠재값) → 디코딩 (가우시안 / 메시)
```

TRELLIS와 다른 점은 **포인트맵 단계**가 붙어 있다는 것이다. 물체를 만들 뿐 아니라 사진 속 장면의 카메라 좌표계에 맞게 배치한다. 그래서 한 장면에서 여러 물체를 뽑아 원래 자리에 놓는 용도에 강하다. 우리 용도(유물 하나를 뽑아 전시실에 놓기)에는 이 정렬이 필요 없다.

라이선스는 자체 SAM License다. 체크포인트는 Hugging Face에서 접근 승인 신청 후 받는다.

## 2. 공식 요구사항

[setup.md](https://github.com/facebookresearch/sam-3d-objects/blob/main/doc/setup.md) 기준.

| 항목 | 요구 |
| --- | --- |
| OS | Linux 64비트 전용 |
| GPU | NVIDIA, **VRAM 32GB 이상** |
| CUDA / PyTorch | 12.1 / 2.5.1 |
| 의존성 | PyTorch3D, Kaolin, Hydra (패치 필요) |

Windows 네이티브 빌드는 [이슈 #19](https://github.com/facebookresearch/sam-3d-objects/issues/19)가 열린 채로 있다. 실제 Windows 사용자들은 WSL로 돌렸다.

메인테이너가 [이슈 #6](https://github.com/facebookresearch/sam-3d-objects/issues/6)에 남긴 답.

> The smallest GPU we've been able to run the model reliably is a V100, which is about 32 Gb of VRAM.

## 3. 사용자 보고 — GPU별 결과

이슈를 훑어 실제 보고를 모았다.

| GPU | VRAM | 결과 | 출처 |
| --- | --- | --- | --- |
| RTX 4080 | 16GB | 한 명은 성공 (일부 단계 느림), 다른 한 명은 OOM | [이슈 #30](https://github.com/facebookresearch/sam-3d-objects/issues/30) |
| RTX 5080Ti (WSL) | 12GB | 성공, **데모 1회 약 1시간** | 이슈 #30 |
| RTX 4090 | 24GB | 메시 디코딩을 건너뛰면 성공 | 이슈 #6 |
| 20GB급 | 20GB | OOM | 이슈 #6 |
| RTX 3090 | 24GB | OOM | [이슈 #129](https://github.com/facebookresearch/sam-3d-objects/issues/129) |
| 8GB | 8GB | **보고 없음** | — |

같은 16GB에서 성공과 실패가 갈리고, 24GB에서도 OOM이 난다. 즉 **VRAM 크기만으로 되고 안 되고가 결정되지 않는다.** 이유는 다음 절에 있다.

## 4. 메모리가 어디서 터지는가

[이슈 #6](https://github.com/facebookresearch/sam-3d-objects/issues/6)에서 메인테이너가 설명한 것을 요약하면 이렇다.

- 메모리 사용량은 **1단계 희소 구조가 내는 복셀 수**에 비례한다.
- 복셀이 수백~수천 개면 문제없다. **1만 개를 넘으면** "Decoding sparse latent" 단계에서 OOM이 난다.
- 복셀 수는 입력 사진에 따라 다르다. 배경이 남아 있거나 물체가 복잡하면 늘어난다.

그래서 같은 GPU에서 어떤 사진은 되고 어떤 사진은 안 된다. 16GB에서 결과가 갈린 이유가 이것이다.

제시된 우회책 둘.

```python
# demo.py — 메시 디코딩을 건너뛰고 가우시안만 뽑는다
output = inference._pipeline.run(
    inference.merge_mask_to_rgba(image, mask),
    None,
    seed=10,
    decode_formats=["gaussian"],   # 기본은 ["gaussian", "mesh"]
)
```

```yaml
# checkpoints/.../pipeline.yaml — 1단계 복셀을 다운샘플한다
downsample_ss_dist: 2   # 또는 4. 메인테이너: "품질 저하 있고 결과 보장 안 함"
```

둘 다 24GB 사용자가 성공한 우회책이다. `downsample_ss_dist: 8`까지 올리고도 24GB에서 실패한 보고도 같은 스레드에 있다.

## 5. 8GB에서의 판단

- 8GB 성공 보고가 없다.
- 12GB에서 1시간이 걸렸다. 8GB는 성공해도 실용성이 없다.
- Windows 오버헤드로 실제 가용 VRAM은 7GB 정도다. Quest Link 드라이버(Meta Virtual Monitor)가 항상 점유한다.
- NVIDIA Windows 드라이버의 시스템 RAM 폴백으로 크래시 대신 느려지는 쪽으로 빠질 수는 있지만, 이미 12GB에서 1시간인 작업이 더 느려지는 것이다.

**결론: 로컬 실행 불가.** 시간을 더 쓰지 않고 대안으로 넘어갔다.

## 6. 확인한 대안

| 경로 | 판단 |
| --- | --- |
| **Segment Anything Playground** (aidemos.meta.com) | 브라우저에서 사진 업로드 → 결과 확인. 설치 없이 품질을 보는 데는 가장 빠르다 |
| 클라우드 GPU (Colab A100 40GB, RunPod) | 공식 저장소 그대로 실행 가능. 체크포인트 접근 승인 필요 |
| [ComfyUI-SAM3DObjects-Low-Ram](https://github.com/DDS-3DPrintman/ComfyUI-SAM3DObjects-Low-Ram) | 저장소 이름은 "Low VRAM (8GB) RTX 2060"인데 **README는 최소 24GB, 권장 32GB**. 이름만 믿으면 안 된다 |
| [Fast-SAM3D](https://arxiv.org/abs/2602.05293) | 속도 2.67배 개선. 메모리는 약 19GB → 18GB로 거의 그대로. 8GB 해법이 아니다 |
| **TRELLIS / TRELLIS.2 (Microsoft)** | 같은 뼈대, 장면 정렬 없음. Windows 8GB용 포크가 있다 → **이쪽으로 전환** |

TRELLIS 계열로 옮긴 이후는 [trellis2-2d-to-3d-setting.md](%5BAI%5D%20trellis2-%EC%84%A4%EC%B9%98%EC%99%80-%EC%84%B8%ED%8C%85.md)와 [trellis2-model-architecture.md](%5BAI%5D%20trellis2-%EB%AA%A8%EB%8D%B8-%EA%B5%AC%EC%A1%B0.md)에 정리했다.

## 7. 오늘 배운 것

- **"요구 VRAM"은 한 숫자가 아니다.** 입력에 따라 변하는 활성값이 지배하는 모델은 공식 숫자 아래에서도 되고, 위에서도 터진다. 어느 단계에서 무엇에 비례해 커지는지를 알아야 판단할 수 있다.
- **이슈 스레드가 README보다 정확하다.** 공식 문서는 32GB 한 줄이지만, 이슈에는 GPU별 결과와 우회책과 그 한계가 다 있었다.
- **이름과 문서가 다를 때는 문서를 믿는다.** "8GB" 포크의 README가 24GB라고 하면 24GB다.
