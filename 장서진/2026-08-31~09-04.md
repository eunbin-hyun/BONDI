## 2. VR-PC 스트리밍 경로 정리 (9/2~9/3)

9/2에 미러링과 Air Link(Meta Link) 두 방법을 확인했고, 9/3에 Study 브랜치 pull 후 팀 문서 4건(`quest2-alvr-steamvr-setup`, `2026-09-02`, `VR환경세팅-스트리밍용`, `ssafy-wifi-airlink-분석`)을 읽어 전체 경로를 정리.

- 9/2 확인한 두 방법의 위치: **미러링(웹 캐스팅)은 헤드셋→PC 방향**이라 VR Preview 대체가 안 되는 확인 수단. **Air Link는 Meta Horizon Link의 기능**으로 PC→헤드셋이며, Horizon Link가 안 뜨는 PC에서는 함께 못 쓴다
- 구조: `언리얼 VR Preview → OpenXR → SteamVR(활성 런타임) → ALVR 드라이버 → ALVR Streamer(PC) ──Wi-Fi──▶ ALVR 앱(Quest 2)`. **PC GPU가 렌더링**, 헤드셋은 표시·트래킹만
- 왜 ALVR인가: Meta Horizon Link(USB/Air Link)는 팀 PC에서 호환성 오류(Intel Arc + RTX 하이브리드 추정), Steam Link는 Quest 스토어 미노출 → ALVR + SteamVR로 우회. 9/2 연결·SteamVR 홈까지 확인됨, 언리얼 VR Preview는 미검증
- 네트워크: PC 유선·Quest 5GHz. **SSAFY Wi-Fi는 같은 서브넷이어도 mDNS/multicast discovery가 막혀 PC 검색 불가**(Wireshark로 확인됨) → 교육장은 노트북 핫스팟
- 한계: 스트리밍 프리뷰 성능은 PC GPU 성능이라 **성능 판정은 APK로만**. 웹 캐스팅은 방향이 반대(헤드셋→PC)라 확인 수단
- AI 직군 관점: ①②③ 산출물을 UE5에 넣어 눈으로 검수하는 데는 APK 빌드 없이 스트리밍 프리뷰로 충분. OpenXR 런타임은 SteamVR 하나로 통일(PICO 4도 동일)

## 3. 2D→3D 생성 모델 조사 (9/3)

- 명세 재확인: 2D→3D는 ① 손상 상태 생성 한 단계만 담당. "두 가지 방법"은 ② 복원 모델 vs ③ MCP 복원. **②는 후보 모델조차 없는 빈 칸**(D-18은 ①, D-19는 ③)
- D-18 후보(TripoSR 안전판 + Hunyuan3D 2.x 도전) 및 대안을 공식 저장소 기준으로 확인

| 모델 | VRAM | 라이선스 | 8GB Windows 판단 |
| --- | --- | --- | --- |
| TripoSR | 6GB | MIT | 유지 |
| Hunyuan3D 2.0 / 2.1 | 형상 6GB, 텍스처 16GB / 29GB | Hunyuan Community — **대한민국 제외**(Territory 조항, 출력물 사용·배포까지) | 도전 후보 재검토 필요 |
| TRELLIS | 16GB | MIT(서브모듈 별도) | Windows 미지원, 제외 사유 타당 |
| Stable Fast 3D | 6GB | Stability Community | UV 메시 + PBR. 실측 대상 |
| SPAR3D | 10.5GB, 저VRAM 약 7GB | Stability Community | 뒷면 개선 목표. 실측 대상 |
| TripoSG | 8GB+ | MIT | 형상만, 텍스처 없음 |
| InstantMesh | 10GB+ 추정 | Zero123++ 가중치 CC BY-NC | 비추천 |

- **Hunyuan3D 라이선스가 한국을 명시적으로 제외한다는 점은 D-18에 없다.** 팀 공유 필요
- "손상 3D 스캔이 있으면 그걸 정답지로 ①을 학습시킬 수 있나?" → 추천 모델 전부 추론 코드만 공개(학습 코드 없음), 수백 쌍 필요, 스캔이 있는 유물은 스캔 자체가 ①이라 순환 → **스캔은 학습이 아니라 평가(벤치마크) 정답지**로 쓴다. G3 게이트를 "GLB가 나온다"에서 수치 기준으로 올릴 수 있다

## 4. TripoSR vs 실측 스캔 정량 비교 (9/3)

- 입력 `ai/2d-to-3d/test-images/comb-patterned pottery1.jpg`(빗살무늬토기, 388×515) / 정답지 국립박물관 스캔 `ssu022891`(OBJ·PLY·STL, 높이 383mm, 저장소 밖 보관). **사진과 동일 개체인지는 미확인** — 개체 차이가 오차에 섞일 수 있음
- 환경: CUDA Toolkit 없음 → `torchmcubes` 빌드 실패, scikit-image `marching_cubes`(CPU)로 패치. 추론 6.1s, 배경 제거 포함 약 104s. 텍스처 베이크는 헤드리스 셸에서 WGL 컨텍스트 불가 → 정점색만
- 평가 도구 `compare.py` 작성: 표면 20만점 샘플 → 24개 축 초기값 유사변환 ICP → GT 좌표계(mm)에서 Chamfer / F-score(bbox 대각선 1·2·5%) / Hausdorff. **배율은 bbox 추정치 ±20%로 제한** — 자유 배율은 납작한 메시가 GT 일부에 축소·밀착하는 퇴화 해를 냄
- 결과: **Chamfer 10.1mm**, 정확도/완전성 중앙값 5.0/7.2mm, **F@10.7mm 0.71**, Hausdorff 113mm. GT PLY vs OBJ 노이즈 바닥 1.06mm(측정 방법 오차는 결과의 1/10 이하)
- 소견: 외벽 실루엣은 5mm 안팎으로 맞음(높이/폭 비율 일치). **입구가 막힘**(z≈325mm 접시형 뚜껑, Hausdorff 원인) · **속이 찬 덩어리**(GT는 벽 15~20mm 이중 표면) · 첨저가 폭 50mm 평바닥 · 뒷면 19° 기울어짐 · 크기 정보 없음(1 unit = 364mm)
- 같은 날 발표 준비 병행

## 5. 대칭 규칙 후처리 실험 (9/4)

"완전대칭 규칙을 넣어도 뭉개지나?" — TripoSR은 규칙 입력 자리가 없으므로 후처리로 검증(`symmetry_test.py`)

| 모델 | Chamfer | F@10.7mm | 최대 오차 |
| --- | --- | --- | --- |
| A. TripoSR 원본 | 10.1mm | 0.71 | 113mm |
| B. 앞면 실루엣 회전, 속 찬 덩어리 | 11.4mm | 0.60 | 119mm |
| C. B + 입구 개방 + 벽 두께 15mm | **5.1mm** | **0.88** | 25mm |
| D. GT 자체를 완전대칭화 | 3.6mm | 1.00 | 12mm |

- **대칭만 걸면 나빠진다.** 큰 오차(막힌 입구·속 찬 내부·평바닥)가 앞뒤 대칭인 오류라서. 뒷면 형상 오차는 앞면과 비슷(평균 12.4 vs 10.6mm) — 턴테이블에서 뭉개져 보이는 건 텍스처
- **대칭 + 그릇 구조 규칙(C)은 학습 없이 오차 절반.** 실물 비대칭 바닥 3.6mm(높이의 1%) 아래로는 어떤 대칭 모델도 못 간다
- Blender Screw 모디파이어 하나로 구현 가능 → **③ MCP 복원의 첫 작업 항목 후보.** 회전대칭 토기 한정, 벽 두께는 검수자 파라미터, 뒷면 실제 파손은 지워지므로 `ai_inferred` 표시 필수

## 6. SF3D·SPAR3D 실행과 3모델 비교 (9/4)

- Hugging Face 게이트 저장소 2건 라이선스 동의(Stability AI Community, "Powered by Stability AI" 표기 의무 → manifest·발표 자료 반영)
- 빌드: C++ 확장(`uv_unwrapper`, `texture_baker`)은 **VS 2026 개발자 환경**(`vcvarsall.bat x64`, `DISTUTILS_USE_SDK=1`, `USE_CUDA=0`, `--no-build-isolation`)에서만 컴파일. CPU 빌드 `texture_baker`가 CUDA 텐서를 못 받아 `baker.py` 패치. SPAR3D는 `transparent_background`의 flet import, `run.py`의 `reduction_count_type` 버그 추가 패치. 가중치 SF3D 4.0GB, SPAR3D 7.3GB(+AlphaCLIP 891MB)

| 모델 | Chamfer | 완전성 중앙값 | F@10.7mm | Hausdorff | 생성 시간 | 피크 VRAM |
| --- | --- | --- | --- | --- | --- | --- |
| **TripoSR** | **10.1mm** | **7.2mm** | **0.71** | **113mm** | 약 104s | 미계측 |
| SF3D | 46.6mm | 63.9mm | 0.27 | 236mm | 22s | 7.9GB(tex 2048) |
| SPAR3D | 46.8mm | 70.6mm | 0.27 | 207mm | 약 60s | 8.3GB(저VRAM, 물리 VRAM 초과) |

- SF3D·SPAR3D는 **앞면만 있는 얇은 부조**(깊이/폭 0.35·0.36, 실물 1.0). SF3D는 foreground ratio 0.75/0.85/1.0 모두 재현. 배경 제거 결과는 깨끗 → 전처리 문제 아님
- 텍스처는 SPAR3D가 최상(빗살·균열 보존), SF3D는 delighting으로 무늬 평탄화. 형상이 맞았다면 전시용 표면은 SPAR3D
- 전날 조사에서 "SF3D 1순위"로 본 것은 **실측으로 틀렸다.** 사진 1장 결과라 단정은 못 하지만 세 조건에서 재현됨
- 명세 시사점: **D-18 TripoSR 유지** / **G3 기준 수치화** — TripoSR 기준선 Chamfer 10.1mm·F@2% 0.71을 넘어야 교체 논의 / 막힌 입구·속 찬 형상은 단발 모델 공통 한계 → ③에서 입구 개방+벽 두께 부여 / 스캔 있는 유물은 스캔이 ①(명세 11.2, G3 폴백) / `compare.py`·`multi_compare.py`가 FR-AI-005 지표 도구 / 공식 VRAM 표기와 실측 차이 — 8GB PC에서 SF3D·SPAR3D는 여유 없음
