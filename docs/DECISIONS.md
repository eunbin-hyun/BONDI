## R1. 플랫폼 토대 — 확정 2026-08-31

### D-01. 엔진: 언리얼 엔진 5 (잠정) + W1 재검토 여지

- **Unreal Engine 5를 1순위로 진행한다.**
- 단, W1 스파이크 결과에 따라 Unity로 되돌릴 수 있다. **아직 동결(freeze)하지 않는다.**
- 기존 명세 v1.0의 3부·4부는 Unity 기반으로 작성돼 있고 `Unity`→`언리얼5` 전역 치환 사고가 있는 상태다.
  해당 내용은 **Unity 원문으로 복원해 별도 보존**하고, UE5 확정 시 폐기한다.
- **미결정:** 엔진 최종 확정 시점과 판단 기준 → R2에서 결정

### D-02. 주력 기기: Pico 4

- **Pico 4를 개발·최적화·성능 판정의 단일 기준 기기로 고정한다.**
- Quest 2는 보조 검증용. Quest 3는 사용하지 않는다.
- 보유: 오큘러스2 x3, 피코4 x2
- **파생 제약:**
  - Pico 4 / Quest 2 모두 Snapdragon XR2 **Gen 1** — Quest 3(Gen 2) 대비 GPU 성능이 크게 낮다.
  - 기존 명세의 성능 예산(72Hz, 350k tris, draw call 120, texture 256MiB)은 **Quest 3 + Unity URP 기준**이므로 그대로 사용 불가. 재산정 대상.
  - UE5 사용 시 PICO Unreal Integration SDK 필요. 손 추적 지원 범위를 W1에 실기 확인해야 한다.
- **미결정:** 새 성능 예산 수치 → R4에서 결정

### D-03. 범위: 세 축 모두 유지

1. 손상 3D 유물 복원
2. 단일 2D 이미지 → 3D 생성
3. VR 개인 박물관
- 축을 줄이지 않는다. 대신 **각 축 내부의 깊이를 얕게** 가져가 5주에 맞춘다.
- **미결정:** 각 축의 최소 성공 기준 → R3, R4에서 결정

### D-04. 핵심 컨셉: provenance 구분 — 유지 확정

- **"관측 데이터 vs AI 추정 영역을 구분해서 보여준다"**가 프로젝트의 핵심 가치다.
- **"AI 복원은 역사적 정답이 아니라 검증 가능한 복원 가설"** 원칙을 유지한다.
- 이 컨셉은 3D 복원과 2D→3D **양쪽 모두에** 적용한다.
  - 3D 복원: 관측부 / 추정부를 영역으로 분리
  - 2D→3D: 전체 geometry가 추정, 입력 사진만 관측 근거
- **미결정:** 검증·승인 절차의 복잡도 수준 (기존 명세의 3중 digest 검증은 과잉 가능성) → R3에서 결정

## R2. 제품 정의 — 확정 2026-08-31

### D-05. 팀 역량: VR 개발 경험자 보유

- 엔진 무관하게 XR/VR 앱을 만들어본 팀원이 있다. 프로젝트 최대 자산.
- UE5 자체 경험 여부는 별도 확인 대상이나, VR 도메인 지식은 확보된 것으로 본다.

### D-06. 엔진 확정 게이트: UE5 단독 스파이크

- **W1에 UE5만 스파이크한다.** 두 엔진 병행 스파이크는 하지 않는다 (W1 인력 분산 방지).
- **통과 조건:** Pico 4 실기에 UE5 빌드 설치 + VR 기본 동작 확인
- **실패 시:** 즉시 Unity로 전환. 되돌릴 수 있게 Unity 기반 기존 명세를 보존한다.
- 판단 시점: W1 내 (구체 일자는 R5 일정 확정 시 결정)

### D-07. 입력 방식: 컨트롤러가 기본, 손 추적은 목표

- **컨트롤러로 전체 핵심 흐름을 완성하는 것이 MUST다.**
- **손 추적은 SHOULD.** 되면 추가하고, 안 되면 범위에서 뺀다.
- ※ **기존 명세 v1.0과 정반대다.** v1.0은 손 추적이 MUST(M-06), 컨트롤러가 대체 입력(M-08)이었다.
  재작성 시 두 요구사항의 우선순위를 뒤집고 관련 수용시험도 함께 조정한다.
- 근거: Pico 4 + UE5 조합에서 손 추적이 최대 기술 리스크이고, 시연 안정성이 우선이다.

### D-08. VR 경험 재정의 — 큐레이션형에서 관람형으로

**공세민이 실제로 생각한 그림:**

> 박물관처럼 유물 카탈로그들이 전시되어 있고, 사용자는 그 유물에 가까이 가면
> 해당 정보와 우리가 복원한 내용·부분을 확인할 수 있게 UI로 띄운다.

**기존 명세 v1.0과의 차이 (중요):**

| 항목 | v1.0 (AI 작성) | 실제 의도 |
| --- | --- | --- |
| 컨셉 | "나만의 박물관" 큐레이션 | 관람형 박물관 |
| 유물 노출 | 5점 중 **3점만** 골라 배치 | 유물들이 **전시되어 있음** |
| 시작 흐름 | Composer 화면에서 선택·배치 후 입장 | 바로 전시 공간 |
| 정보 표시 | 유물 잡고 비교 모드 전환 | **가까이 가면** 정보 UI 표시 |
| 저장·재방문 | MUST | 불필요할 가능성 |

- v1.0의 `10_Composer` 씬, 3슬롯 배치, `museum-layout-v1.json` 저장 체계, FR-VR-002~007은
  **재검토 대상**이다. 그대로 유지하지 않는다.
- **미결정:** 전시 유물 수, 근접 UI 트리거 방식, 유물 조작 가능 여부, 복원부 표시 방식 → R3에서 결정

## R3. VR 경험 상세 — 확정 2026-08-31

### D-09. 전시 방식: 전부 고정 전시 (큐레이션 폐기)

- 제작한 유물 전부를 전시 공간에 **고정 배치**한다. 사용자는 돌아다니며 관람만 한다.
- **폐기 확정:** 유물 선택 화면(`10_Composer`), 3슬롯 배치, 배치 저장·재방문(`museum-layout-v1.json`),
  카탈로그 5점 중 3점 제약. v1.0의 FR-VR-002/003/004/006/007과 AT-05/06/07/16이 모두 삭제 대상이다.
- 제품 이름에서 **"개인형/나만의"** 표현을 뺀다. 큐레이션 제품이 아니다.
- **미결정:** 전시 유물 수와 공간 구성 → R5에서 결정

### D-10. 정보 UI: 거리 기반 자동 표시

- 유물에 일정 거리 안으로 들어가면 정보 패널이 **자동으로** 뜨고, 벗어나면 사라진다.
- 응시(gaze)나 포인팅 선택을 요구하지 않는다.
- **주의:** 유물이 가까이 모여 있으면 패널이 동시에 여러 개 떠서 겹칠 수 있다.
  전시대 간격과 트리거 반경을 함께 설계해야 하며, "가장 가까운 유물 1개만 표시" 규칙이 필요할 수 있다.
- **미결정:** 트리거 반경, 패널 위치·크기, 동시 표시 처리 → R5에서 결정

### D-11. 유물 조작: 잡고 돌리기 가능

- 사용자가 유물을 **집어서 회전시키며 관찰**할 수 있다. 놓으면 원래 전시대로 복귀한다.
- 기본 입력은 컨트롤러(D-07), 손 추적은 SHOULD.
- v1.0의 유물 상호작용 상태(`ON_PEDESTAL → HOVERED → GRABBED → RETURNING`)와
  FR-HND-003/004는 유지한다. 투척 물리는 넣지 않는다.

### D-12. 복원부 표시: 원본/복원 토글 + 설명 패널

**채택:**
1. **원본/복원 토글 전환** — 버튼 하나로 손상 원본 상태와 복원 상태를 번갈아 본다.
2. **패널 설명·근거 텍스트** — 어떤 모델로 어떻게 복원했는지, 한계는 무엇인지를 글로 함께 표시한다.

**미채택 (SHOULD 후보로 보류):**
- 복원부를 색·패턴으로 강조하는 방식 (v1.0의 `InferenceHighlight` 모드)
- 원본·복원본을 나란히 두 개 배치하는 방식

**데이터 구조에 미치는 영향 (중요):**
- v1.0은 하나의 모델 안에서 `observed` / `geometry_interpolated` / `ai_inferred` / `human_edited`를
  **submesh 단위로 분리**하고 `nodePath + primitiveIndex`로 바인딩하는 복잡한 계약을 요구했다(FR-DAT-005).
- 토글 방식만 쓴다면 **모델 두 개(손상 원본 / 복원본)를 전환**하는 것으로 충분하다.
  region submesh 분리·바인딩 계약 전체가 불필요해진다. 대폭 단순화 가능.
- 단, 토글만으로는 "복원된 모델의 **어느 부분**이 AI인지"가 직접 보이지 않는다.
  사용자가 두 상태를 기억해서 비교해야 한다. 색·패턴 강조를 SHOULD로 남겨두는 이유다.

## R4. AI 파이프라인 — 확정 2026-08-31

### D-13. 복원 사례: 미정 (실험 단계)

- **주 복원 사례를 아직 확정하지 않는다.** 팀원들이 각자 실험 중인 단계다.
- v1.0이 `ssu022891-001-30000_Step3.stl`을 "1순위 주 사례"로 못박은 것은 **근거 없는 조기 확정**이었다.
  현은빈의 U-Net 실험 대상일 뿐 팀이 합의한 전시 대상이 아니다.
- 기존 실험(현은빈 U-Net, 공세민 Geometry-prior)은 **학습·조사 자산**으로 보존하되
  제품 파이프라인의 확정 경로로 간주하지 않는다.
- **미결정:** 복원 대상 유물, 확정 시점 → R5 이후 별도 결정

### D-14. 복원 제작 방식: 2D→3D + Claude Blender MCP

**공세민이 구상하는 실제 흐름:**

> 2D에서 3D로 만들어서, 그 3D를 Claude MCP(Blender MCP)를 활용해서 복원물을 제작한다.

- **v1.0과 근본적으로 다르다.** v1.0은 "손상 3D 스캔 → 학습된 모델이 결손부 추론"이었다.
  실제 구상은 "사진 → 3D 생성 → **AI 에이전트가 Blender에서 복원 모델링**"이다.
- 2D→3D와 3D 복원이 **별개 축이 아니라 하나의 연결된 파이프라인**이 된다.
  v1.0의 M-01/M-02 분리 구조를 재검토해야 한다.

**파생 영향 (반드시 반영):**

1. **재현성 정의가 바뀐다.** LLM 주도 모델링은 결정론적이지 않다.
   v1.0의 `NFR-REP-002`(동일 seed·config에서 `1e-6` 이내 재현)는 **성립 불가**하다.
   재현성을 "동일 수치 재생산"이 아니라 **"작업 로그·프롬프트·중간 스냅샷 보존으로 과정을 추적 가능"**
   으로 재정의해야 한다.
2. **provenance 분류에 새 범주가 필요하다.** Blender MCP가 만든 영역은
   `ai_inferred`(모델 추론)도 `human_edited`(사람 제작)도 아니다. 별도 클래스가 필요하다.
3. **발표 임팩트는 오히려 커진다.** "AI 에이전트가 3D 복원 모델링을 수행"은 특화 프로젝트 주제로 강하다.

- **미결정:** MCP의 담당 범위, provenance 분류 방식 → R5에서 결정

### D-15. 부가 목표: 포트폴리오 활용

- 이 프로젝트를 **포트폴리오로도 쓸 수 있게** 3D 비전 모델을 활용하는 방법을 추가하고 싶다.
- 즉 프로젝트에는 **두 가지 목표**가 있다.
  1. 5주 안에 동작하는 시연물 (주 목표)
  2. 팀원 각자의 기술 포트폴리오 (부가 목표)
- 이 목표는 v1.0에 전혀 반영돼 있지 않았다. 명세서에 **명시적으로 기록**한다.
- 부가 목표는 주 목표의 일정을 침범하지 않는 선에서 배치한다.
- **미결정:** 어느 축에 3D 비전 모델을 붙일지, 필수/부가 여부 → R5에서 결정

### D-16. 2D→3D 모델: 미정 — 후보군에서 선정

- 확정하지 않았다. W1에 실제 실행해보고 정한다.
- **미결정:** 후보 확정 → R5에서 결정

### D-17. 검증·승인 절차: 크게 단순화

- v1.0의 RFC 8785 정규화 해시 **3중 검증**(technical digest / approved digest / current digest 일치),
  `REGISTERED→…→APPROVED` 8단계 상태 머신, `PREBUILD_VALIDATED`/`BUILD_VALIDATED` 이중 빌드 레코드를
  **모두 폐기한다.**
- 대체 수준: 자산마다 **출처·라이선스·생성 방식·한계**를 JSON으로 기록하고 **팀원 1명이 눈으로 확인**한다.
- 자동 검사는 최소한만 남긴다 (파일 존재, 메시 유효성, 면 수·텍스처 예산).
- **버리는 안전장치 (인지하고 감수):**
  - 승인 후 파일이 몰래 바뀌어도 빌드가 막히지 않는다 (AT-29 폐기)
  - 미승인 자산이 빌드에 섞여 들어갈 수 있다 → **카탈로그 목록을 코드로 명시**하는 방식으로 대체
- v1.0의 FR-DAT-006, AT-28/29, 4.2 pre-build 증거 8종은 삭제 대상이다.

## R5. 파이프라인 확정 — 확정 2026-08-31

### D-18. 2D→3D 모델: TripoSR(안전판) + Hunyuan3D 2.x(도전)

- **TripoSR을 먼저 붙여 파이프라인을 관통시킨다.** MIT, 저VRAM, 설치 단순 — W1이 막힐 위험이 가장 낮다.
- **병행해서 Hunyuan3D 2.x를 시도**하고, 품질이 확인되면 교체한다.
- TRELLIS는 이번 범위에서 제외한다 (VRAM 부담). 발표 자료에는 대안 조사 결과로만 언급 가능.
- W1에 기준 PC(RTX 4070 Laptop)에서 실제 실행·VRAM·소요시간을 측정해 기록한다.
- 두 모델 중 **최종 1개만** 제품 경로에 남긴다. 병행 유지하지 않는다.

### D-19. Blender MCP 범위: 복원 모델링 전체

- **손상부를 채우고 형상을 만드는 복원 작업 자체를 Claude Blender MCP로 수행한다.**
- 이것이 이 프로젝트의 AI 색깔이며 특화 주제의 핵심이다.
- **반드시 남겨야 할 것 (재현성 대체 수단):**
  - 사용한 프롬프트 전문
  - MCP 작업 로그 (호출 순서와 결과)
  - 복원 전/중/후 메시 스냅샷
  - 작업자, 소요 시간, Blender 버전
- 위 기록이 v1.0의 `seed + config hash` 자리를 대신한다.

### D-20. provenance 표시: 'AI 추정'으로 통합

- 3D 비전 모델이 만들었든 Blender MCP가 만들었든 **전부 "AI가 추정한 영역"으로 묶어서 표시**한다.
- v1.0의 4개 region class(`observed` / `geometry_interpolated` / `ai_inferred` / `human_edited`)를
  **`observed` / `ai_inferred` 2개로 축소**한다.
- D-12(원본/복원 토글) + D-17(검증 단순화)와 합쳐지면 데이터 계약이 대폭 단순해진다.
  submesh 단위 region 바인딩(`nodePath + primitiveIndex`) 계약 폐기 가능.

### D-21. 포트폴리오용 3D 비전 모델: 위치 미정

- D-15의 부가 목표는 유지하되, **제품 경로 어디에 붙일지는 아직 정하지 않는다.**
- 팀원들의 실험 결과를 보고 결정한다.
- 명세서에는 "부가 목표로 존재하며 위치 미정"이라고 명시한다. 조용히 빠뜨리지 않는다.

## R7. 직군·예산 — 확정 2026-08-31

### D-26. FE 직군 = VR 내부 UI/UX

- 웹 프론트엔드는 **만들지 않는다.** 관리자 웹, 공개 웹 전시관 모두 범위 밖이다.
- FE 직군은 **VR 안의 UI/UX**를 담당한다: 정보 패널, 원본/복원 토글, 안내 문구, 폰트·대비,
  그리고 D-25에 따라 **미러링 화면에서의 가독성**.

### D-27. Infra 직군 = 빌드·자산 파이프라인 + CI/CD

- APK 빌드 자동화, 자산 검사 스크립트, 저장소 구조, 대용량 파일 관리, 환경 재현
- **추가로 CI/CD를 구축한다.** (GitLab CI 등)
- ※ UE5 빌드는 CI 구축 난도가 높다. W1에 파일럿을 돌려보고, 막히면
  "로컬 빌드 스크립트 + 수동 배포"로 내려오는 fallback을 미리 정해둔다.

### D-28. 3D 스캔 데이터 확보 판단: W1 안에

- W1 안에 실측 3D 데이터 확보 가능성을 확인하고 **입력 경로를 확정한다.**
- 못 구하면 즉시 **사진 단일 경로로 확정**하고 이후 설계를 진행한다. W2로 넘기지 않는다.

### D-29. 성능 예산: W1 실기 측정 후 확정

- v1.0의 수치(72Hz / 350k tris / draw call 120 / texture 256MiB / PSS 2.5GB)는
  **Quest 3 + Unity URP 기준이므로 전부 폐기한다.**
- W1에 Pico 4 실기에서 측정한 뒤 확정한다. 그전까지 명세에 숫자를 적지 않는다.
- 측정할 것: 목표 프레임(72/90Hz), 유물 1점당 면 수 상한, 최대 장면 면 수,
  draw call, 텍스처 총량, 메모리
- **W1 측정 전까지의 임시 작업 기준** (자산 제작이 멈추지 않게):
  유물 1점당 30k 면 이하, 텍스처 1024 이하로 보수적으로 만든다. 측정 후 상향 조정한다.

**② 복원 대상 선정 기준 (부록 A.4)**

두 건의 실험이 같은 결론을 냈다.

- 토기 항아리: 하부 전체 결실인데 PoinTr가 완형(bowl)으로 오인해 보충점 0점

**③ 색상 복원의 범위 (부록 A.3)**

Blender MCP(`bpy`)는 이미지 생성을 못 하므로 색상·풍화 복원에는 적용되지 않는다.
지오메트리 복원과 색상 복원은 서로 다른 종류의 AI가 필요한 별개 작업이다.
현재 명세는 이 구분을 담고 있지 않다. 색상 복원을 범위에 넣을지 결정이 필요하다.

**④ 데이터 라이선스 (부록 A.6)**

AIHub 계열 LAS 데이터를 여러 명이 이미 사용 중이나

김채원이 지적한 대로 데이터 ID와 실제 문화재명의 공식 대응표도 없다.

## R11. 복원 대상 방향 — 확정 2026-08-31

### D-43. 소형 유물로 한정, 토기로 먼저 관통

**개체는 여전히 미정이다 (U-05). 방향만 확정한다.**

**대상 유형: 소형 유물** — 토기, 검 등 단일 개체. 건축물·대형 석조물은 제외한다.

이 제약이 명세와 잘 맞는 이유:

- 사진 1장에 전체가 들어가고 배경이 단순해 `13.1 사진 입력 프로파일`을 충족하기 쉽다
- 전시대에 올려 근접 관찰하기 좋은 크기다 (D-11 잡고 돌리기)
- 김채원이 석인상에서 겪은 **지면·식생 분리 문제가 발생하지 않는다**
- 자산 예산에 유리하다

**진행 순서: 토기 우선**

- W2 수직 슬라이스는 **토기**로 관통한다.
- 다른 종류는 W3 콘텐츠 확대 단계에서 추가한다.
- 이유: 팀에 토기 실험 경험이 이미 셋 있고(현은빈 U-Net, 권영호 회전대칭, 장서진 PoinTr),
  얇고 긴 금속 유물은 2D→3D 생성 모델이 가장 약한 형태다.

**최종 3점 구성: 종류별 1점씩 (목표)**

- N-05의 MUST 3점은 **종류별 1점씩**을 목표로 한다.
- **Fallback:** 다른 종류가 W3까지 안 되면 **같은 종류로 3점을 채운다.**
  N-05는 점수만 요구하고 종류를 요구하지 않으므로 MUST는 지켜진다.

**검 유형의 알려진 위험 (명세 13.1에 기록)**

| 항목 | 내용 |
| --- | --- |
| 형태 | 얇고 긴 검신·슴베가 2D→3D 생성에서 뭉개지기 쉽다 |
| 재질 | 금속 반사가 사진 기반 생성 품질을 크게 떨어뜨린다 |
| 크기 | 사진만으로는 실물 크기를 알 수 없어 `scaleKnown=false`가 된다. **검은 길이가 핵심 정보이므로** 전시 크기의 근거를 검수자가 반드시 기록해야 한다 |
| 유리한 점 | 좌우대칭이 강해 대칭 기반 복원에는 유리하다 |

**개체 선정 시 적용할 기준 (부록 A.4의 교훈)**

1. **결손이 실제로 존재하는가** — 석인상처럼 결손이 없으면 "복원 전시"가 성립하지 않는다
2. **그 결손이 AI로 다룰 만한가** — 토기 항아리처럼 하부 전체가 결실되면
   생성 모델이 완형으로 오인해 보충점이 나오지 않는다
3. 사진 입력 프로파일을 충족하는 사진을 구할 수 있는가
4. 출처·라이선스가 확인되는가

### D-45. PC VR 방식이 MUST (D-41 부분 번복)

- **시연은 PC에 연결한 상태로 한다.** PC가 렌더링을 담당해 그래픽 품질을 높인다.
- **환경 제약(배선·PC 반입)이 생기면 헤드셋 내부 빌드로 전환**하고 그래픽 하향을 감수한다.

### D-46. 이동·회전: 연속 이동 + 시선 회전 (FR-VR-007 폐기)

- **스냅 턴을 쓰지 않는다.** 회전은 헤드셋을 돌리는 것으로 처리한다.
- **전시실 내부 이동 = 연속 이동.** 걸어다니듯 이동한다. 컨트롤러는 **조이스틱만**
  사용하며 텔레포트 조준선은 없다. 전시실 안에서는 텔레포트를 쓰지 않는다.
- **전시실 사이 이동 = 포털 순간이동**(`D-54`). 메인 홀 안내판 옆 포털 → 해당
  전시실, 전시실 ↔ 전시실도 포털. 연속 이동은 방 내부에만 적용한다.
- 이전 명세의 `FR-VR-007`(연속 이동 강제 금지)은 **전시실 내부에 한해** 폐기된다.
- **인지하고 감수하는 위험:** 연속 이동은 VR 멀미의 주요 원인이다.
  이동 가속을 최소화하고, 리허설에서 시연자 여러 명이 사전 검증한다.
  멀미가 확인되면 이동 구간을 줄인 동선으로 대응한다. 위험 표에 등재했다.
- **갱신 2026-09-09:** 팀 내부 협의로 전시실 내부(연속)/전시실 사이(포털)
  분리를 확정. `D-54`와 정합.

### D-47. 복원 3단계 토글

- 원본/복원 2단계를 **3단계로 확장**한다.

| 단계 | 내용 |

| ① 손상 상태 | 생성 모델이 만든 훼손 그대로의 형상 |
| ② 모델 복원 | 3D 복원 모델이 결손부를 채운 상태 |
| ③ MCP 복원 | Blender MCP가 다듬은 상태 |

### D-55. 전시 공간의 건축은 모델링 메시로 만든다 — 확정 2026-09-10

- **문제.** 홀·테마관의 벽·바닥·천장·기둥·문틀을 엔진 프리미티브(늘린 큐브)로 세웠더니, 스캔 PBR 재질과 베이크 조명을 넣어도 "블록"으로 보였다. 실제 미술관 벽도 평면이므로 원인은 형태가 아니라 **몰딩·걸레받이·문틀이 없고 모서리가 전부 90°라 빛을 받지 못하는 것**이었다.
- **결정.** 건축 요소는 **Blender에서 모델링해 FBX로 임포트한다.** 프리미티브는 임시 배치·프로토타이핑에만 쓴다.
  - 홀(고전) — 걸레받이, 웨인스코트 판넬과 챙목 레일, 코브 조명 홈, 격자 천장, 반원 아치 문틀.
  - 테마관(현대) — 몰딩 대신 바닥 그림자 홈(벽이 떠 보이는 8 cm 슬릿), 천장 단차, 코브 홈.
  - 모든 모서리에 **1.2 cm 챔퍼**. 이것 하나가 CG 느낌을 가장 크게 줄인다.
- **필수 제약 — 메시에 UV가 반드시 있어야 한다.** 표면 재질이 월드 정렬 트라이플래너(`M_Museum_Scan`)라 재질용 UV는 필요 없지만, **Lightmass는 UV 없이 굽지 못한다.** UE는 UV0을 소스로 라이트맵 UV를 생성하는데 소스가 없으면 조용히 실패하고, 해당 메시는 스카이라이트만 받아 남색으로 보인다. Blender에서 UV0(재질용)·UV1(라이트맵용) 두 채널을 만들어 내보낸다. 임포트 후 `LightMapCoordinateIndex`가 0이 아닌 값이면 정상이다.
- **알베도 상한 0.75.** 흰 대리석을 1.0으로 두면 좁은 실내에서 바운스가 폭주해 베이크 결과가 하얗게 날아간다. 실제 백대리석은 0.65 내외다.
- **조명 기구 메시는 그림자를 끈다.** 샹들리에 링·다운라이트 디스크가 자기 빛을 가려 천장이 새까맣게 나왔다. 아크비즈 관행대로 `CastShadow=false`.
- **파생:** 22.2.1에 라이트맵 UV·알베도·기구 그림자 항목 추가. 프리미티브로 만든 소품(샹들리에·소파·피처월·배경벽)은 다음 라운드에 같은 방식으로 교체한다.

### D-56. 안내 패널은 그림으로 줄이고, AI 고지는 1·5번과 유물 옆에만 둔다 — 확정 2026-09-11

- **문제.** 홀 안내 패널 5장이 전부 줄글이었다. 스폰 정면 호(弧)에 5장을 세우고 순차 공개까지 붙였는데도
  "너무 줄글"이라 읽히지 않았다. 게다가 **AI 복원 고지를 5장 모두 하단에 붙여** 놓아서, 한 장에 평균
  4줄이 고지로 채워졌다 — 정작 조작을 배우러 온 사람에게는 같은 문장을 다섯 번 읽히는 셈이었다.
- **결정 1 — 설명은 그림이 하고 글은 제목 + 1~2줄만 남긴다.**
  3번(손 조작)을 시제품으로: 본문을 7줄 → 3줄로 줄이고, 패널 앞에 **핀치하는 손 3D 픽토그램**
  (`SM_Icon_PinchHand`)을 띄운다. 게임이 실제로 손을 관절 구체로 그리므로, 같은 모양의 손을 보여 주면
  "관절마다 구체로 표시된다"와 "엄지·검지를 맞대면 집기"를 그림 하나가 동시에 설명한다.
  접점에는 두 번째 머티리얼 슬롯(`MI_HoloIcon_Spark`)의 밝은 구슬을 놓아 어디가 핵심인지 못 놓치게 한다.
- **결정 2 — 픽토그램은 천천히 돈다.** 정지한 3D 아이콘은 관람자가 서는 위치에 따라 전혀 다르게 보인다.
  실제로 같은 메시가 각도에 따라 "손"으로도 "덩어리"로도 보였다. 관람자를 바라보게 만드는 방법도 있지만
  **월드 Z축으로 초당 35°씩 돌리는 쪽이 노드 두 개로 끝나고**, 몇 초 안에 반드시 읽히는 각이 온다.
  회전 반경만큼 패널에서 띄워야 한다 — 메시 원점을 바운딩 박스 중심으로 옮겨(`museum_icons.py`) 반경을
  8.6 cm로 줄이고, 배율 3.6에서 패널 앞 40 cm에 놓았다.
- **결정 3 — AI 고지는 1번(입장)·5번(전시 시작)과 테마관 유물 패널에만 둔다.**
  `NFR-ETH-003`이 요구하는 것은 "관측과 AI 추정의 구분"이지 같은 문장의 반복이 아니다. 생성물 바로 옆인
  **유물 패널**에서 요건을 충족하고, 홀에서는 입·출구 두 장이 맥락을 잡아 준다. 이동·손·시야를 설명하는
  2·3·4번에서는 `Text_Disclaimer` 위젯을 **제거**했다.
  - `Visibility: Collapsed` 로는 지워지지 않았다. 애셋(템플릿과 생성 클래스 양쪽)은 `Collapsed`로 읽히는데
    레벨에서는 계속 그려졌다. 원인을 더 파는 대신 `UMGToolSet.RemoveWidget`으로 위젯 자체를 뺐다.
- **결정 4 — 픽토그램은 Unlit 으로 두지 않는다.** 처음 만든 아이콘은 `M_Museum_Emissive`(Unlit)를 썼는데,
  면 방향이 결과에 전혀 들어가지 않아 어느 각도에서 봐도 납작한 실루엣이었다. 관람자가 "물체 같지 않다"고
  했고 원인은 테두리가 아니라 **음영이 없는 것**이었다. `M_HoloIcon` = `M_Museum_Emissive` 복제 +
  프레넬 림 + 방향 음영으로 바꿨다:
  `Emissive = EmissiveColor * Intensity * (Lerp(1, N·L*0.5+0.5, ShadeAmount) + Fresnel * RimBoost)`.
  Unlit 을 유지한 이유는 홀 조명·베이크와 무관하게 홀로그램이 항상 같은 밝기로 보여야 하기 때문이다.
  `Intensity` 는 1.2 — 2.5 에서는 톤매핑에 날아가 음영이 다시 사라진다.
- **범위.** 2·3·4·5번에 픽토그램을 놓는다(조이스틱·손·받침대·아치). **1번은 텍스트만** 둔다 —
  입장 인사와 AI 고지가 들어가 있어 그림을 더하면 붐비고, 5번 아치와 의미가 겹친다.
- **파생:** 21.5 홀 행에서 "모든 패널 하단" 문구를 고친다. 2·4·5번 본문도 제목 + 2~3줄로 줄였다.

### D-57. 리센터는 관람자를 제자리에 둔다 — 확정 2026-09-11

- **증상.** 포털로 테마관에 갔다 홀로 돌아온 뒤 메타 버튼으로 리센터하면 엉뚱한 곳에 가 있다.
- **원인 두 가지.**
  1. **리센터가 관람자를 폰 원점으로 던진다.** 트래킹 원점이 `LocalFloor` 라서 메타 버튼을 누르면
     런타임이 로컬 공간을 현재 머리 위치로 다시 0 으로 잡는다. 그러면 HMD 오프셋이 0 이 되어 카메라가
     `VROrigin`(= 폰 원점)으로 순간이동한다. 평소엔 플레이 공간 반경(≈1~1.5 m)만큼이지만,
     **포털이 이 오프셋을 키운다** — `BP_Portal` 은 카메라가 목표점에 정확히 서도록
     폰을 `목표 − 회전된 HMD 오프셋` 에 놓기 때문에, 왕복하면 폰 원점이 머리에서 2~3 m 떨어진다.
  2. **홀 복귀 지점이 안내 패널에 너무 붙어 있었다.** 세 방 모두 `TargetLoc = (350, 0, 0)`,
     yaw 0 — 패널 호(스폰 (220,0) 반경 300) **안쪽**이고, 정면 170 cm 에 3번 패널이 있다
     (위젯 컴포넌트에도 콜리전이 있어 트레이스에 걸린다). 리센터로 1.5 m 밀리면 패널·아치 사이에 낀다.
- **결정 1 — 복귀 지점을 (280, 0, 0) 으로 옮긴다.** 사방 최소 240 cm (동 240 · 서 275 · 나머지 >300).
  기존 170 cm 대비 크게 개선되고 `D-54` 의 2 m 규칙을 만족한다. 세 방 모두 같은 값이다.
- **결정 2 — 리센터 때 관람자의 월드 위치를 유지한다.** `BP_XRPawn` 의 기존 `VRNotifications`
  컴포넌트에 `HMDRecenteredDelegate` 와 `XRTrackingOriginChangedDelegate` 를 물려
  `MarkRecenter`(카운터 2 설정) 를, 틱에 `KeepPlaceOnRecenter` 를 건다. 카운터가 1 이 되는 틱에
  `AddActorWorldOffset(리센터 직전 카메라 XY − 현재 카메라 XY)` 로 되돌린다.
  **2틱 미루는 이유**는 델리게이트 브로드캐스트와 카메라 포즈 갱신의 순서가 런타임마다 달라서다.
  카운트다운 중에는 `LastCamXY` 를 갱신하지 않아 "리센터 직전" 값이 보존된다.
- **위치만 되돌리고 yaw 는 그대로 둔다.** 관람자가 메타 버튼을 누르는 이유가 정면 재정렬이므로
  yaw 까지 되돌리면 리센터가 아무 일도 안 하는 셈이 된다.
- **검증.** PIE 에서 `LastCamXY`·`RecenterFrames` 를 주입해 폰이 정확히 그 차이만큼
  (+100, +40) 이동하는 것을 확인했다. **실기 확인은 아직** — 델리게이트가 ALVR/SteamVR OpenXR 에서
  실제로 발화하는지는 헤드셋에서 봐야 한다. 발화하지 않아도 손해는 없고(틱이 벡터 하나 저장할 뿐),
  결정 1 의 여유 덕분에 최악의 경우에도 빈 바닥에 선다.
- **파생:** `BP_XRPawn` 은 XRFramework 공용 파일이다(si_hoo903). 노드는 그래프를 다시 쓰지 않고
  `add_event`·`add_component_bound_event`·`create_node`·`connect_pins` 로 얹었다 —
  `write_graph_dsl` 은 이 그래프에서 **손실이 있다**(노드 158개인데 DSL 은 입력 이벤트 본문을 비워서 낸다).

### D-58. 리센터는 트래킹 원점으로 막는다 — 추론 감지는 버린다 — 확정 2026-09-11

- **측정.** `D-57` 의 보정을 넣고 실기에서 진단 카운터를 읽었다:
  `DelegateHits = 0`, `RecenterHits = 4`, 폰 위치 `(-130, -135)`.
  - **이 런타임(ALVR + SteamVR OpenXR)은 리센터를 알려 주지 않는다.**
    `HMDRecenteredDelegate` 도 `XRTrackingOriginChangedDelegate` 도 발화하지 않았다.
  - **그리고 내가 넣은 추론 감지가 관람자를 홀 밖으로 끌어냈다.** (-130,-135)는 서쪽 벽 바깥이다
    (그 지점에서 동쪽으로 쏘면 110 cm 에 벽이 맞는다).
- **왜 추론이 틀렸나.** "머리는 한 프레임에 몇 cm 만 움직인다"를 전제로 머리–원점 거리가 한 프레임에
  20 cm 넘게 줄면 리센터로 봤다. **ALVR 은 프레임을 300 ms 씩 흘린다.** 그 한 프레임 동안 머리는
  실제로 30~40 cm 움직인다. 스터터마다 오발화해서 관람자를 계속 뒤로 당겼다.
  → **프레임당 거리 임계값은 흔들리는 링크에서 반드시 깨진다.** 다시 넣으려면 최소한
  `DeltaSeconds` 로 나눠 속도로 판정해야 하고, 그래도 트래킹 원점 해결책이 우선이다.
- **결정 — `SetTrackingOrigin` 을 `LocalFloor` → `Stage` 로 바꾼다.**
  `LocalFloor` 는 리센터 때 런타임이 현재 머리 위치로 로컬 공간을 다시 0 으로 잡아서
  카메라가 `VROrigin` 으로 튄다. `Stage` 의 원점은 가디언 중심이라 뷰 리셋이 건드리지 않는다.
  **한 줄짜리 변경이고 되돌리기도 한 줄이다.**
- **못 고치는 것.** 카메라는 항상 `VROrigin + HMD포즈` 다. HMD 포즈를 0 으로 만들 수 있는 건
  런타임뿐이므로, **앱이 카메라와 폰 원점을 겹치게 만들 방법은 없다.** 리센터가 위치를 바꾸는 걸
  앱에서 "감지해서 되돌리는" 접근은 알림이 오는 런타임에서만 성립한다. 여기서는 안 온다.
- **델리게이트 경로는 남긴다.** 비용이 0 이고(발화가 없으면 완전히 비활성) 다른 런타임에서는 뜬다.
- **파생:** 실기 재확인 필요. Stage 를 런타임이 지원하지 않으면 조용히 Local 로 떨어져 증상이 그대로다.
  그 경우 남는 수단은 도착 지점 여유(`D-57` 결정 1)뿐이다.

### D-59. 리센터가 서는 자리를 정한다 — 폰 원점을 마크에 세운다 — 확정 2026-09-11

- **요구.** 메인 홀은 기본. **각 테마관에서는 리센터하면 그 방 포털을 등지고 포털 바로 앞에 선다.**
- **성립 근거.** 리센터는 카메라를 `VROrigin`(= 폰 원점)으로 보낸다. `D-58` 에서 이 런타임이
  리센터를 **알려 주지 않는다**는 걸 측정으로 확인했으므로 "감지해서 되돌리기"는 불가능하다.
  대신 **착지 지점이 폰 원점이라는 성질을 이용한다** — 폰 원점을 원하는 마크에 세워 두면
  리센터가 항상 그 마크로 데려간다.
- **결정.** `BP_Portal` 이 폰을 `TargetLoc` 에 **그대로** 놓고 yaw 도 `TargetRot.yaw` 로 절대 지정한다.
  기존에는 카메라가 목표점에 정확히 서도록 폰을 `목표 − 회전된 HMD 오프셋` 에 놓았는데,
  그게 폰 원점을 마크에서 밀어내 리센터를 망가뜨리던 원인이었다(`D-57`).
- **대가.** 도착 순간 **머리**는 마크에서 "관람자가 플레이 공간 중심에서 벗어난 만큼" 어긋난다.
  그래서 도착 지점을 사방 2 m 이상 비워 두는 규칙(`D-54`·`D-57`)이 더 중요해졌다.
  홀 복귀 (280,0) 는 사방 최소 240 cm, A방 도착은 머리 높이 사방 297 cm 이상이다.
- **한계 — 조이스틱으로 걸으면 마크도 같이 움직인다.** 이동은 폰을 옮기고, 리센터 착지 지점은
  폰 원점이므로 둘을 분리할 수 없다. 카메라는 항상 `VROrigin + HMD포즈` 이고 HMD 포즈를 0 으로
  만들 수 있는 건 런타임뿐이다. 따라서 "방 안 어디서 걸어 다녀도 리센터는 항상 포털 앞"은
  **이 구조로는 불가능**하다. 도착 직후에는 정확히 마크이고, 걸은 만큼 함께 밀린다.
  방에서 조이스틱 이동을 빼면(룸스케일 전용) 마크가 고정된다 — 필요하면 그때 결정한다.
- **`BP_XRPawn` 의 위치 복원은 제거했다.** 리센터에서 원래 자리로 되돌리는 동작은 이 설계와 정반대다.
  카운터(`DelegateHits`)만 진단용으로 남겼다. 트래킹 원점은 `LocalFloor` 로 되돌렸다 —
  `Stage` 는 리센터가 위치를 안 건드리게 만들어서, 오히려 "마크로 데려가기"를 막는다.
- **검증.** PIE 로 양방향 확인: 홀→A방 폰이 (4800,−6000) yaw 0(복귀 포털 4620 앞 180 cm, 방 안쪽 향함),
  A방→홀 폰이 (280,0). 실기 확인 필요.
- **뒷정리(2026-09-11).** `BP_XRPawn` 에 넣었던 진단 장치를 전부 걷어냈다 — 틱 이벤트, 바운드 이벤트 2개,
  호출 노드 3개, 함수 `MarkRecenter`·`KeepPlaceOnRecenter`, 변수 5개. 노드 158개·그래프 10개·변수 11개로
  **원본과 일치**한다. 설계가 델리게이트에 전혀 의존하지 않게 됐으므로, 이름만 보면 뭔가 하는 것 같은
  죽은 코드를 공용 파일에 남기는 게 더 위험하다.
  - **함정:** 노드를 지운 직후 PIE 에서 폰이 스폰되지 않고 `SpectatorPawn` 이 대신 떴다. 컴파일 에러도
    CDO 손상도 없었다 — **저장하지 않아 스켈레톤만 컴파일된 상태**였던 것이다. 저장해 풀 컴파일을
    강제하니 정상 스폰. 블루프린트를 노드 단위로 수술한 뒤에는 **반드시 저장까지 하고** PIE 를 돌린다.

### D-60. 순간이동할 때 머리를 플레이 공간에 맞춰 0 으로 돌린다 — 확정 2026-09-11

- **실기 측정(`D-59` 검증).** 리센터 자체는 완벽했다 — 홀·방 모두 머리가 마크에서 **1.6~13 cm**,
  방향 **0.4~1.6°**. 4번 체크포인트에서 복귀 포털이 등 뒤 정확히 177 cm, 요구대로였다.
  **문제는 리센터가 아니라 도착이었다:**

  | | 상황 | 머리↔마크 |
  | --- | --- | --- |
  | 1 | 홀 스폰 | 233 cm |
  | 2 | 홀 리센터 | 13.5 cm |
  | 3 | A방 도착 | **369 cm** |
  | 4 | 방 리센터 | 3.3 cm |
  | 5 | 홀 복귀 | **162 cm**, 뒤돌아선 채 |
  | 6 | 홀 리센터 | 1.6 cm |

  `LocalFloor` 는 관람자가 실제로 걸은 만큼 HMD 오프셋을 계속 키운다. 폰은 마크에 서지만
  **머리는 그만큼 벗어난 채 도착**하고, 방향도 몸이 향한 대로다 — 포털에 들어가려 돌아섰으니 뒤를 본다.
  **관람객은 메타 버튼을 누를 줄 모른다.**
- **결정.** `BP_Portal` 이 페이드 아웃 뒤·폰 이동 앞에
  `ResetOrientationAndPosition(Yaw 0, OrientationAndPosition)` 을 호출한다.
  그러면 머리가 VR 원점에 0 으로 붙고, 도착은 **폰 트랜스폼이 전부 결정**한다.
  0.08 초 페이드 뒤라 관람객은 리셋을 느끼지 못한다.
- **왜 이제야 하나.** 처음엔 "플로어 기준 원점에서 위치를 리셋하면 머리 높이까지 0 이 될 수 있다"는
  우려로 피했다. 이번 측정이 그 우려를 없앴다 — 런타임 리센터가 위치와 yaw 를 리셋하면서
  **눈높이는 z≈160 으로 세 번 다 유지**했다. 같은 연산이므로 높이는 안전하다.
- **검증 — 실기 완료 2026-09-11.** 리센터를 누르지 않은 상태의 도착 측정:

  | 구간 | 이전 | 이후 |
  | --- | --- | --- |
  | A방 도착 | 369 cm · 몸 방향 그대로 | **13 cm · yaw 4.7°** |
  | 홀 복귀 | 162 cm · 뒤돌아선 채(−173°) | **15 cm · yaw −0.9°** |

  **눈높이는 z 162·164 로 유지**됐다 — 피했던 우려는 근거가 없었다.
  같은 세션에서 패널 가독성·픽토그램 4종·회전 속도(초당 35°)·벽 콜리전·멀미까지 모두 확인,
  이상 없음. 이로써 `D-54`~`D-60` 의 포털·리센터 작업이 실기 검증을 통과했다.

### D-61. 전역 조명은 Movable 로 둔다 — 확정 2026-09-11

- **배경.** 성능 점검에서 `L_XRTemplate_Lighting` 의 `DirectionalLight`·`SkyLight` 가 Movable 인 것을
  찾았다. 베이크와 무관하게 매 프레임 그림자를 다시 계산하므로 VR(눈마다 렌더)에서는 상시 비용이
  가장 큰 항목이다. UE VR 템플릿 기본값이고 우리가 바꾼 적은 없다.
- **결정.** **그대로 둔다.** Stationary 로 내리면 크게 싸지지만 **라이팅 재베이크가 필요**하고,
  안 구우면 장면이 어두워진다. 실기(ALVR + SteamVR OpenXR)에서 **렉이 없다고 확인**됐으므로
  굽는 시간과 어두워질 위험을 지불할 이유가 없다.
- **같이 고친 것은 남긴다.** 이번 점검에서 실제로 비쌌던 두 가지는 처리했다 —
  안내 패널 렌더 타깃이 매 프레임 갱신되던 것(`RedrawTime` 0 → 1.0)과 `BP_HoloGuide` 틱이
  알파가 안 바뀌어도 매번 쓰던 것. 둘 다 재베이크가 필요 없는 순수 이득이었다.
- **다시 꺼낼 조건.** 프레임이 실제로 모자랄 때. 그때는 이 항목이 1순위다.
  방 B·C 의 `Fill_*`·`Spot_*` 도 Movable 이므로(A 방은 Static) B·C 를 제대로 만들 때 같이 본다.
