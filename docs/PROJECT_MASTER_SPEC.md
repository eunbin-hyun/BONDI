# 1부. 프로젝트 기획

## 1. 목적

4주 안에 심사위원 앞에서 시연 가능한 제품을 만든다. 이 문서는 그 제품의 범위, 팀 구성, 일정,
완료 조건, 위험 대응을 확정한다.

이 프로젝트에는 목표가 둘 있다.

1. **주 목표** — 4주 안에 동작하는 시연물
2. **부가 목표** — 팀원 각자의 기술 포트폴리오

부가 목표 때문에 주 목표가 늦어지면 부가 목표를 버린다.

## 2. 제품 정의

### 2.1 한 문장 정의

> 훼손된 유물을 **AI가 단계별로 복원하는 과정**을 VR 안에서 직접 보고 비교하는 박물관.

이 제품이 다른 디지털 전시와 다른 지점은 **완성본 하나를 보여주지 않는다**는 것이다.
손상된 상태에서 복원된 상태까지 **어떤 단계를 거쳐 무엇이 채워졌는지**를 사용자가 직접 전환해 본다.

### 2.2 해결하려는 문제

- 훼손된 문화유산을 완성된 모델 하나로만 보여주면, 보는 사람은 무엇이 실제 근거이고
  무엇이 추정인지 알 수 없다.
- 기존 디지털 전시는 대부분 수동 관람이라 유물을 가까이 보고 돌려보며 복원 근거를 확인하기 어렵다.
- 3D·AI 처리 결과와 VR 전시 자산 사이에 공통 기준이 없으면 통합 단계에서 크기·축·재질·성능 문제가 터진다.

### 2.3 핵심 가치

1. **단계의 가시화** — 복원이 한 번에 되는 게 아니라 여러 단계로 쌓인다는 것을 보여준다.
2. **투명성** — 관측과 AI 추정을 구분하고 근거·한계를 함께 보여준다.
3. **직관성** — 유물을 직접 잡고 돌려보며 단계를 전환한다.

## 3. 핵심 컨셉 — 3단계 복원

이 프로젝트의 복원은 **한 번에 끝나지 않고 세 단계로 쌓인다.** 이 구조를 사용자가 직접 전환해
보는 것이 제품의 핵심이다.

```text
📷 입력 사진 / 스캔        ← 관측 근거

  ① 손상 상태 3D           생성 모델이 만든, 훼손된 그대로의 형상
        ↓  3D 복원 모델
  ② 모델 복원              결손부를 학습 모델이 채운 상태
        ↓  Claude Blender MCP
  ③ MCP 복원               AI 에이전트가 형상을 다듬어 완성한 상태
```

- VR의 **복원 단계 토글**은 이 ①②③을 전환한다.
- 세 상태 모두 **AI가 추정한 결과**다. 사진에 보이지 않는 면은 전부 추정이다.
- **단계가 올라갈수록 추정의 비중이 커진다.** 이 사실을 정보 패널에 명시한다.
- 이 구조는 숨겨야 할 약점이 아니라 **제품이 주장하는 정직성 그 자체**다. 발표에서 전면에 내세운다.

> **②와 ③을 나누는 이유.** 3D 복원 모델과 AI 에이전트는 서로 다른 방식이고 결과도 다르다.
> 둘을 나란히 보여주면 "AI 복원"이 하나의 기술이 아니라는 것이 드러나고,
> 팀이 두 접근을 모두 다뤄본 근거가 된다.

### 3.1 관측과 추정의 구분

| 분류 | 의미 | 이 프로젝트에서 |
| --- | --- | --- |
| `observed` | 실제로 관측된 근거 | 입력 사진, 그리고 실측 3D 스캔을 확보한 경우 그 스캔 |
| `ai_inferred` | AI가 추정한 영역 | 생성된 3D 전체, 모델이 채운 결손부, MCP가 다듬은 부분 |

- 생성 모델이 만들었든 MCP가 만들었든 **모두 `ai_inferred`로 묶는다.**
- 사람이 손댄 부분도 별도 분류하지 않는다. 단, 사람이 수정했다는 사실은 기록에 남긴다.
- **① 단계가 항상 `ai_inferred`인 것은 아니다.** 실측 스캔을 확보한 유물은 ①이 `observed`다.
  이 경우 ①에 추정 문구를 붙이면 오히려 틀린 표시가 된다 (`NFR-ETH-003`).
  분류는 유물·단계마다 `manifest`의 `provenance`가 정하고, UI는 그 값을 그대로 따른다.

## 4. 사용자와 시연 상황

### 4.1 시연 상황

**심사위원 발표.** 운영에 최소 3명이 붙는다.

| 역할 | 하는 일 |
| --- | --- |
| **발표자** | 발표 진행, 설명 |
| **시연자** | 헤드셋을 착용하고 VR 안에서 조작 (필요 시 교대) |
| **화면 구성자** | 미러링 화면 송출, 장비 상태 확인, 백업 영상 대기 |

**이 결정이 우선순위에 미치는 영향**

| 항목 | 판단 |
| --- | --- |
| VR 초심자 온보딩 | **핵심 게이트 아님.** 시연자는 숙련 사용자다 |
| 미러링 화면 가독성 | **최우선.** 심사위원은 화면으로만 본다 |
| 복원 단계 전환의 시각적 임팩트 | **최우선.** 화면으로 봤을 때 차이가 명확해야 한다 |
| 시연 3회 연속 무사고 | **최우선 유지.** 발표는 한 번뿐이다 |
| 착용·교대 절차 | 시연자가 바뀔 때 흐름이 끊기지 않아야 한다 |

### 4.2 사용자

| 사용자 | 목적 | 제공할 경험 |
| --- | --- | --- |
| 시연자(관람객 역할) | 복원 단계와 근거를 보여준다 | 공간 이동, 유물 잡기·회전, 복원 단계 토글, 근접 정보 확인 |
| 제작자(팀원) | 유물 자산을 만들고 검수한다 | 생성 → 모델 복원 → MCP 복원 파이프라인, 자산 검사, 목록 등록 |

### 4.3 관람 흐름

```text
앱 시작
→ 전시 공간 입장 (선택·배치 단계 없음)
→ 걸어다니며 전시된 유물 사이를 이동
→ 유물에 가까이 가면 정보 패널 자동 표시
→ 유물을 잡아 회전하며 관찰
→ 복원 단계 토글 ① 손상 → ② 모델 복원 → ③ MCP 복원
→ 설명·출처·한계 확인
```

> **같은 자리에서 바뀐다.** 유물을 여러 개 늘어놓고 비교하는 방식이 아니라,
> **한 유물이 그 자리에서 단계별로 변하는** 방식이다. 변화가 눈앞에서 일어나야 극적이다.

### 4.4 제작 흐름

```text
입력 확보 (출처·라이선스 확인)
→ 3D 생성 — 손상 상태 3D
→ 3D 복원 모델 적용 — 모델 복원 상태
→ Claude Blender MCP 적용 — MCP 복원 상태
→ 경량화·재질 정리
→ 자산 검사 (파일·메시·예산)
→ 팀원 1명이 눈으로 검수
→ 유물 목록 등록
→ UE5 반입
→ APK 빌드·실기 확인
```

## 5. 범위

### 5.1 MUST — 최종 시연 전 반드시 완료

| ID | 범위 | 담당 직군 |
| --- | --- | --- |
| **N-01** | 입력에서 3D를 생성하는 파이프라인 1건을 다른 팀원이 문서만 보고 재현 가능 | AI |
| **N-02** | 3D 복원 모델과 Blender MCP로 각각 복원한 결과를 만든다. 프롬프트·작업 로그·전후 스냅샷 보존 | AI |
| **N-03** | 유물마다 관측과 AI 추정을 구분 표시하고 출처·생성 방식·한계를 기록 | AI · FE |
| **N-04** | **Oculus Quest 2**에서 실행되는 빌드와 전시 공간 1개 | VR · Infra |
| **N-05** | 유물 3점을 고정 전시 | AI · VR |
| **N-06** | 컨트롤러로 이동·잡기·회전·놓기 수행 | VR |
| **N-07** | 유물 근접 시 정보 패널 자동 표시 | FE · VR |
| **N-08** | **복원 3단계 토글**과 설명·근거 텍스트 표시 | FE |
| **N-09** | **PC VR 방식으로 시연 가능** (아래 주석 참조) | VR · Infra |
| **N-10** | 시연 시나리오 3회 연속 무사고 + 미러링 화면 가독 확보 | 전원 |

> **N-01 확인 사항.** 사진만으로 3D 복원이 가능한지 아직 검증되지 않았다.
> W1 게이트 G3에서 확인하고, 안 되면 실측 3D 스캔을 입력으로 쓴다 (U-02).
>
> **N-05 구성.** 복원 대상은 **소형 유물**로 한정한다 (토기, 검 등).
> 파이프라인은 **토기로 먼저 관통**하고 다른 종류를 뒤에 추가한다.
> 종류를 못 늘리면 같은 종류로 3점을 채워 MUST를 지킨다.
>
> **N-09 PC VR.** 시연은 **PC에 연결한 상태**로 진행한다. PC가 렌더링을 담당하므로
> 헤드셋 단독 실행보다 그래픽 품질을 높일 수 있다.
> **환경 제약(시연장 배선·PC 반입 등)이 생기면 헤드셋 내부 빌드로 전환한다.**
> 이 경우 그래픽 사양을 낮추는 trade-off를 감수한다. 두 방식 모두 W1에 확인한다.

### 5.2 SHOULD — MUST 완료 후

- 손 추적(맨손 잡기·UI 선택)
- 전시 유물을 5점까지 확대
- **복원 영역을 분리해서 표시** — 어느 부분이 채워진 것인지 색·패턴 등으로 구분
- 손상 3D 스캔 입력 경로 — *W1 데이터 판단(G2) 결과에 따름*
- 복원 단계 전환 트리거 다양화 — 버튼 외에 동작 기반 트리거

### 5.3 MAY — 여유가 있을 때만

- **공간 이동** — 전시 공간을 여러 개 두고 이동
- 전시 유물 6점 이상
- 조명·테마 전환
- 양손 확대·축소
- 웹 프론트엔드·API 서버

### 이번 범위에서 다루지 않는 것

- 모든 종류의 유물을 처리하는 범용 자동 복원
- 대규모 모델 신규 학습, 헤드셋 내부 실시간 AI 생성
- 유물 선택·배치·저장 같은 개인 큐레이션 기능
- 허공 드로잉과 스케치 인식으로 유물을 소환하는 인터랙션
- 멀티플레이, 계정, 클라우드 동기화
- 물리적 문화재 개입, 3D 프린팅 적합성 보증

> 생성 결과를 고고학적으로 검증된 원형이라고 주장하지 않는다. 관련 요구사항은 `NFR-ETH-001~004`를 따른다.

### 6.2 직군별 상세

**AI**

- 3D 생성 모델(2D→3D 등)을 찾고 튜닝한다.
- **Blender MCP만 쓰지 않는다.** MCP를 사용만 하면 학습이 되지 않으므로,
  **3D 복원을 수행하는 모델을 별도로 찾아 공부하고 MCP 결과와 비교한다.**
  이 비교가 3장의 복원 2단계(②모델 복원 / ③MCP 복원)를 만든다.
- 생성한 모델은 **원본 그대로 VR에 넘긴다.** 경량화 정도는 VR 쪽 요구에 맞춘다.

**VR**

- 사용자가 무엇을 할 수 있는가에 대한 책임. 잡기, 회전, 이동, 단계 전환의 동작.
- 씬 구성, 성능, 실기 빌드.

**FE**

- 사용자에게 무엇이 보이는가에 대한 책임. 정보 패널, 문구, 배치, 대비, 폰트.
- 미러링 화면에서의 가독성이 최종 판정 기준이다.

**Infra**

- 언리얼 빌드가 필요하면 그 스크립트를 만들고 자동화 파이프라인을 관리한다.
- GitLab 관리 — 브랜치, 권한, 저장소 구조.
- **3D 데이터와 자료 정리** — 원본을 모아 저장하고 팀이 찾을 수 있게 한다.
- **배포 대상이 없으므로 CI/CD는 구축하지 않는다.** 필요해지면 그때 결정한다.

### 6.3 협업 경계

- AI가 만든 모델은 자산 검사와 팀원 1명의 눈 검수를 통과해야 UE5에 들어간다.
- **AI는 생성된 모델의 원본을 제공하고, VR이 필요한 만큼 가공한다.**
  AI가 미리 경량화해서 넘기지 않는다. 어디까지 줄일지는 실기 성능이 정한다.
- AI와 VR은 W1에 **단위·축·pivot·재질 계약**을 함께 확정한다.
- VR·FE·Infra는 매일 같은 기기에서 빌드를 확인한다.
- **W3 종료 후 새로운 MUST를 추가하지 않는다.**

## 7. 4주 일정

W1부터 직군별 트랙으로 진행한다. 단 **W1의 4개 결정 게이트는 직군을 넘어 최우선**이며,
게이트가 실패하면 해당 트랙을 즉시 멈추고 fallback으로 전환한다.

# 2부. 요구사항과 수용시험

1부에서 정의한 목적·범위는 반복하지 않는다. 이 부의 표가 개별 기능의 완료 판정 기준이다.

## 11. 입력 요구사항

### 11.1 사진 입력

| 항목 | 요구 |
| --- | --- |
| 포맷 | PNG 또는 JPEG, sRGB |
| 해상도 | 짧은 변 512 px 이상, 권장 1024 px 이상 |
| 피사체 | 한 장에 유물 1개, 외곽이 잘리지 않고 화면의 60~90% 차지 |
| 대상 유형 | **소형 유물** — 토기, 검 등 단일 개체. 건축물·대형 석조물은 제외 |
| 배경 | 투명 또는 단색·단순 배경 |
| 시점 | 정면 또는 3/4 시점. 강한 원근·반사·모션 블러는 거부 |
| 출처 | 출처와 라이선스가 확인된 것만 사용 |
| 의미 | **사진에 보이지 않는 면은 모두 AI 추정으로 분류** |

> **사진만으로 3D 복원이 되는지는 아직 검증되지 않았다 (U-02).** W1 게이트 G3에서 확인한다.
> 형태별로 난이도 차이가 크다 — 회전대칭 토기류는 비교적 안정적이지만
> 얇고 긴 금속 유물(검 등)은 검신이 뭉개지고 금속 반사가 품질을 떨어뜨린다.
> 또 사진만으로는 실물 크기를 알 수 없어 전시 크기의 근거를 검수자가 기록해야 한다.

### 11.2 3D 스캔 입력 (조건부 — G2 결과에 따름)

| 항목 | 요구 |
| --- | --- |
| 포맷 | STL, OBJ 또는 PLY |
| 단위 | mm 또는 m를 manifest에 필수 명시 |
| 원본 보존 | 입력 파일 SHA-256 기록, 읽기 전용 디렉터리에 보존 |
| 거부 조건 | 빈 메시, NaN/Infinity 좌표, 단위 불명, 라이선스 불명 |

## 12. 기능 요구사항

### 12.1 자산 제작 — AI 직군

| ID | 우선순위 | 요구사항 | 수용 기준 |
| --- | --- | --- | --- |
| FR-AI-001 | MUST | 입력에서 3D 후보를 생성해야 한다 | 고정 입력 2건 중 1건 이상에서 비어 있지 않은 메시와 텍스처를 가진 GLB가 생성된다 |
| FR-AI-002 | MUST | 부적합한 입력을 명시적으로 거부해야 한다 | 해상도·포맷·메시 유효성 검사가 자동화되고 실패 사유가 출력된다 |
| FR-AI-003 | MUST | **3D 복원 모델로 결손부를 채운 모델**을 만들어야 한다 | 손상 상태와 모델 복원 상태 두 파일이 각각 존재하고 렌더 가능하다 |
| FR-AI-004 | MUST | **Blender MCP로 복원한 모델**을 만들어야 한다 | MCP 복원 상태 파일이 존재하고 렌더 가능하다 |
| FR-AI-005 | MUST | 복원 과정을 추적 가능하게 기록해야 한다 | MCP는 프롬프트 전문·호출 로그·전후 스냅샷, 모델 복원은 모델명·버전·설정·지표가 보존된다 |
| FR-AI-006 | MUST | 원본 입력을 덮어쓰지 않아야 한다 | 처리 전후 입력 파일 해시가 일치하고 출력은 별도 디렉터리에 생성된다 |
| FR-AI-007 | MUST | 자산마다 출처·라이선스·생성 방식·한계를 기록해야 한다 | manifest에 해당 필드가 모두 있고 하나라도 없으면 검사가 실패한다 |
| FR-AI-008 | MUST | **생성 모델의 원본을 VR에 제공해야 한다** | 경량화 이전 원본과 전시용 모델이 각각 존재하고 면 수가 기록된다 |
| FR-AI-009 | MUST | 전시 유물 3점을 완성해야 한다 | 3점 모두 자산 검사와 눈 검수를 통과하고 실기에서 렌더 확인된다 |
| FR-AI-010 | SHOULD | 전시 유물을 5점까지 확대해야 한다 | 2점이 추가로 승인된다 |
| FR-AI-011 | SHOULD | 3D 복원 모델과 MCP 결과의 차이를 정리해야 한다 | 두 방식의 지표·소요 시간·품질 관찰을 비교 기록으로 남긴다 |

### 12.2 VR 앱 — VR 직군

| ID | 우선순위 | 요구사항 | 수용 기준 |
| --- | --- | --- | --- |

# 3부. 구현 명세

이 부는 구현자가 공유해야 하는 파이프라인과 데이터 계약만 담는다.
세부 파라미터와 명령행은 실제 코드와 config가 최종 권위다.

## 17. 구현 원칙

1. **제작은 PC에서, VR은 렌더링만 한다.**
   3D 생성, 모델 복원, MCP 복원, 경량화는 모두 제작 PC에서 미리 끝낸다.
   VR 앱은 완성된 파일을 불러와 보여주기만 한다. **앱 안에서 AI를 돌리지 않는다.**
2. **원본을 덮어쓰지 않는다.** 모든 단계의 결과를 새 파일로 남긴다.
   나중에 "이 단계에서 뭐가 달라졌나"를 되짚을 수 있어야 한다.
3. **관측과 추정을 구분해서 저장한다.** 파일과 기록 양쪽에서 구분한다.
4. **작은 것부터 끝까지 연결한다.**
   W2 안에 입력 1건이 헤드셋 화면에 뜨는 것까지 관통시킨 뒤 콘텐츠와 기능을 늘린다.
   기능을 많이 만드는 것보다 **끊기지 않는 경로 하나**가 먼저다.
5. **AI는 원본을, VR은 가공본을 다룬다.**
   AI 직군은 생성한 모델을 **줄이지 않고 원본 그대로** 넘긴다.
   VR 직군이 실기 성능을 보고 필요한 만큼 줄인다.
   미리 줄여서 넘기면 나중에 품질을 되돌릴 수 없다.
6. **XR 입력 체계는 하나만 쓴다.** 두 SDK를 섞지 않는다.
7. **성능 한계는 자산을 만들 때 지킨다.**
   헤드셋에서 느려진 뒤 고치는 방식은 쓰지 않는다.

## 18. 시스템 구성

```text
📷 입력 (사진 또는 실측 스캔)
   │  ※ 관측 근거
   ▼
[3D 생성]  생성 모델
   │
   ▼
🗿 ① 손상 상태 3D
   │
   ├─────────────────────┐
   ▼                     ▼
[3D 복원 모델]      (② 결과를 입력으로)
   │                     │
   ▼                     ▼
🔧 ② 모델 복원      [Claude Blender MCP]
                          │
                          ▼
                     ✨ ③ MCP 복원
   │
   ▼
[경량화·재질 정리]  ← VR 직군이 실기 성능 보고 결정
   │
   ▼
[자산 검사]  파일 · 메시 유효성 · 면 수 · 텍스처 예산
   │  실패 → 되돌아감
   ▼
[팀원 1명 눈 검수]
   │
   ▼
[유물 목록 등록]  →  [UE5 반입]  →  [빌드]  →  [실기 확인]
```

> **③의 입력.** MCP 복원을 ①에서 시작할지 ②에서 이어갈지는 W2에 실제로 해보고 정한다.
> ②를 이어받으면 단계가 누적돼 비교가 자연스럽고, ①에서 시작하면 두 방식을 독립 비교할 수 있다.

#### 21.1.1 전시 공간 설계

**공간 구조 — `D-54` (2026-09-09 확정)**

```text
메인 홀 (시작 지점 · 로비 · 안내 패널)
 ├─ 포털 ⇄ 테마관 A  (유물 A)
 ├─ 포털 ⇄ 테마관 B  (유물 B)
 └─ 포털 ⇄ 테마관 C  (유물 C)      ← MUST N-05 유물 3점 = 테마관 3개
```

| 항목 | 결정 | 근거 |
| --- | --- | --- |
| 구성 | **메인 홀 1 + 테마관 N** — 유물 1점 = 테마관 1개 | 유물마다 시대·재질·용도에 맞는 분위기를 따로 잡는다. 한 방에 3점을 두면 조명·마감 규칙(21.1.2)이 서로 충돌한다 |
| 시작 지점 | **메인 홀** | 홀 → 안내 → 테마관 선택. 21.1의 "메뉴 화면 없음"은 유지된다 — 선택은 공간 안에서 포털로 한다 |
| 방 사이 이동 | **포털 텔레포트만.** 홀 ⇄ 테마관 양방향, 도착 지점·방향 고정 | 방 사이를 걸어 다니게 하면 통로가 생기고, 통로는 아래 "빈 공간을 만들지 않는다"에 어긋난다. 연속 이동(`D-46`)은 홀·테마관 **내부**에만 적용한다 |
| 포털 도착 지점 | **짝 포털을 이미 빠져나온 자리** — 관람자의 **머리**가 짝 포털 면에서 도착 공간 쪽으로 **1 m** 나온 지점에, 공간 안쪽을 바라보는 방향으로 놓인다. 테마관 도착은 유물 정면 **2.8 m**(방→홀 포털을 유물 정면 3.8 m에 세운다). **홀 도착만 예외로 홀 한가운데 (350, 0)** — 사방 3.4 m 이상 비어 있는 유일한 지점이다 | 폰 원점이 아니라 **HMD(머리) 위치·시선 기준**으로 옮긴다. 처음엔 게이트 30 cm **뒤**에 두어 한 걸음 걸어 나오게 했으나, **메타 버튼 뷰 리센터**가 트래킹 원점을 초기화하면 관람자가 폰 원점으로 순간이동해 게이트 안이나 벽에 서 버렸다 — 도착 지점 자체를 게이트 밖으로 옮겨 해결했다(2026-09-10). 게이트 앞 1 m는 발동 반경 70 cm 밖이라 되튀지 않는다. **도착 지점은 사방 2 m 이상 비어 있어야 한다** — 리센터가 보내는 폰 원점까지의 거리는 관람자가 플레이 공간에서 얼마나 걸었는지에 달려 예측할 수 없다. 페이드는 0.08 s/0.12 s |
| 포털 발동 | 머리가 **걸어서** 포털 중심 반경 70 cm 안으로 들어온 순간만 발동한다. 한 틱에 3 m 이상 움직여 들어온 경우(포털 도착, 텔레포트 착지)는 발동하지 않는다 | 도착 직후 짝 포털이 되받아 보내는 것을 막는다. 나온 포털로 되돌아가려면 반경 밖으로 한 걸음 나갔다가 다시 들어가면 된다 |
| 포털 전환 | 짧은 페이드(약 0.2~0.3 s) 후 위치 전환 | 화면이 그대로 바뀌면 멀미와 방향 상실을 부른다 |
| 레벨 구조 | **퍼시스턴트 레벨 = 메인 홀, 테마관마다 서브레벨 `.umap` 1개** | `.umap`은 LFS `lockable`이라 한 파일은 한 사람만 편집한다. **서브레벨 = 락 단위 = 담당자 단위** |
| 스트리밍 | 처음에는 **항상 로드**. 테마관은 서로 보이지 않게 충분히 떨어뜨려 배치 | PC VR(`N-09`)에 방 3개는 예산 안이다. 내부 빌드로 전환하면 포털 진입 시 로드로 바꾼다 |
| 메인 홀 | 안내 패널 **5장을 튜토리얼 동선**으로 배치 — ① 환영·전시 소개 ② 이동 ③ 손 조작 ④ 관람 ⑤ 포털 안내. 시작점에서 포털까지 좌우로 번갈아 놓아 순서대로 읽으며 나아간다. **AI 복원 고지(`NFR-ETH-003`)는 ①·⑤번에만** 둔다 — 생성물 바로 옆인 테마관 유물 패널이 요건을 충족하므로, 조작을 설명하는 ②③④에 같은 문장을 반복하지 않는다(`D-56`). 본문은 제목 + 1~2줄로 줄이고 설명은 3D 픽토그램이 맡는다. **유물 실물은 두지 않는다** | 관람 집중은 테마관에서. 홀에 유물을 두면 테마관에 갈 이유가 사라진다 |

- **유물 식별은 방 단위로 한다.** `Artifact` 태그를 레벨 전체에서 찾는 현재 구현은 유물이 2점 이상이면
  버튼 하나가 모든 유물을 토글하고 복귀 로직이 남의 방 유물을 끌어온다. `BP_StageToggle`·`BP_HandGrab`은
  자기 테마관의 유물만 대상으로 고친다.
- 홀은 공용 파일이다. 홀을 고칠 때는 미리 공유하고, 테마관은 담당자가 서브레벨 락을 잡고 작업한다.

**테마관 내부 — 초안값.** 2026-09-08 프로토타입(현 `L_Museum` 단일 방)에서 배치해 본 값이며, 이 방이 테마관 A의 원형이 된다. 실기 검증 후 조정한다.

| 항목 | 값 | 근거 |
| --- | --- | --- |
| 테마관 | 약 10 × 11 × 4 m, 닫힌 단일 공간. **출입은 포털만** | 통로·빈 방을 두면 시선과 동선이 분산된다 |
| 포털 도착 지점 → 유물 | **2.0~2.2 m** | 26~39 cm 유물이 알아볼 만한 크기로 보이는 거리. 3.5 m는 너무 멀다 |
| 좌대 | 지름 약 46 cm · 높이 **110 cm** | 유물 중심이 성인 눈높이보다 약간 아래 |
| 유물 뒤 배경 | 불투명 배경벽 (약 4.4 × 3 m) | 유물 뒤가 뚫려 있으면 실루엣이 어둠에 묻힌다 |

| 정보 패널 | 유물 옆, 중심 높이 **약 140 cm** | 21.3의 앵커 규칙을 따른다 |

- **빈 공간을 만들지 않는다.** 관람객이 갈 곳이 없는 방·조명 없는 통로는 동선만 흡수한다.

#### 21.1.2 조명

유물은 표면 요철(빗살무늬 등 음각)이 정보의 대부분이다. **수직으로 내리꽂는 조명은 이 요철을 지운다.**

| 광원 | 역할 | 초안 값 |
| --- | --- | --- |
| 키 | 유물 요철을 드러내는 **사광** | 정면 위 약 45°, 좁은 콘, 난색 |
| 림 | 유물을 배경에서 분리 | 반대편 뒤, 키의 1/3 이하, 한색 |
| 필 | 공간이 완전한 암흑이 되지 않게 | 약한 세기 여러 개, 그림자 없음 |
| 조작부 | 버튼을 찾을 수 있게 | 좁은 콘, 약한 세기 |

- **키 광원을 수직으로 두지 않는다.** 사광이라야 음각에 그림자가 생긴다.
- 실내 마감은 저채도 어두운 색으로 두고 유물만 밝게 남긴다. 다만 벽이 완전한 검정이면
  기기 화면에서 뭉개지므로 최소한의 계조를 남긴다.
- 조명 수치를 만지기 전에 **22.2.1의 노출 고정을 먼저 적용한다.**

### 21.2 유물 상호작용 상태

```text
전시대 → 강조 → 잡힘 → 복귀중 → 전시대
                 └─추적 손실──┘
```

- 한 번에 한 손만 한 유물을 잡는다.
- 잡은 상태에서 이동이 시작되면 안전하게 놓고 복귀 상태로 간다.
- 복귀 중에는 새 잡기를 막고 0.5초 이내에 전시대 위치로 돌아간다.
- 유물은 kinematic으로 다룬다. **투척 속도를 적용하지 않는다.**
- **손을 뗀 순간 반드시 복귀 상태로 간다.** 놓은 자리에 그대로 멈추면 안 된다.
  복귀가 없으면 관람객이 유물을 옮겨 놓고 떠나 다음 관람객의 전시가 깨진다.
- 복귀 트리거는 세 가지다 — 놓기 · 추적 손실 · 잡은 채 이동 시작.
  **잡기를 막는 것으로 이 문제를 해결하지 않는다.** 잡고 돌려보는 것이 24장 완료 체크 항목이다.

### 21.3 근접 정보 UI

| 항목 | 규칙 |
| --- | --- |
| 트리거 | 유물 중심으로부터 일정 거리 안에 들어오면 표시 |
| 트리거 반경 | 표시 **1.8 m** / 해제 **2.6 m** (초안, U-10) — 전시대 간격과 함께 W2에 확정 |
| 동시 표시 | **가장 가까운 유물 1개만** 표시한다 |
| 이탈 | 반경을 벗어나면 사라진다. 반복 깜빡임을 막는 여유 구간을 둔다 |
| 위치 | 유물 옆 고정 앵커. 사용자를 향하도록 회전 |

> 걸어다니며 이동하므로 유물 사이를 빠르게 지나갈 수 있다. 패널이 깜빡이지 않도록
> 표시·해제 거리를 다르게 두는 것이 필요하다.

**깜빡임을 막는 방법은 거리 비교가 아니라 상태 전이다.** 매 프레임 거리와 임계값을
비교해 표시 여부를 정하면 경계에서 반복 점멸한다. 진입·이탈 **에지에서만** 상태를 바꾼다.

```text
표시중 아님 + 거리 < 표시반경   → 표시한다 (상태 = 표시중)
표시중     + 거리 > 해제반경   → 숨긴다   (상태 = 표시중 아님)
그 외                          → 아무것도 하지 않는다
해제반경 > 표시반경
```

이 규칙은 단계 전환 버튼 등 **근접으로 발동하는 모든 상호작용에 똑같이 적용한다.**
쿨다운만으로는 막지 못한다. 손을 대고 있는 동안 쿨다운 주기마다 계속 재발동한다.

### 21.4 복원 단계 표시

| 단계 | 표시 | 우선순위 |
| --- | --- | --- |
| ① `Damaged` | 손상 상태 3D | MUST |
| ② `ModelRestored` | 3D 복원 모델이 채운 상태 | MUST |
| ③ `MCPRestored` | Blender MCP가 다듬은 상태 | MUST (G4 실패 시 제외) |
| `RegionHighlight` | 채워진 영역을 색·패턴으로 강조 | SHOULD |

- 토글은 미리 로드해둔 세 모델의 표시를 전환한다. **전환할 때 파일을 새로 읽지 않는다.**
  - 구체적으로 — 단계마다 메시 컴포넌트를 하나씩 두고 **Visibility만 전환**한다.
  - **런타임에 `SetStaticMesh`로 메시를 갈아끼우지 않는다.** 자산 참조를 데이터에서 읽어
    오더라도 마찬가지다. 처음 보이는 순간 셰이더·PSO 컴파일이 일어나 전환이 끊긴다.
    이 끊김은 관람객이 복원 결과를 처음 보는 바로 그 순간에 발생한다.
- 현재 몇 단계인지 항상 화면에 보인다.
- 단계와 무관하게 **"AI 기반 복원 가설" 문구는 항상 표시**한다.

### 21.5 입력 매핑

| 사용자 행동 | 컨트롤러 (MUST) | 손 추적 (SHOULD) |
| --- | --- | --- |
| 이동 | 썸스틱 — **연속 이동** | 해당 없음 |
| 회전 | **헤드셋을 돌린다** (별도 입력 없음) | 동일 |
| UI 가리키기 | 레이 | 레이 |
| 선택 | 트리거 | 핀치 |
| 유물 잡기 | 그립 | 근접 핀치 |
| 유물 회전 | 컨트롤러 자세 | 손 자세 |
| 놓기 | 그립 해제 | 핀치 해제 |
| 복원 단계 전환 | 좌대 전면 버튼에 손을 가져간다 (근접) | 동일 |

- 복잡한 커스텀 제스처는 넣지 않는다.
- 손 추적을 구현하는 경우, 컨트롤러와 동시에 인식되면 마지막으로 입력한 장치를 활성으로 둔다.
- **단계 전환은 근접 하나로 통일한다.** 근접·그립·오버랩을 동시에 살려두면 한 번 누른 것이
  두 번 처리되고, 컨트롤러와 손 추적의 동작이 달라진다. 판정은 21.3의 에지 전이 규칙을 따른다.

> **VR 템플릿 기본값을 그대로 쓰지 않는다.** UE VR Template은 텔레포트 이동과 스냅 턴이
> 켜진 채로 생성된다. `D-46`은 **연속 이동 + 시선 회전**을 택했으므로 둘 다 꺼야 한다.
> 프로토타입 단계에서 이 차이를 넘기면 나중에 이동 동선 전체를 다시 잡게 된다.
>
> `D-46`이 감수하기로 한 멀미 위험은 **이동 거리를 줄여** 낮춘다. 21.1.1이 포털 도착 지점을
> 유물에서 2 m로 둔 이유가 이것이다. 관람의 대부분이 제자리에서 이루어지면 연속 이동의
> 노출 시간 자체가 줄어든다. 방 사이는 포털(`D-54`)이므로 연속 이동은 홀·테마관 내부로 한정된다.

#### 22.2.1 렌더링 경로 고정

**에디터에서 보는 화면과 헤드셋에서 보는 화면이 같아야 한다.** 아래 설정이 켜져 있으면
에디터는 PC 경로로 렌더하고 기기는 조용히 폴백하므로, 조명·재질을 맞춘 작업이 전부 헛일이 된다.

> **갱신 2026-09-10.** 실행 경로가 기기 단독이 아니라 **ALVR + SteamVR로 PC가 렌더**하는 방식으로 굳어졌다.
> "기기 폴백" 전제는 사라졌지만 VR 프레임 예산(72 Hz × 양안, 약 13.9 ms)은 그대로라 Lumen·하드웨어 RT·Substrate는
> 계속 끈다. 실사 품질은 **정적 조명 베이크 + 리플렉션 캡처 + 스캔 PBR 재질**로 낸다. 정적 전시 공간에서는 이 조합이
> 가장 싸고 가장 실사적이다.

| 설정 | 값 | 이유 |
| --- | --- | --- |
| `r.DynamicGlobalIlluminationMethod` | `0` (None) | Lumen은 VR 예산을 넘긴다. GI는 라이팅 빌드로 굽는다 |
| `r.ReflectionMethod` | `0` (None) | SSR·Lumen 반사 없음. **Sphere/Box Reflection Capture는 이 값과 무관하게 동작**하므로 홀·방마다 2~3개 둔다 |
| `r.RayTracing` | `False` | 예산 초과. GPU Lightmass 대신 CPU Lightmass를 쓴다 |
| `r.Substrate` | `False` | 이득 없이 셰이더 수만 늘린다 |
| 그림자 방식 | Shadow Maps (Virtual Shadow Maps 아님) | Forward 경로에서 무시된다 |
| 조명 모빌리티 | 구조·가구 **Static**, 키·주요 포인트 **Stationary**, 필·버튼 스팟 **Static** → **Build Lighting Only**로 굽는다 | 간접광·부드러운 그림자·AO가 베이크로 들어오고 런타임 비용은 줄어든다. 유물·손 같은 Movable에는 Stationary 키의 동적 그림자가 붙는다 |
| 라이트맵 해상도 | 바닥·천장 1024, 벽 2048, 가구 128~256 (메시 애셋의 `LightMapResolution`) | 기본값 64는 10 m 벽에서 얼룩진다. 배치된 `StaticMeshActor`의 컴포넌트 override는 거부되므로 **메시 애셋 쪽에 건다** |
| 임포트 메시의 UV | **UV0(재질용)·UV1(라이트맵용) 두 채널을 반드시 넣어 내보낸다** (`D-55`) | 표면 재질이 월드 정렬이라 재질용 UV는 안 쓰지만, **Lightmass는 UV 없이 굽지 못한다.** UE는 UV0을 소스로 라이트맵 UV를 만드는데 소스가 없으면 조용히 실패하고 그 메시만 스카이라이트만 받아 남색으로 보인다. 임포트 후 `LightMapCoordinateIndex`가 0이 아니면 정상 |
| 알베도 상한 | 밝은 재질도 **0.75 이하** | 흰 대리석을 1.0으로 두면 좁은 실내에서 바운스가 폭주해 베이크가 하얗게 날아간다. 실제 백대리석은 0.65 내외 |
| 조명 기구 메시 | `CastShadow=false` | 샹들리에 링·다운라이트 디스크가 자기 빛을 가려 천장이 새까맣게 나온다. 기구는 조명보다 위에 있는 경우가 많다 |
| 임포트 메시의 콜리전 | 건축물은 `BodySetup.CollisionTraceFlag = **CTF_UseComplexAsSimple**` | FBX 임포트는 콜리전을 만들지 않는다. 심플 프리미티브 0개 + `CTF_UseDefault` 면 **관람자가 벽을 통과한다.** 방 셸은 속이 빈 상자라 볼록 껍질을 씌우면 안 된다 — 삼각형 메시를 그대로 쓴다. `SceneTools.trace_world` 로 검증한다 |
| 프로토타이핑 메시 | `SM_Cube` 등은 **Nanite 끔** | Nanite + VSM 꺼짐 조합은 Stationary 라이트 그림자를 지원하지 않는다는 Map Check 경고가 뜬다 |
| 재질 | 스캔 PBR(Fab Quixel Megascans, 베이스컬러·노멀·러프니스·AO) | 노멀·러프니스 맵이 없으면 상자는 상자로 보인다. 프리미티브 기반 `MI_Lobby_*`·`MI_RoomA_*`는 부모만 교체한다 |
| `r.Mobile.AllowMovableSpotlightShadows` | 필요하면 `True` | **기본값이 꺼져 있다.** 끈 채로 두면 기기에서 접지 그림자가 사라진다 |
| 노출 | 무한 범위 PostProcessVolume으로 **고정** | 자동 노출은 고개를 돌릴 때 밝기가 출렁여 멀미를 유발한다 |

- `r.Substrate`와 `r.RayTracing`은 **에디터를 재시작해야 반영된다.** 설정만 바꾸고 계속
  작업하면 프로젝트 설정과 실행 중 렌더러가 어긋난 상태가 되고, 이 상태에서 겪은 증상은
  실제 문제와 무관할 수 있다. 바꾼 뒤 재시작하고 나서 판단한다.
- 조명 수치를 조정하기 전에 **노출을 먼저 고정한다.** 자동 노출이 켜져 있으면 조명을
  낮춰도 노출이 보상해 화면이 변하지 않는다.

## A.1 엔진·기기 — U-01, U-11 관련

**김소영** — UE 5.8.1 기준 포팅 가이드 4편 작성 중

| 문서 | 내용 |

| `unreal-vr-build-management.md` | 두 기기 전환과 빌드 분리 |

조사된 내용:

- 기준 엔진을 **UE 5.8.1**로 잡고 문서를 작성했다.
- **UE 5.8에 PICO 기본 지원이 들어갔다**는 PICO 공식 안내를 확인했다.
- 도구 조합 후보: Android Studio Koala Feature Drop 2024.1.2 Patch 1, SDK API 35,
  Build-Tools 35.0.1, NDK r27c(27.2.12479018), JDK OpenJDK 21.0.3(Koala `jbr`)
- 플러그인 구성 후보: PICO 4는 엔진 OpenXR + 외부 **PICO For OpenXR**,
  Quest 2는 엔진 OpenXR 단독. 구형 PXR 계열은 사용하지 않음.
- 기기별로 패키지명·출력 폴더를 분리하고 **처음에는 한 번에 한 기기만 빌드**하는 방식을 제안.
- 알려진 리스크: UE 5.6에서 PICO OpenXR 빌드 시 `xmlns:android` 중복 속성으로
  Manifest 생성이 실패한 개발자 보고가 있다. **5.8.1에서 동일한지는 확인되지 않았다.**

> **미검증 상태.** 문서 자체에 "실제 PC·헤드셋 실행 검증 전"이라고 명시돼 있다.
> UE 5.8.1을 엔진 버전으로 확정하지 않는다. **G1 게이트는 여전히 열려 있다.**
> 다만 이 조사 덕분에 G1 스파이크의 절차와 도구 버전 후보가 이미 준비된 상태다.

## A.2 손 추적 — D-07 관련

**김신정** — 핸드트래킹 기술 스택 조사

- OpenXR 기반으로 Quest 2·PICO 4 공통 로직을 작성하는 방향을 검토.
- 핀치 판정을 OS별 pinch-strength 값에 의존하지 않고
  **엄지-검지 손끝 거리 계산으로 직접 처리**하는 안. 플랫폼 무관하다는 것이 이유.
- 궤적 시각화에 UE5 내장 **Niagara Ribbon** 사용 검토.
- 난이도 평가: 기본 손 인식은 쉬움, 핀치·궤적 로직은 중간,
  **트래킹 노이즈 스무딩이 가장 시간을 많이 쓰는 구간**이라는 판단.
- 마찰 요소로 정리된 것:
  - Meta XR SDK와 PICO OpenXR SDK가 UE 버전에 따라 충돌하는 사례가 흔함
  - OpenXR 표준이어도 기기별 관절 인덱스·신뢰도 값이 달라 분기 처리가 어느 정도 필요
  - PC 한 대에서 Quest 런타임과 PICO 런타임을 **동시에 활성 OpenXR 런타임으로 둘 수 없음**
- 참고 레포지토리 정리됨: Meta `Unreal-HandSample`/`Unreal-HandGameplay`,
  PICO `PICO_UE5_OpenXRSample`/`HandTracking`/`FeaturesDemo`, `open-brush`, `VRDraw`

> 명세의 D-07(컨트롤러 MUST, 손 추적 SHOULD)은 유지한다.
> 이 조사는 손 추적을 SHOULD로 구현할 때의 접근 방법을 미리 확보해둔 것이다.

## A.3 Blender MCP 복원 — U-05 / G4 관련

**김신정, 김채원** — 실제 사용 경험 보고

- 김신정: `blender-mcp`로 Claude가 `bpy`를 직접 호출해 자연어 지시로 지오메트리 복원이 가능하며,
  **"실제로 사용해본 결과 형태 복원은 결과물이 꽤 좋았음"** 이라고 보고.
- 김채원: **Blender 5.2.0 LTS + BlenderMCP(localhost:9876)** 연동 환경에서 작업 중.
- **확인된 한계:** `bpy`는 지오메트리와 머티리얼 노드는 다루지만
  **이미지 생성은 못 한다.** 즉 "원래 어떤 색이었을지"를 그려내는 **색상·풍화 복원에는 적용되지 않는다.**
- 색상 복원 대안으로 제시된 것: UV 텍스처 인페인팅 모델(Stable Diffusion 계열),
  또는 프로시저럴 머티리얼로 추정 복원 연출만 하는 절충안.

> **G4 게이트에 긍정적인 신호다.** 다만 팀 차원의 공식 검증 기록은 아직 없다.
> 그리고 **지오메트리 복원과 색상 복원은 서로 다른 종류의 AI가 필요한 별개 작업**이라는 점이
> 명세에 반영돼 있지 않다. 색상 복원을 범위에 넣을지 팀 결정이 필요하다.

## A.4 복원 대상 후보 — U-06 관련

현재 네 개의 대상이 각각 실험되고 있다. **어느 것도 주 사례로 확정되지 않았다.**

| 대상 | 데이터 | 담당 | 상태 |
| --- | --- | --- | --- |
| 빗살무늬토기 | `ssu022891-001-30000_Step3.stl` | 현은빈 | 자기지도 U-Net 복원, watertight 메시 출력 성공 |
| 토기 항아리 | `RR_07_01_EA_028.las` | 권영호, 장서진, 공세민 | 회전대칭 복원 / PoinTr 검증 |
| 석인상 | `RR_07_01_ST_075.las` | 김채원 | 전처리·메시 재구성 완료, **결손 복원 미수행** |

### 반드시 알아야 할 두 가지 발견

**① 석인상에는 복원할 결손이 사실상 없다 (김채원)**

> 경계 진단 결과 이 유물에는 복원해야 할 물리적 결손이 사실상 없으며,
> 메시의 구멍은 전부 스캔 사각이었다. 따라서 "결손 복원 전시"라는 당초 기획은 성립하지 않으며,
> 풍화 마모 복원 또는 스캔 사각 보완으로 방향을 바꿔야 한다.

- 1,329만 점에서 데이터 분포로 도출한 임계값만 써서 5.6%만 제거하고 메시 재구성.
- 부수 확인: 서역인 무인석으로 판독됨. 다만 **실측 3.227m와 공개 기록 2.57m가 26% 차이**나
  개체 지정은 보류 중.
- 전문가에게 물을 쟁점 목록을 정리해둠 (스캔 사각을 추정 생성해도 되는가, 이끼 제거 여부 등).

**② 토기 항아리는 하부 전체가 결실됐고 AI가 완형으로 오인한다 (장서진)**

- 테두리 규칙성을 측정한 결과, 위 구멍은 마감된 구연부이고 아래는 불규칙 파단면 →
  **대형 항아리의 어깨~구연부만 잔존한 상태.**
- PoinTr(ShapeNet-55 사전학습, 파인튜닝 없음) 결과: 잔존 부위 실루엣 재현은 성공(정합 오차 중앙값 3.5mm)했으나
  **결실된 하부로 연장된 출력점이 0점.**
- 원인 분석: "바닥 없는 돔"이 ShapeNet bowl 카테고리의 완형과 동형이라
  모델이 부분 항아리를 온전한 사발로 해석. **그릇류 prior 근접이 오히려 결손 인지를 방해.**
- 교훈으로 정리된 것: 형상 상식은 사전학습에 있으나
  **"이것이 전체인가 일부인가"는 형상만으로 판별 불가.**

> 두 발견 모두 **"손상 3D 복원"이라는 축 자체의 난이도를 보여준다.**
> 복원 대상을 정할 때 "결손이 실제로 존재하고, 그 결손이 AI로 다룰 만한 것인지"를
> 먼저 진단해야 한다는 것이 공통 결론이다. U-06 결정 시 반드시 반영한다.

## A.5 3D 복원 모델 — U-04 관련

| 접근 | 담당 | 결과 |
| --- | --- | --- |
| 자기지도 U-Net (원통 전개 inpainting) | 현은빈 | 합성 holdout MAE 0.1904mm, watertight 출력 |
| 회전대칭 기반 결손·색상 복원 | 권영호 | 가상 절단 평가에서 sqrt-Chamfer 2.2597mm (baseline 3.2160mm) |
| PoinTr (ShapeNet-55 사전학습) | 장서진 | 형상 재현 성공, 결손 복원 실패 (A.4 참조) |

- 권영호: 복원 결과를 LAS classification으로 구분 저장
  (원본 0 / 신규 채움 20 / 색 보정 21). **provenance 분리를 이미 실천하고 있다.**
  Poisson depth 9로 메시화, OBJ에 정점별 RGB 기록.
- 장서진: 색 복원 정책을 `conserved`(색만 복원, 명암·노멀맵 완전 보존)를 기본으로,
  `pristine`(균일 마감)을 옵션으로 정리. 재질 프리셋 7종, 처리 실적 10유물 기술명세서 작성.
- 장서진 다음 계획: 그릇류 파인튜닝 데이터셋 v0 (국립박물관 온전 스캔 12점에 합성 결손 생성),
  세그멘테이션 데이터셋 착수, Unreal 입문 후 복원 OBJ 임포트 검증.

> U-04(3D 복원 모델 선정)는 미정이다.
> 다만 **세 갈래 실험이 이미 상당히 진행돼 있어** 연구 트랙으로만 남기기에는 아까운 상태다.
> 권영호의 classification 기반 provenance 분리는 명세의 `observed`/`ai_inferred` 구분과 잘 맞는다.

## A.7 조사 내용의 반영 결과

김신정의 조사 문서는 명세와 다른 제품을 전제하고 있었다. 회의를 거쳐 아래처럼 정리됐다.

| 항목 | 조사 문서의 제안 | 결정 |
| --- | --- | --- |
| 핵심 인터랙션 | 허공 드로잉 → 스케치 인식 → 유물 소환 | **채택 안 함.** 관람형 + 근접 정보 UI 유지 |
| 실행 방식 | PC VR (PC가 렌더·추론) | **채택.** PC VR이 시연 기본 방식 (`N-09`) |
| 이동·회전 | — | **연속 이동 + 시선 회전으로 변경** (`FR-VR-004`, `005`) |
| 외부 추론 서버 | FastAPI 추론 서버 | **채택 안 함.** 앱 안에서 AI를 돌리지 않는다 |
| 손 추적 | 핵심 인터랙션 | SHOULD 유지 |

> 조사에서 정리된 참고 레포지토리와 구현 순서는 손 추적을 SHOULD로 구현할 때 그대로 쓸 수 있다.
