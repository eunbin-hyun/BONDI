# 1부. 금관 — 세 겹의 방향 문제와 "없다"던 색

금관 카드 세 장이 제각각이었다: 원본은 옆으로 눕고, 복원본은 거꾸로 서고, 에셋2는 옆을 보고 섰다.
한 유물인데 증상이 다 달랐다 — **원인이 세 겹이었기 때문이다.**

## 1.1 같은 기하, 다른 프레임 — 임포터가 좌표계를 바꾼다

원본(OBJ)과 복원본(GLB)에 같은 방향 설정을 줬는데 하나만 맞았다. 재 보니 Blender 임포터가 다르게 동작한다:

```text
OBJ 임포트   forward_axis=Y, up_axis=Z   → 좌표 변환 없음 (그대로)
GLB 임포트   Y-up → Z-up 자동 변환        → (x, y, z) → (x, −z, y)
```

**같은 기하라도 확장자가 다르면 override 값이 달라야 한다.** `orientation_overrides.json` 에
이 사실을 `_note` 로 박아 두고, 유물마다 축을 다시 쟀다. "한 번 맞춘 값을 복사하면 된다"는
가정이 확장자 하나로 무너진다.

## 1.2 up·flip 으로 부족했다 — yaw 추가

에셋2는 바로 섰는데 **옆을 보고** 섰다. 세로축은 맞고 세로축 둘레 회전이 틀린 것이라
up/flip 으로는 표현이 안 된다. 서버 미리보기에 `--yaw <도>` 를 추가했다
(`preview/rebuild?asset=…&yaw=90`). 방향 고정이 (up, flip) 2자유도에서 3자유도가 됐다.

## 1.3 "이 유물에는 색 데이터가 없다" — 틀렸다

금관이 계속 회색이었다. 나는 "스캔에 색이 없다"고 결론 내렸다. **틀렸다.**
출처를 따라가 보니 박물관 공식 패키지 안에 **18.95 MB 색 텍스처**(채도 40.7)가 멀쩡히 있었다.
우리 임포트가 알파 마스크(`_alpha.jpg`)를 디퓨즈(`_diffuse.jpg`) 자리에 저장한 것이었다.

교훈이 두 개다.

- **"없다"는 결론은 "어디까지 찾아봤다"와 함께여야 한다.** 나는 서버에 올라온 파일만 보고
  원본 패키지를 안 열었다.
- 파일 이름은 내용을 보증하지 않는다. `_diffuse.jpg` 라는 이름의 흑백 알파 마스크였다.

## 1.4 컷아웃 마스크 규칙 — 고치고, 과했고, 줄였다

금관 텍스처는 색이 아니라 **컷아웃 마스크**(뚫린 부분 표시)였다. 미리보기 생성에
"베이스컬러 이미지가 알파 이미지와 같고 무채색이면 → 색에서 떼어 알파에만 쓴다" 규칙을 넣었다.

첫 판은 과했다 — 판정 문턱이 낮아 **관의 투조(뚫린 장식)까지 지워 버렸다.** 채도 실측으로
문턱을 좁혀(`sat×255 < 2.0`) 두 번째 판에서 잡았다. 전수 규칙을 넣을 때는
**규칙이 잘못 발동한 사례**를 먼저 찾아봐야 한다.

# 2부. 화면·전달 속도 — 버그는 서버가 아니라 캐시에 있었다

## 2.1 "자꾸 옛날 파일이 뜬다" — 진짜 원인은 한 줄

새 복원본을 올려도 옛 모델이 보였다. 몇 주 동안 "Ctrl+Shift+R 하세요"로 넘겨 온 증상인데,
원인은 서버 응답 한 줄이었다:

```python
# preview-status 응답 — 여기만 ?v=수정시각 이 빠져 있었다
j["preview_url"] = "/" + row["preview_path"]        # 전 (버전 없음)
j["preview_url"] = _vurl(row["preview_path"])       # 후
```

nginx 가 `/preview/` 에 **7일 캐시**를 주므로, 버전 없는 URL 을 돌려주면 브라우저는
새로 만든 직후에도 옛 GLB 를 쓴다. 목록·카드 API 는 전부 `_vurl` 을 거치는데 이 응답만 빠져 있었다.
지난주 "전역 규칙" 교훈과 같은 결이다 — **버전 붙이기를 응답마다 하면 언젠가 한 곳을 빠뜨린다.**

## 2.2 체감 속도 — 로딩 막대와 선행 로딩

- 3D 로딩 막대: GLTFLoader 의 progress 콜백을 화면에 연결 (`viewer.js` `load(url, onProgress)`)
- 즐겨찾기 선행 로딩: 홈에 들어오면 즐겨찾기 GLB 를 미리 받아 두어 클릭 시 바로 뜬다
- 밝기 상한 2.4 → 5.0 + 휠 조절 — 어두운 유물 실측 요구에서 나옴

## 2.3 한글 라벨이 조용히 버려졌다

복원본 라벨 슬러그가 `[a-z0-9-]` 만 남기니 한글 라벨은 **빈 문자열**이 됐고, 서버는 라벨이
없다고 보고 기본 칸을 덮어쓰려 했다. 걸러서 비면 `ko-<해시6>` 슬러그를 준다.
"입력을 거른다"는 코드는 **거른 결과가 빈 값일 때**의 경로를 같이 설계해야 한다.

## 2.4 더 보기 버튼 — 기능은 멀쩡했고 스크롤이 문제였다

"더 보기가 이상하다"는 보고. 재 보니 로드는 175/175, 233/233 으로 중복 0 — 기능은 멀쩡했다.
문제는 클릭 후 버튼이 화면 밖 4,000px 아래로 밀리는 것. 새로 붙은 첫 카드로 스크롤을 옮기고
로드 중 버튼을 잠갔다. **"이상하다"는 보고는 기능·표시·이동 셋으로 쪼개 재현해야 한다.**

# 3부. ERS 양방향을 검증대에 올리다

지난주에 만든 ERS 양방향(투창 보존)을 "맞는지 확인해 달라"는 요청을 받았다. 만든 사람이
자기 코드를 다시 보는 것이라, **믿음 대신 정답지를 만들었다.**

## 3.1 합성 정답지 — 답을 아는 굽다리를 만든다

실제 유물은 정답을 모른다. 그래서 64³ 격자에 **투창 2단×4개 + 위로 열린 결손**을 심은
합성 굽다리바리를 만들었다 — 투창은 사방이 막힌 구멍, 결손은 위로 열린 틈. 8항목 전부 통과:

| 검사 | 결과 |
|---|---|
| 관측 복셀과 마스크 교집합 | 0 — ERS 의 1 고정과 충돌 없음 |
| 투창 검출 | **8/8** |
| 결손부 오염 | **0 복셀** — 열린 틈은 건드리지 않음 |
| 몸통 번짐 | 0 |
| 로짓 억제 후 점유 잔존 / 마스크 밖 보존 | 0 / 보존 |
| 해상도 불일치 통과 · fp16 유한성 | 통과 |

저자 코드도 대조했다 — `flow_euler.py:221` 의 `pred_voxel = (decoder(x_0) > 0.0)` 이
한쪽 방향인 것, 최종 추출(`trellis_image_to_3d.py:245`)이 **같은 디코더 객체**를 써서
억제가 끝까지 가는 것을 확인했다.

## 3.2 통과했는데 결함이 나왔다 — 잠복 결함

검증 중에 마스크 전역(`_KEEP_EMPTY_MASK`)이 **한 번 만들면 재생성되지 않는** 것을 발견했다.
지금 스크립트는 전부 프로세스당 유물 1개라 드러나지 않지만, 한 프로세스에서 두 유물을 돌리면
두 번째가 첫 번째의 마스크를 쓴다. 호출마다 새로 만들고, 만들다 실패해도 앞 마스크가 남지 않게
먼저 비우도록 고쳤다. **"지금은 안 터진다"와 "맞다"는 다르다.**

# 4부. 결 합성 실측 — 같은 표준편차가 다른 것을 잰다

지난주 결 합성의 "std [12.66, 12.80, 12.96] → 동일" 은 **적합 대상(원통 관측 이미지)** 기준이었다.
완성 GLB 로 다시 재니 채움 결이 원본 텍스처보다 +1.7~2.0 높게 나왔다 — 모순이 아니라
**두 측정이 다른 것을 잰 것**이다. 원본 1024² 와 채움 2048² 의 해상도 차이도 있어서,
고역 σ 를 변 길이에 비례시켜 같은 공간 대역으로 맞춘 뒤에야 비교가 성립했다:

| 산출물 | 결 std (R·G·B) | 평균 밝기 |
|---|---|---|
| 원본 실측 텍스처 (1024², σ6) | 10.83 · 11.17 · 11.02 | 127.8 · 118.1 · 99.3 |
| 채움 무보정 (2048², σ12) | 12.74 · 12.87 · 13.04 | **131.3 · 121.3 · 102.1** |
| 채움 ×1.12 (사이트 V4) | 14.27 · 14.42 · 14.60 | 146.6 · 135.4 · 113.8 |

무보정판은 톤이 원본과 **±3 안**이다. V4 의 ×1.12 는 수치를 맞추려는 게 아니라 표현상의
선택(살아있는 원본 조각 옆에서 어두워 보임)임을 문서에 명시했다 — 성능개선.md §3-4.
**해상도가 다른 두 이미지의 고역 통계는 σ 를 맞추기 전에는 비교가 아니다.**

# 5부. 손상 사진 전수 판정 — 키워드 38장, 눈으로 96장

발표 자료용으로 "손상된 유물 사진"이 몇 장인지 세야 했다.

## 5.1 첫 시도 — 설명문 키워드 검색은 반도 못 찾았다

`파손·결손·수리…` 키워드로 38장. 그런데 두 가지가 틀렸다: 경로 형태가 두 가지라 그룹핑이
233 → 133 으로 새고 있었고, **발굴 파편은 설명에 "파손"이라 쓰지 않는다**(파편이 정상 상태라서).
결국 233장을 전부 눈으로 봤다 — 96장. 일주일 전 독립 계수(95장)와 1장 차이로 일치했다.
**전수 판정은 두 번 세서 맞아야 숫자다.**

## 5.2 분류 기준을 바꿨다 — 인덱스가 아니라 형태

96장을 배치할 때 "명품 구간(인덱스 96~)"으로 나눴더니 96~99번이 여전히 토기 파편이었다.
인덱스는 **출처** 기준이지 **보이는 것** 기준이 아니다. "형태를 알아볼 수 있는가"로 다시 나누니
유물 50 / 무형 파편 46 — 줄마다 유물 6~7개가 고르게 깔리고 파편 최장 연속이 2칸이 됐다.
같은 데이터도 **무엇을 위해 나누는지**에 따라 축이 달라야 한다.

# 6부. 회전 점검 에이전트 — 절대 질문은 실패, 비교 선택은 3/3 ★

미리보기가 뒤집힌 사고가 반복됐다(1부의 금관, 이전의 굽다리·빗살무늬토기 — 수동 override 가
21개다). 그 확인을 사람 눈에서 에이전트로 옮기기로 했다. 제약: **무료**(로컬 Ollama Qwen2.5-VL 7B),
**고치지 않고 보고만**(판정 주체가 7B 라 최종 확인은 사람).

## 6.1 첫 설계는 실패했다 — "바로 섰나?"

썸네일을 주고 "바로 서 있나?"를 물었다. 옆으로 누운 청자기린장식향로에 **확신 0.95 로 "바로 섬"**
이라고 답했다. reason 도 프롬프트의 예시 문구를 앵무새처럼 되풀이했다. 질문을
"위쪽이 화면 어느 방향을 향하나"로 바꿔도 같았다 — 7B 에게 **절대 방향 판정은 무리다.**

## 6.2 질문을 바꾸니 같은 모델이 맞힌다 — 비교 선택

같은 그림을 **0/90/180/270° 돌린 네 장**을 주고 "바르게 선 것은 몇 번?"으로 바꿨다.

```text
누운 기린향로   → 4번 (시계 90°)   ← 탐지뿐 아니라 고치는 회전까지 정확
선 표주박 주자  → 1번 (원본)
선 금관        → 1번 (원본)                                  정답지 3/3
```

**모델을 바꾸지 않았다. 질문을 바꿨다.** 절대 판정은 못 해도 비교 선택은 하는 것 —
사람의 지각 실험에서도 흔한 성질인데, VLM 프롬프트에서 그대로 재현됐다.

## 6.3 에이전트 구조 — 애매하면 스스로 증거를 만든다

```text
지각    썸네일을 네 방향으로 돌려 보여준다 (회전은 WSL PIL)
판단    바른 번호 선택 — 1번(원본)이 아니면 문제
행동    모델이 고른 회전을 적용한 그림을 만들어 "이제 바로 섰나?" 재확인
재지각  그래도 애매하면 미리보기 GLB 를 받아 정면 렌더로 한 번 더
보고    콘솔 + JSONL(프롬프트 원문까지) + rebuild 명령 제안 — 실행은 안 한다
```

고정 파이프라인과 갈리는 지점은 **애매할 때 스스로 증거를 더 만들어 다시 보는 고리**다.
판단 기록은 D-19 의 재현성 규칙(프롬프트 전문 + 작업 로그) 그대로 JSONL 에 남는다.

등록 경로는 병존한다 — 일반 등록(웹 업로드)은 그대로 두고, `upload` 부명령은 올린 뒤
회전 점검까지 이어서 한다. 서버 코드는 한 줄도 바꾸지 않았다.

## 6.4 걸린 돌부리

- Ollama 기본 컨텍스트 4096 을 이미지 토큰이 넘는다(3000×2000 사진 실측 4.2k) → `num_ctx 16384`.
  오류가 겹따옴표로 감싸인 400 이라 원인이 바로 안 보였다.
- Windows 콘솔(cp949)에서 한글 출력이 죽는다 → `sys.stdout.reconfigure(encoding="utf-8")`.
- 라이브 read-only 점검 2건(굽다리바리 원본·복원본) 통과 후 dev 병합. 전수(175건) 오판율은
  측정을 걸어 두었다 — 결과는 README 에 적는다.
