# 1부. 화면 결함 네 가지 — 개별 가드 대신 전역 규칙

팀이 쓰기 시작하니 보고가 들어왔다. 네 가지를 고쳤는데, 그중 하나에서 배운 게 남는다.

| 증상 | 원인 | 고침 |
|---|---|---|
| 등록 시각이 9시간 어긋남 | 서버는 UTC, 보는 사람은 KST | 저장은 UTC 유지, 표시만 로컬 변환 |
| 목록에 같은 카드가 두 번 | 화면 전환 시 기존 목록을 안 비움 | 렌더 전 초기화 |
| 숨긴 항목이 가끔 보임 | 필터마다 가드를 따로 넣다 빠뜨림 | **전역 한 줄** |
| 최신 등록이 뒤에 묻힘 | 이름순 정렬 | `registered_at` 내림차순 기본 |

세 번째가 핵심이다. 처음엔 `hidden` 검사를 목록·검색·즐겨찾기마다 따로 넣었는데, 새 화면을 만들 때마다
빠뜨렸다. **"곳곳에서 검사한다"는 곧 "언젠가 한 곳을 빠뜨린다"** 다. 데이터가 나가는 지점 하나에
규칙을 두니 그 뒤로 재발이 없다.

| `성능개선.md` | 진단 → 구현 → 측정 (3부의 내용) |

## 2.1 8GB 에 넣기 — 어디서 터졌나

이미지 조건 + IAS 1 로 굽다리바리를 돌리면 **디코딩에서 7,350 MiB** 를 찍고 OOM 이었다.
양자화(FP8)와 오프로드를 걸어도 **디코딩 구간은 안 줄었다.** 가중치가 아니라 중간 활성값이 문제였기 때문이다.

| | 디코딩 피크 | 프로세스 피크 |
|---|---|---|
| 훅 없음 | 7,350 MiB → **OOM** | 6,588 MiB |
| 훅 있음 | **3,276 MiB** | **4,529 MiB** |

`SparseGroupNorm32` 를 4 MiB(2²²) 조각 단위 제자리 연산으로 바꾼 것이 컸다.
**양자화는 가중치를, 오프로드는 안 쓰는 모듈을, 조각 연산은 활성값을 줄인다** — 셋이 겹치지 않는다.
이걸 몰라서 "FP8 을 걸었는데 왜 안 줄지?" 로 하루를 썼다.

## 2.2 배운 것 — 절감책은 줄이는 대상이 다르다

```text
가중치 (모델 파라미터)   ← FP8 양자화
안 쓰는 모듈             ← CPU 오프로드
중간 활성값 (연산 중)    ← 조각 단위 연산 · CPU 메시 추출
```

VRAM 이 안 줄면 **"무엇이 차지하고 있는지" 부터 재야 한다.** 나는 그걸 안 재고 양자화 비율만 올렸다.

# 3부. 투창이 메워진다 — ERS 를 양방향으로 ★

이번 주에 가장 오래 붙든 문제이고, 가장 크게 틀린 진단이기도 하다.

## 3.1 증상

굽다리바리의 굽다리에는 투창(透窓)이 2단 8개 뚫려 있다. 복원 결과는 **통짜 원통**이 됐다.
가이드 이미지에 투창을 또렷하게 그려 넣어도 막혔다.

## 3.2 첫 진단은 틀렸다 — 재지 않고 추론했다

처음에 이렇게 판단했다:

> "투창은 64³ 격자에서 **폭 2~3복셀**뿐이라 FlexiCubes 가 양쪽 벽을 이어 버린다."

**그럴듯했지만 틀렸다.** 이 값은 26×72 짜리 성긴 전개 격자를 눈으로 보고 어림한 것이지 잰 게 아니었다.
격자 1칸을 복셀 1개에 맞춰 다시 재니 **투창은 7~16복셀 폭**이었다. 64³ 에서 충분히 크다.

## 3.3 실제 원인 — 단계별로 재니 보였다

어디서 막히는지 단계마다 채운 칸과 남은 창을 셌다.

| 단계 | 채운 칸 | 남은 창 |
|---|---|---|
| ① 원본 점군 (모델 입력) | 74.4% | **7개** (16×12 · 11×7 · 11×7 · 10×5 · 7×6) |
| ② 1단계 복셀 64³ | 92.7% | **2개** ← 여기서 사라진다 |
| ③ 2단계 LaS 메시 | 97.1% | 2개 |

**①→② 에서 5개가 사라진다.** 메시 추출(FlexiCubes)이 아니라 희소 구조 생성 단계다.

원인은 LaS-Comp 의 ERS(Explicit Replacement Stage)였다. 매 샘플링 스텝에서 이렇게 한다:

```python
pred_voxel[voxel_mask] = 1.0    # 관측된 곳은 "있다"로 강제
```

**"있다"만 강제하고 "없다"는 강제하지 않는다.** 단방향이다. 그래서 관측이 없는 칸 —
결손부든 투창이든 — 은 전부 모델의 사전확률에 맡겨지고, 모델은 "그릇 굽다리는 대개 막혀 있다"로 채운다.

## 3.4 고친 방법 — 투창과 결손을 구분한다

점군만 보면 둘 다 "관측이 없는 곳"이라 같아 보인다. 구분 기준을 **둘러싸임**으로 잡았다:

- **투창** — 사방이 관측된 표면으로 둘러싸인 빈 구멍
- **결손** — 관측 영역의 가장자리로 열려 있는 곳

굽다리 띠를 원통 좌표 (높이, 각도) 로 펼쳐 빈 영역에 연결 성분 번호를 매기고,
띠의 위·아래 끝에 닿지 않는 것만 투창으로 본다(θ 는 순환이니 3배 타일링해서 라벨링).
그 칸들의 디코더 로짓을 −1e4 로 눌러 "반드시 비어 있음"을 강제했다 — ERS 가
`decoder(x_0) > 0.0` 으로 판정하므로 이렇게 하면 양방향이 된다.

굽다리바리에서 투창 6개 · 716복셀을 잡았다(관측 복셀 17,563 대비 4.1%). `mask &= ~occ` 로
관측 복셀과 겹치지 않음을 보장했다.

## 3.5 결과 — 모든 축에서 좋아졌다

같은 유물·가이드·시드·설정(τ 0.6 · 섬 0.2% · 질감 k12 g0.8):

| 단계 | 기존 | 양방향 |
|---|---|---|
| ② 1단계 복셀 | 92.7% · 창 **2개** | **82.4% · 창 9개** |
| ③ 2단계 메시 | 97.1% · 창 **2개** | **86.6% · 창 10개** |

| 지표 | 기존 | 양방향 |
|---|---|---|
| 채움 (원본 면적) | 48.1% | **43.1%** |
| 복셀 1칸 밖 비율 | 17.12% | **16.55%** |
| 걸린 시간 | 697.0 초 | **473.1 초** |
| VRAM 피크 | 4,631 MiB | **4,566 MiB** |

채움이 5%p 줄었는데 **줄어든 것이 전부 덮지 말아야 했던 굽다리**다. 창 크기도 원본과 맞는다.
그리고 **시간이 32% 빨라졌다** — 빈 칸이 확정되니 모델이 그쪽에서 헤매지 않는 것으로 보인다.

## 3.6 훅이 안 걸려서 또 하루

고쳐 놓고도 효과가 없었다. 두 가지였다.

1. 훅을 `tools/` 에만 복사했는데 실행 시점의 `sys.path` 는 **저장소 루트**를 먼저 본다 → 양쪽에 둬야 했다.
2. `sample_sparse_structure` 를 감쌌는데 파이프라인이 부르는 것은 `lascomp_sample_sparse_structure` 였다 → 둘 다 감쌌다.

**"고쳤는데 안 바뀐다"면 고친 코드가 실제로 실행되는지부터 확인한다.** 이번 주에 이 교훈을 세 번 만났다(5부).

## 3.7 대안과 비교 — 왜 이 방법인가

| | 채움 (원본 면적) | 투창 띠 |
|---|---|---|
| 기본 | 48.1% | 99.6% · 창 6개(잡음 크기) |
| 높이 필터 (굽다리를 통째로 제외) | 32.4% | 57.1% · 원본과 완전히 동일 |
| **ERS 양방향** | **43.1%** | 86.6% · 창 10개 |

높이 필터는 투창을 완벽히 지키지만 **굽다리의 진짜 결손도 못 채운다.**
양방향은 투창만 지키므로 더 낫다.

# 4부. 한 원본에 복원본 여러 개

같은 유물을 여러 설정으로 복원하니 비교해서 올릴 곳이 필요했다.

## 4.1 스키마를 안 바꾸고 넣었다

`assets` 에 이미 `UNIQUE(artifact_id, media_type, variant)` 가 있었다.
**`variant` 에 슬러그를 붙이면 칸이 생긴다:**

```text
restored                 기존 (한 칸)
restored__las-comp-3d-v2 새 칸
restored__las-comp-3d-v3 새 칸
```

폴더도 `restored/<유물ID>__<슬러그>/` 로 나뉜다. 마이그레이션 없이, 라벨을 안 주면 기존과 똑같이 동작한다.
**제약을 이미 만족하는 값을 찾으면 스키마 변경이 필요 없다.**

## 4.2 실수 — 정확히 같은지 비교하면 접두사를 놓친다

미리보기를 만드는 `_artifact_folder()` 가 이랬다:

```python
if variant == "restored":        # ← restored__las-comp 는 여기 안 걸린다
    folder = originals/<id>      #    그래서 원본으로 미리보기를 만들었다
```

증상이 교묘했다. 오류가 없고, 미리보기가 **원본과 똑같이** 나왔다(삼각형 149,150 → 149,150, 4.76MB).
`startswith("restored")` 로 고쳤고, 재생성 후 778,098 → 199,999 로 정상이 됐다.

여기서 또 **"코드만 바꾸면 산출물은 안 바뀐다"** 를 만났다. 병합·배포를 하고도 화면이 그대로여서
한참 헤맸는데, 미리보기 파일은 새로 만들 때만 갱신된다. `POST /api/preview/rebuild` 를 불러야 했다.

# 5부. 거꾸로 선 미리보기 — 장치는 있었는데 연결이 없었다

"양손잡이 굽다리바리가 뒤집혀 있다"는 지적에서 시작했다.

## 5.1 원인 — 세 겹이었다

1. `app/orientation_overrides.json` 이 **있었다.** 방향을 손으로 고정하는 목록이고 6건이 적혀 있었다.
2. 그런데 **서버는 그 파일을 읽지 않았다.** 일괄 생성 도구(`local/make_preview.py`)만 썼다.
3. `blender_preview.py` 는 `--up`/`--flip` 을 받게 돼 있는데 **`main.py` 가 안 넘겼다.**

즉 장치는 세 조각이 다 있는데 **가운데가 끊겨** 있었다. 코드를 읽고서야 알았다.
`grep` 으로 `override` 를 찾았을 때 `main.py` 에서 하나도 안 나온 것이 결정적 단서였다.

## 5.2 자동 추정은 왜 틀리나 — 재서 알았다

`guess_orientation()` 은 **정점이 가장 몰린 끝면을 바닥으로** 놓는다. 그릇은 굽이 납작하니 맞는다.
그런데 토기는 몰린 쪽이 **아가리 테두리**다:

| 유물 | +Z 끝 정점비율 | −Z 끝 | 결과 |
|---|---|---|---|
| 빗살무늬토기 | **0.015** (아가리) | 0.003 (굽) | 아가리를 바닥으로 → 거꾸로 |
| 청자 은테 대접 | **0.005** (아가리) | 0.003 (굽) | 같은 이유 |

추정 규칙 자체는 **안 고쳤다.** 바로 서 있는 150여 건을 되돌릴 위험이 있어서, 틀린 카드만 목록에 적는
방식을 유지했다. **잘 되는 다수를 위험에 빠뜨리는 일반화보다, 틀린 소수를 명시하는 편이 안전하다.**

## 5.3 전수 대조

3D 카드 **163장**의 썸네일을 한 장에 모아 눈으로 훑고, 의심되는 것은 모델을 내려받아
`guess_orientation` 과 같은 계산을 다시 돌려 값을 확인했다. 5건을 고쳤고 목록을 6 → 20건으로 맞췄다.

**고칠 수 없는 것도 기록했다** — 굽다리바리 원본 4건은 뒤집힌 게 아니라 파일 좌표 자체가
30~40° 기울어 있다. `up`/`flip` 은 축을 고르는 장치라 임의 각도는 못 세운다.
"이건 이 방법으로 안 된다"를 커밋 메시지에 남겨야 다음 사람이 같은 시도를 반복하지 않는다.

# 6부. 채움부 질감 — 원본의 결을 통계로 옮기다

형상을 채워도 색이 단색이면 복원으로 안 보인다. 채움부에 원본과 같은 질감을 입히는 작업.

## 6.1 세 번 바꿨다

| 방식 | 문제 |
|---|---|
| ① 모델 예측색 | 어둡고 뭉개짐 (평균 RGB [46,43,23]) — 쓸 수 없었다 |
| ② 원본 텍스처를 거울 반사 | 얼룩·쐐기 무늬가 그대로 옮겨져 부자연스러움 |
| ③ **원본 결의 통계로 합성** | 채택 |

③은 이렇다:
1. 원본 표면에 표본점 1,600만 개를 찍어 채움 텍스처와 같은 (둘레, 높이) 격자에 **관측 이미지**를 만든다
   (굽다리바리는 원통의 **62.1%** 를 원본이 덮는다)
2. 완전히 관측된 64×64 창 **1,960개**에서 결의 통계를 잰다 — 굵기(방사 평균 파워 스펙트럼)와
   명암 분포(고역 밝기 히스토그램)
3. 그 통계대로 결을 합성(FFT, 둘레 한 바퀴가 주기)해 높이대 톤 위에 얹는다

원본 결 표준편차 [12.66, 12.80, 12.96] → 합성 [12.66, 12.80, 12.96]. **정확히 같다.**
FFT 주기를 둘레에 맞췄으므로 이음선도 없다.

## 6.2 "붙이기"는 안 됐다 — 반복이 보인다

처음엔 견본 이미지를 반사 타일링으로 그대로 붙였다. 사진 견본에 위→아래 밝기 기울기(161→137)와
가로 줄 구조가 있어서 **128px 주기 줄무늬**가 생겼다(행 평균 자기상관 +0.28).
고역 필터로 기울기는 뺐지만 줄 구조는 남았다 — 붙이는 방식 자체의 한계였다.
합성으로 바꾸니 행 평균 편차 7.9 → **1.25**, 128px 자기상관 **−0.16**.

## 6.3 색이 원본과 달라 보인 이유 둘 — 둘 다 재서 찾았다

**(가) 재질 유효값.** 원본 GLB 는 `metallicFactor 1 · roughnessFactor 1` 인데
metallicRoughness **텍스처**가 B(금속성)=0, G(거칠기)=255 다. 즉 유효값은 `metallic 0 · roughness 1`,
완전 무광. 채움에 factor 만 복사했더니 **금속처럼 어둡게** 나왔다.
이제 `factor × 텍스처 평균 = 유효값`을 쓴다.

> **factor 와 텍스처가 같이 있으면 둘의 곱이 실제 값이다.** factor 만 보고 판단하면 안 된다.

**(나) 톤의 표본 편향.** 높이대 중앙값을 **정점 표본** 색으로 잡았는데, 사진측량 메시는
어두운 틈·굽다리에 정점이 몰려 있어 면적 가중보다 어둡다:

| 높이 | 정점 표본 | 면적 가중(관측 이미지) |
|---|---|---|
| 0.15~0.25 (굽다리) | [116, 104, 86] | [132, 121, 103] |
| 0.35~0.45 | [109, 97, 79] | [122, 110, 92] |
| 0.75~0.85 | [161, 153, 137] | [151, 145, 128] |

**정점은 균일 표본이 아니다.** 메시에서 색·통계를 낼 때는 면적으로 가중해야 한다.
이걸 몰라서 "왜 어둡지" 를 눈대중으로 밝기만 올리며 헤맸다.

## 6.4 UV 로 굽는 이유

채움을 정점 색으로 두면 서버 미리보기에서 **단색**이 된다. 원본(텍스처)과 채움(정점색)을 한 오브젝트로
합치면서 흰색 더미 색 속성이 `COLOR_0` 을 차지하고 실제 색이 `COLOR_1` 로 밀리는데, three.js 는
`COLOR_0` 만 읽는다. 채움을 2048² UV 텍스처로 구우면 색 속성이 아예 없어져 이 문제가 사라지고
텍셀 밀도도 원본과 같아진다.

# 7부. 같은 방법이 안 되는 유물 — 한계를 재다

금동 일광삼존불(얇은 판에 새긴 저부조)에 같은 파이프라인을 써 봤다. **끝까지 돌아갔지만 결과는 못 썼다.**

| | |
|---|---|
| 실행 | 510.8초 · VRAM 피크 4,235 MiB · 예측 복셀 13,984 |
| 결과 | 부조가 전부 사라진 **덩어리** |

왜인지 쟀다:

| | 값 |
|---|---|
| 64³ 격자에서 차지하는 칸 | 32.7 × 64.0 × 24.9 |
| 광배 두께 | **7.0 칸** (윗부분 4.3 칸) |
| 얼굴·불꽃무늬 부조 요철 | **1~2 칸** ← 격자 아래 |

τ 를 0.6 → 6.0 까지 훑어 봤지만(채움 46.4% → 8.1%), 덮는 정도만 달라질 뿐 채움 내용이 틀린 건 그대로였다.
**막힌 곳은 파라미터가 아니라 희소 구조의 해상도다.** 이건 τ 로 못 넘는다.

대신 이런 유물은 대개 **좌우 대칭**이라 살아남은 쪽을 반사하면 부조까지 실측 그대로 옮길 수 있다.
회전대칭(물레 그릇)이 아니라 **면대칭**이라 회전축이 필요 없다 — 이쪽으로 이어서 해 보기로 했다.

# 8. 이번 기간의 결론

**네 번의 오진이 전부 같은 형태였다** — 그럴듯한 설명을 먼저 세우고 그것을 고치려 했다.

| 내가 생각한 원인 | 실제 원인 | 어떻게 알았나 |
|---|---|---|
| 투창이 2~3복셀로 좁다 | ERS 가 단방향이다 | 단계별로 채운 칸을 셌다 |
| 양자화가 부족하다 | 줄여야 할 게 활성값이었다 | 구간별 VRAM 을 쟀다 |
| 채움 재질이 무광이 아니다 | factor × 텍스처가 유효값이다 | 텍스처 채널을 열어 봤다 |
| 톤이 그냥 어둡다 | 정점 표본이 편향됐다 | 면적 가중과 나란히 쟀다 |

네 줄로 줄이면:

1. **"그럴 것이다" 와 "재 봤다" 는 다르다.** 어림한 값을 측정값처럼 쓰면 엉뚱한 곳을 고친다.
2. **어디서 망가지는지 단계별로 재면 원인이 드러난다.** ①→② 에서 창이 사라진 것을 보고서야 ERS 를 의심했다.
3. **"고쳤는데 안 바뀐다"면 고친 코드가 실행되는지부터 본다.** 이번 주에 세 번 만났다 —
   훅 경로, 훅 메서드 이름, 그리고 미리보기 재생성.
4. **잘 되는 다수를 위험에 빠뜨리는 일반화보다 틀린 소수를 명시하는 편이 안전하다.**
   방향 추정 규칙을 고치는 대신 목록에 적었다.

그리고 **안 되는 것을 안 된다고 기록하는 것도 산출이다.** 30~40° 기울어진 4건, 얇은 판의 64³ 한계 —
이걸 안 적으면 다음 사람이 같은 시도를 반복한다.

```text
1부 화면 ─→ 2부 8GB 진입 ─→ 3부 ERS ─→ 4~5부 서버 반영 ─→ 6부 질감 ─→ 7부 한계
 쓰이게      돌아가게        제대로     팀이 보게           보이게       경계를 긋다
```
