# 1부. 배포 — 설계한 것을 실제로 띄우기

## 1.1 구성

```text
브라우저 ──:80──▶ nginx ──┬─▶ /              화면(HTML·JS)      직접 서빙
                          ├─▶ /files/        원본 자료 9.4GB     직접 서빙 + autoindex
                          ├─▶ /preview/      GLB·썸네일 776MB    직접 서빙 + gzip_static
                          └─▶ /api/ ──▶ 127.0.0.1:8412  FastAPI (systemd, uvicorn --workers 2)
                                                            └─▶ SQLite catalog.db (WAL)
```

**앱은 JSON 만 만든다.** 큰 파일은 전부 nginx 가 낸다. 이 분리가 나중에 여러 번 도움이 됐다 —
앱을 재시작해도 다운로드는 끊기지 않고, 앱 버그가 파일 서빙을 망가뜨리지 못한다.

| 결정 | 이유 |
|---|---|
| 포트 8412 (앱), 외부 노출 없음 | SSAFY "기본 포트 피하라" 지침. 8000·8080 은 다른 팀과 충돌 |
| systemd `Restart=always` | 재부팅·크래시 후 사람 손 없이 살아나야 한다 (AT-09) |
| 인증 없음 | 팀 내부 도구, 링크만 있으면 쓰게 (계획서 AS-04) |
| Docker 안 씀 | 서버 한 대·서비스 한 개. 이미지 빌드·레지스트리가 순손실 |

## 1.2 배운 것 — systemd 에는 PATH 가 없다

```ini
ExecStart=/home/ubuntu/.local/bin/uv run --project /srv/catalog uvicorn app.main:app --host 127.0.0.1 --port 8412
#          ↑ 절대경로여야 한다
```

셸에서 되던 `uv run` 이 서비스로 올리면 실패한다. systemd 는 로그인 셸이 아니라
**환경변수를 물려받지 않는다.** 같은 함정을 이번 주에 한 번 더 만났다 — Blender 경로(5.1).

## 1.3 수용시험을 먼저 써 둔 것이 효과가 있었다

지난 주에 구현 전에 써 둔 `AS-AT-01~10` 을 그대로 돌렸다.

| 항목 | 결과 |
|---|---|
| AT-01~07 목록·검색·다운로드·미리보기 | 통과 |
| AT-08 텍스트 압축 | 통과 — OBJ 23.9MB → 6.6MB (`gzip_static`) |
| AT-09 재부팅 후 자동 복구 | 통과 — 실제로 `reboot` 해서 확인 |
| AT-10 새 zip 15분 내 투입 | 미실행 |

**완료 기준이 문서에 있으면 "다 됐나?" 를 감으로 판단하지 않게 된다.** 9개는 통과, 1개는
미실행이라고 쓸 수 있다. 이게 "대충 됐다" 보다 훨씬 쓸모 있는 상태 보고였다.

## 1.4 OBJ 는 한 벌이다 — 폴더 ZIP

팀원 지적: **"OBJ 는 폴더 전체가 있어야 열린다."** 맞다. OBJ 는 모델·재질(MTL)·텍스처가
세 파일로 나뉘어 있고 서로를 파일명으로 참조한다. 하나만 받으면 회색 덩어리가 된다.

```
GET /api/groups?asset=<카드>     → 폴더별 묶음 목록
GET /api/zip?asset=&group=       → 즉석 ZIP (만든 것은 zips/ 에 캐시)
```

> **막힌 곳** `/api/cards/{asset_id:path}` 가 `:path` 라 하위 경로를 전부 삼켰다.
> `/api/cards/<카드>/groups` 가 카드 ID 의 일부로 먹혀 404. → 쿼리 파라미터로 바꿨다.
> **경로 변수에 `:path` 를 쓰면 그 아래에 하위 경로를 더 만들 수 없다.**

# 2부. 자동 배포 — Jenkins, 그리고 권한을 어디까지 줄까

## 2.1 목표를 좁혔다

"`infra/web/` 을 고쳐 `dev` 에 병합하면 서버에 반영된다." 그 이상은 하지 않기로 했다.
저장소에는 언리얼 프로젝트도 있어서, **아무 병합이나 서버를 건드리면 안 된다.**

```groovy
// Jenkinsfile — 바뀐 파일에 infra/web/ 이 없으면 아예 배포하지 않는다
def changed = sh(returnStdout:true, script:'git diff --name-only HEAD~1 HEAD').trim()
if (!changed.split('\n').any { it.startsWith('infra/web/') }) {
  currentBuild.result = 'NOT_BUILT'; error('infra/web 변경 없음 — 배포 건너뜀')
}
```

## 2.2 권한을 세 겹으로 나눴다

파이프라인만 믿으면 안 된다. **Jenkinsfile 은 저장소 안에 있어서 MR 로 고칠 수 있다.**
누가 파이프라인을 고쳐 `rm -rf /` 를 넣으면? 그래서 실제 배포는 저장소 **밖**에 둔다.

```text
① 파이프라인 경로 필터        Jenkinsfile — 저장소 안 (MR 로 바꿀 수 있음)
② 실제 배포 스크립트          /srv/catalog/bin/deploy-from-workspace.sh — root 소유, 저장소 밖
③ sudoers 는 그 한 줄만 허용   jenkins ALL=(root) NOPASSWD: /srv/catalog/bin/deploy-from-workspace.sh
```

②는 `server/app` 과 `server/web` 만 rsync 하고 **`files/`·`preview/`·`catalog.db` 는 건드리지 않는다.**
그래서 코드를 아무리 배포해도 자료와 DB 는 안전하다. 실제로 이번 주에 배포를 열 번 넘게
했는데 자료가 한 번도 다치지 않았다.

**배운 것: 자동화의 권한은 "무엇을 할 수 있나" 가 아니라 "무엇을 못 하게 했나" 로 설계한다.**

## 2.3 가장 크게 헤맨 것 — IPv6

플러그인 설치가 **94개 전부** 실패했다. 로그는 그냥 타임아웃.

```bash
curl https://updates.jenkins.io/...     # 멈춘다
curl -4 https://updates.jenkins.io/...  # 즉시 받아진다
```

이 EC2 는 **전역 IPv6 주소가 없는데 시스템이 IPv6 를 먼저 시도**한다. 실패를 기다리다 죽는다.

```bash
echo 'precedence ::ffff:0:0/96  100' | sudo tee -a /etc/gai.conf   # 시스템 IPv4 우선
# Jenkins JVM 에도 -Djava.net.preferIPv4Stack=true
```

그 실패 때문에 설치 마법사가 되돌아가 `Unlock Jenkins` 가 다시 뜨고 초기 비밀번호가
거부되는 2차 문제까지 생겼다. **한 가지 원인이 전혀 다른 증상으로 나타난다** —
"비밀번호가 틀렸다" 를 비밀번호 문제로 보면 영원히 못 고친다.

## 2.4 검증

```text
MR 병합 → 웹훅(HTTP 200) → 빌드 #5
  "바뀐 파일 33개 · infra/web 포함: true" → 배포 완료 · API 정상 → SUCCESS (35초)
```

# 3부. 쓰면서 드러난 것 — 설계로는 안 보이던 것들

## 3.1 즐겨찾기는 "팀 공용" 이어야 했다

처음엔 브라우저 `localStorage` 를 생각했다. 그런데 팀 도구에서 **내가 찍은 별을 남이 못 보면
의미가 없다.** 서버 표로 바꿨다.

```sql
CREATE TABLE favorites(asset_id TEXT PRIMARY KEY, note TEXT, created_at ...);
-- FK 를 일부러 걸지 않았다: 재스캔이 assets 를 지우고 다시 만들어서, FK CASCADE 면 별이 전부 날아간다
```

**재스캔이 자료를 지우고 다시 만드는 구조라면, 사람이 만든 것은 그 바깥에 둬야 한다.**
같은 이유로 사람이 적은 메모·태그·복원 방식도 재스캔 때 보존한다.

## 3.2 유물이 누워 있다 — 148건

3D 썸네일 수십 건이 옆으로 누워 있었다. 원인은 **파일마다 위(up) 축이 다르다.**

| 머리말 | 위 축 |
|---|---|
| `# WaveFront *.obj file` | Z |
| `# Blender v3.2.1 OBJ File` | Y |

그런데 **머리말과 실제가 다른 파일도 있었다.** 머리말로 판단하는 방식은 버리고 형상으로 추정했다.

```python
# 바닥이 평평한 슬랩인 정도 × (0.5 + 원형 단면 비율) 이 가장 큰 축을 '위' 로 본다
score = {k: max(flat[(k,-1)], flat[(k,+1)]) * (0.5 + circ[k]) for k in range(3)}
```

148건을 다시 만들었다(19.7분). 판정은 **Y 87 · Z 40 · X 8** 로 갈렸다 — 제각각이라는 게
숫자로 확인됐다. 추정이 틀린 것은 `orientation_overrides.json` 에 손으로 적었다(현재 13건).

> **판단이 애매할 때 정답지는 그 유물의 2D 사진이었다.** 금관은 "원형 관테" 라고 생각해
> 방향을 바꾸려 했는데, 소장품 사진을 보니 **고깔형 모관**이어서 원래 방향이 맞았다.
> 반대로 청자 조롱박 병은 위아래가 뒤집혀 있었다(작은 구가 위여야 한다).
> **같은 자료의 다른 표현을 서로 검증에 쓸 수 있다.**

## 3.3 상세 화면 — 전부 보여주면 아무것도 안 보인다

오른쪽 패널에 여섯 덩어리(폴더 ZIP·파일 목록·유물 정보·다른 자료·복원본 등록·메모)를
다 펼쳐 놨더니, **"이게 무슨 유물인지" 가 파일 목록 밑에 파묻혔다.**

```text
전                                후
─────────────────────────        ─────────────────────────
폴더 ZIP 4개                      [유물 정보] [다운로드 6] [메모]
파일 목록 6개                     ─────────────────────────
유물 정보  ← 여기 보려면 스크롤     설명
다른 자료                         한글명 · 시대 · 재질 …
복원본 등록 폼
메모 폼
```

**높이를 왼쪽 뷰어 칸과 같게 맞춰** 페이지 전체 스크롤을 없앴다(문서 높이 1174 → 1000 =
창 높이). 정보를 읽는 동안 3D 뷰어가 화면에서 사라지지 않는다.

배운 것: **화면 설계에서 "무엇을 보여줄까" 보다 "무엇을 먼저 보여줄까" 가 어렵다.**
자주 쓰는 이동(같은 유물의 다른 자료)은 탭 위로 올려 어느 탭에서도 보이게 했다.

# 4부. 자료를 넣고 빼는 길

## 4.1 복원본 등록 — 메타는 원본에서 상속한다

복원 결과를 올릴 때 유물명·시대·재질을 다시 입력하게 하면 틀린다. **파일만 받고 나머지는
원본의 `_meta.json` 에서 가져온다.**

```text
POST /api/artifacts/<유물>/restored   (multipart)
  확장자로 폴더 배치 → <소장품번호>_restored_<역할>.<ext> 로 개명
  → OBJ 의 mtllib, MTL 의 map_* 를 새 파일명으로 재작성
  → _meta.json 상속(kind=restored, counterpart 양방향) → 재스캔 → 미리보기 생성
```

| 막힌 곳 | 원인 · 해결 |
|---|---|
| OBJ 가 `model-2.obj` 로 저장됨 | 중복 번호를 확장자 구분 없이 셌다. `model.obj` 와 `model.mtl` 은 역할이 같아도 파일명이 안 겹친다 → 번호를 **(역할, 확장자)** 로 센다 |
| 사진이 `_diffuse-2.jpg` 로 저장됨 | 이미지를 무조건 텍스처로 봤다 → 행선지가 `photo_2d` 면 `_photo_01` 로 |
| 이름이 바뀌자 텍스처를 못 찾음 | OBJ·MTL 내부 참조를 새 이름으로 재작성. **안 올린 파일을 가리키면 경고**로 알려준다(회색 모델의 원인) |

## 4.2 추측을 없애는 게 검증보다 싸다

새 유물 등록에서 처음엔 **이미지가 텍스처인지 사진인지 이름으로 짐작**하려 했다
(`diffuse`·`normal` 이 있으면 텍스처, `photo` 가 있으면 사진…). 팀원 지적으로 접었다:
**"3D 등록인지 2D 등록인지 정해서 올리면 안 돼?"** 그리고 한 걸음 더 — **"칸을 다르게 해서."**

```text
┌─ 3D 파일 · 폴더 ─────┐  ┌─ 유물 사진 ────────┐
│ 여기 이미지 = 텍스처  │  │ 여기 이미지 = 사진  │
└─────────────────────┘  └────────────────────┘
```

어느 칸에 넣었는지가 **곧 답**이라 서버가 짐작할 일이 없다. 사고(모델 텍스처가 '유물 사진'
으로 등록되는 일)가 **구조적으로** 안 난다. 3D·2D 카드는 같은 `artifact_id` 아래 생겨
자동으로 "같은 유물의 다른 자료" 로 연결된다.

**배운 것: 휴리스틱으로 맞히려 하기 전에, 사용자가 이미 아는 정보를 받을 자리를 만든다.**

## 4.3 삭제는 "지우기" 가 아니라 "옮기기" 로 만들었다

인증이 없는 서버(AS-04)에서 진짜로 지우는 API 는 위험하다. 실수 한 번에 자료가 사라진다.

```text
DELETE /api/artifacts/<유물>?confirm=<유물>&what=all
  → files/_trash/<날짜시각>_<유물>/ 로 **옮긴다**
  → scan.py 는 originals·restored·aihub 만 훑으므로 목록에서는 사라진다
  → 폴더를 도로 옮기고 재스캔하면 되살아난다
```

`confirm` 에 유물 ID 를 그대로 다시 적어야 진행된다(화면도 타이핑을 받는다).

**배운 것: 되돌릴 수 없는 동작은 되돌릴 수 있는 동작으로 바꿔 구현할 수 있는지 먼저 본다.**

## 4.4 서버에서 GLB 를 만들 수 있었다

계획서에는 "변환은 로컬 GPU 에서"(AS-05) 라고 적어 뒀다. 그런데 업로드 기능을 만들면
**서버가 스스로 미리보기를 만들어야** 올린 사람이 바로 볼 수 있다.

확인해 보니 **데시메이션·텍스처 축소·glTF 내보내기·썸네일 렌더는 전부 CPU 작업**이었다.
썸네일도 Workbench 엔진이라 소프트웨어 렌더로 충분하다. GPU 없는 4코어 서버로 됐다 —
**실측 8.1초 / GLB 0.57MB.**

`AS-05` 는 148건을 **한 번에** 돌릴 때의 이야기였다. 제약을 그대로 믿지 말고
**그 제약이 왜 있었는지**를 봐야 한다(지난 주 언리얼 제약 목록에서 배운 것과 같다).

# 5부. "미리보기가 안 뜬다" — 원인 추적

이번 주 가장 많이 배운 부분이다. 팀원 보고: **"유물 등록·복원본(GLB) 등록 둘 다 미리보기가
안 떠요. 혹시 파일 형식 때문에 서버 블렌더랑 꼬인 게 아니야?"**

## 5.1 형식 문제가 아니었다 — `libEGL`

작업 기록을 먼저 봤다. 세 건 모두 같은 줄이었다.

```json
{"state": "failed", "error": "blender rc=-6: Couldn't open libEGL.so.1: cannot open shared object file"}
```

**Blender 가 썸네일을 렌더할 때** 그래픽 라이브러리를 못 찾아 죽었다. GLB 내보내기는 그
앞 단계라 **파일은 이미 생겼는데** DB 에 경로가 기록되지 않아 "미리보기가 아직 없습니다" 로
보였다. 형식과는 아무 상관이 없었다.

**왜 못 잡았나 — 검증을 잘못했다.**

```bash
blender -b --version    # 이것만 확인했다. 통과한다.
                        # 버전 출력은 그래픽을 초기화하지 않는다!
```

설치 확인을 `--version` 으로 하면 **"실행된다" 는 알지만 "동작한다" 는 모른다.**
가이드의 확인 절차를 **실제로 한 장 렌더하는 것**으로 바꿨다.

```bash
sudo apt-get install -y libegl1 libglx0 libgl1-mesa-dri libxext6
blender -b --python-exit-code 1 -P blender_preview.py -- "$SRC" /tmp/t.glb /tmp/t.png 60000 | grep PREVIEW_REPORT
ls -l /tmp/t.glb /tmp/t.png     # 둘 다 나와야 한다
```

> **가장 값진 교훈: "설치됨" 과 "동작함" 은 다르다.** 그리고 검증 명령이 실제 사용 경로를
> 지나지 않으면, 그 검증은 통과해도 아무것도 보장하지 않는다.

## 5.2 GLB 는 변환을 기다릴 필요가 없었다

팀원 지적: **"glb는 바로 띄울 수 있는 거 아니야?"** 맞다. GLB 는 브라우저가 바로 읽는
형식이다(glTF 의 단일 파일 형태 — 메시·재질·텍스처가 한 파일에).

```text
전: 업로드 → Blender 변환 대기(10~30초) → 그제서야 볼 수 있음
후: 업로드 → 올린 GLB 를 그대로 미리보기로(1.8초) → 뒤이어 경량 판본·썸네일로 교체
```

30MB 이하면 그대로 쓴다. **가진 것을 그대로 쓸 수 있는지 먼저 보고, 최적화는 나중에 겹친다.**

## 5.3 형식별로 무엇이 도는지 표로 정리했다

| 형식 | 처리 | 실측 |
|---|---|---|
| GLB | 그대로 사용 + 뒤이어 경량화 | 즉시 · 5.1초에 0.59MB |
| OBJ(+MTL·텍스처) | Blender — 20만 삼각형·2K 텍스처 | 8.8초 |
| PLY · STL | Blender | 3.7초 |
| LAS(점군) | **Blender 가 못 읽는다** → 순수 파이썬으로 glTF POINTS + PIL 썸네일 | 0.1초 (18만 점) |

LAS 처리기가 서버에 **아예 없었다**(내 PC 에만 있었다). 옮겨 심고 결과가 기존 파일과
**바이트 단위로 동일**함을 확인했다.

## 5.4 캐시는 상태다 — "다른 유물이 뜬다"

또 다른 보고: **목록 썸네일과 상세 뷰어가 서로 다른 유물로 보인다.** 원인이 세 가지였고,
데이터 문제는 하나도 없었다. (GLB 148개에 박힌 텍스처를 각 유물의 실제 텍스처와 대조해
전부 자기 것임을 확인했다 — 최대 차이 0.6, 중앙값 0.1)

| # | 원인 | 해결 |
|---|---|---|
| 1 | **HTTP 캐시** — `/preview/` 7일, `/files/` 1시간. 파일을 다시 만들어도 URL 이 같으면 브라우저는 옛것을 쓴다. 썸네일만 새것이고 GLB 는 옛것이면 서로 다른 유물처럼 보인다 | URL 에 `?v=수정시각` |
| 2 | **서버 파일 1건이 다른 판본** — 톤 보정 때 "GLB 는 안 바뀐다" 고 **한 파일만 확인하고** PNG 만 보냈다. 데시메이션 결과가 미세하게 달라진 게 1건 있었다 | 전송 후 항상 양쪽 해시 대조 |
| 3 | **앞 카드의 그림이 남음** — 화면을 비우면서 뷰어 객체를 남겨 둬, 화면에 없는 캔버스에 계속 그렸다 | 비울 때 뷰어도 버린다 |

그리고 결정적인 한 건. 팀원이 **"내가 테스트했던 이름 1 그 2D 사진 때문에 굽다리바리
사진이 제대로 안 올라가는 것 같아"** 라고 했다. 파일은 정상이었다(3000×2000, HTTP 200).

```text
"1" 등록      → new20260911_01 → .../new20260911_01/photo_2d/new20260911_01_photo_01.jpg
"1" 삭제      → 번호가 비워짐
굽다리바리 등록 → new20260911_01 → 경로가 글자 하나까지 같다 ←──────────┘
```

**지운 ID 를 재사용한 것이 캐시 위험을 증폭했다.** 경로가 완전히 같아서 브라우저가 1시간
캐시에서 지운 자료의 사진을 꺼내 보여줬다. → 지운 번호를 다시 쓰지 않게 했다
(`originals`·`restored`·휴지통·DB 를 모두 보고 빈 번호를 고른다).

> **배운 것: 캐시는 성능 설정이 아니라 상태다.** 내용이 바뀌면 이름(URL)도 바뀌어야 한다.
> 그리고 **식별자 재사용은 그 자체로 버그를 만든다** — 지운 것과 새것이 같은 주소를 갖는다.

## 5.5 눈대중 대신 재기 — 밝기

썸네일이 어둡다는 지적에 조명을 올렸더니 이번엔 **상세 뷰어가 너무 밝다**는 지적이 왔다.
양쪽을 감으로 맞추다 실패한 것이다. 그래서 **물체 픽셀의 평균 밝기를 숫자로 재서** 맞췄다.

| | 썸네일(기준) | 조명 올린 뒤 | 맞춘 뒤 |
|---|---|---|---|
| 나전침 | 19 | 57 | 26 |
| 죽순 주전자 | 71 | 107 | 58 |
| 백자 병 | 129 | 229 | 127 |

원인은 둘이었고 **서로 달랐다.**

- **썸네일**: Blender 5 의 기본 색 변환이 **AgX**(필름 톤). 스캔 텍스처에는 촬영 조명이 이미
  구워져 있는데 필름 톤을 한 번 더 씌우니 청동·나전이 형체를 잃었다 → `Standard` + 0.5EV
- **뷰어**: MTL 에서 온 낮은 거칠기 때문에 반사가 강했다 → `metalness=0, roughness=0.95`.
  그리고 **전방위광(Ambient)을 크게 주면 어두운 유물이 통째로 들뜬다** → 방향광 위주로

유물마다 원래 색이 크게 다르니 결국 **밝기 슬라이더**(0.4~2.4배)를 화면마다 하나 뒀다.
비교 모드에서는 좌우를 따로 조절한다 — 복원본이 원본보다 훨씬 밝은 짝이 많다.

## 5.6 프로세스가 여러 개면 메모리에 상태를 두면 안 된다

미리보기 진행 상태를 파이썬 딕셔너리에 담았는데, API 는 `uvicorn --workers 2` 로 돈다.
**업로드를 받은 워커와 상태를 묻는 워커가 다르면 절반은 아무것도 못 본다.**
실패해도 화면은 "만드는 중" 만 3분 보여주고 끝났다.

```text
/srv/catalog/jobs/<asset>.json        상태 (tmp 후 원자적 교체)
/srv/catalog/jobs/<asset>.json.lock   중복 실행 방지 (O_EXCL, 32분 지나면 회수)
```

파일로 옮기니 워커 수와 무관해지고 재시작해도 상태가 남는다.

# 6. 이번 기간의 결론

**설계와 운영은 다른 기술이다.** 지난 주는 "무엇을 만들까" 였고 이번 주는 "왜 안 보이지" 였다.
운영에서 배운 것을 네 줄로 줄이면:

1. **"설치됨" 과 "동작함" 은 다르다.** 검증 명령이 실제 사용 경로를 지나야 한다
   (`blender --version` 은 렌더 실패를 통과시킨다).
2. **캐시는 상태다.** 내용이 바뀌면 URL 도 바뀌어야 하고, 식별자를 재사용하면 그 위험이 커진다.
3. **눈대중으로 맞추다 두 번 틀리면 재야 한다.** 밝기는 숫자로 재서 한 번에 맞췄다.
4. **추측을 없애는 설계가 검증보다 싸다.** 2D/3D 칸을 나누니 오분류가 구조적으로 사라졌다.

그리고 **팀원의 지적이 가장 좋은 버그 리포트였다.** 이번 주 고친 것 중 절반은 내가 아니라
쓰는 사람이 먼저 발견했다 — "OBJ 는 폴더째 있어야 열린다", "칸을 다르게 해서",
"GLB 는 바로 띄울 수 있는 거 아니야?", "그 2D 사진 때문인 것 같아". 특히 마지막은
**원인 가설까지 정확했다.** 쓰는 사람이 없으면 안 보이는 결함이 있다.

```text
1부 배포 ─→ 2부 자동 배포 ─→ 3~4부 기능 ─→ 5부 원인 추적
 띄웠다      고치기 쉬워졌다    팀이 쓰기 시작했다   쓰니까 부서진 곳이 보였다
```
